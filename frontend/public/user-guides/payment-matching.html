Payment Matching Queue

The Payment Matching Queue lets strata managers review and confirm incoming bank payments that the system was unable to automatically allocate to a lot. The matching engine compares each bank transaction against all open levies and scores the best candidate — you only see items that scored below the auto-allocate threshold or that require human judgement.

Who can access this? Only Strata Admins, Strata Managers, EC Members (including the EC Chairperson — chairperson is an EC Member position, not a separate role), and Super Admins can view and action the matching queue. Owners and tenants do not have access.

Getting there

Dashboard → Financial → Payment Matching. The page is only visible when the Financial Integration Layer v2 feature toggle is enabled for your building.

Where queue items come from

Queue items are created when bank-feed transactions are passed through the MatchingEngine. For Demo Bank backfills, the platform first syncs staged bank transactions into the canonical PostgreSQL bank transaction table, then scores each transaction against the building's candidate lots and open levy data.

Older transactions can also be replayed through a rematch operation. Rematch does not create duplicate review items; if an item already exists for the same canonical bank transaction, it is skipped.

High queue volume is expected after a historical backfill. A backfill may create many unidentified items when legacy payment descriptions do not include a CRN, lot number, or payer name. Treat those as review workload, not as confirmed allocations.

How the matching engine works

When a bank transaction arrives, the engine runs up to eight detection layers in order from highest to lowest confidence. It stops as soon as a layer returns a score at or above the auto-allocate threshold (default: 90%).

Layer Method Score Outcome
L1 – Exact CRN BPAY Reference Number (MOD10V05 checksum) 100% Auto-allocated
L2 – NPP E2E ID PayID / OSKO End-to-End Reference 95% Auto-allocated
L3 – Partial CRN CRN prefix found in payment description 90% Review queue
L4 – Unit Ref + Amount Unit number in description + matching levy amount + within 30 days of due date 85% Review queue
L5 – Owner Name (fuzzy) Jaro-Winkler name similarity ≥ 88% + exact levy amount 80% Review queue
L6 – Surname fuzzy Surname token-ratio ≥ 80% (amount ignored) 60% Review queue
L7 – Unique amount Exact amount matches exactly one open levy (no other lot has the same amount) 50% Review queue
L8 – Unidentified No layer matched 0% Unidentified

Agency sweeps

If the payment amount is larger than the highest individual open levy, and the payer name matches a known real-estate agency in the system, the engine flags it as an Agency Sweep rather than running the normal layers. These require manual splitting across lots.

Stats bar

At the top of the page you will see four live metrics:

  • Queue depth — number of items currently awaiting a decision
  • SLA breaches — items that have exceeded the 24-hour decision window
  • Auto-match rate — percentage of payments in the last 7 days that were allocated automatically without human review
  • Total / Auto (7 days) — raw counts behind the rate

Taking action on a queue item

Each queue item shows the bank transaction details (description, amount) and the engine's best candidate lot. Expand the item to see all candidate scores. You have three actions:

Allocate

  1. Click Allocate on the item.
  2. The dialog pre-fills the best candidate lot and the transaction amount.
  3. Confirm the Lot ID (or change it if the engine picked the wrong lot).
  4. Verify the Amount (AUD) — edit the dollar amount (for example, 123.45) if you are applying a partial payment.
  5. Add optional notes, then click Confirm Allocation.

The system records a MatchDecisionRecorded event with a frozen snapshot of all candidates at the time of decision. This event is immutable and forms part of the trust ledger audit trail.

Mark as Unidentified

Click Unidentified if the payment cannot be linked to any lot. The item is closed and the event is logged. You may need to follow up with the payer separately.

Reject

Click Reject to dismiss the item (for example, a refund or a payment to the wrong account). The decision is logged with any notes you add.

Decisions are final. Once an item has been allocated, rejected, or marked unidentified, it moves to a closed status and cannot be re-opened. The audit event is immutable.

Filtering and searching

  • Use the Status buttons (Pending / Allocated / Rejected / Unidentified / All) to filter the list.
  • Use the Search box to filter by payment description, best lot ID, or item ID.

SLA — decision within 24 hours

Every item in the review queue carries an SLA deadline of 24 hours from when it was created (48 hours for agency sweeps). Items that breach the SLA are highlighted in the queue and counted in the stats bar. Keeping the SLA breach count at zero is important for the building's compliance health score.

Building isolation

The queue is strictly scoped to your building. Managers with access to multiple buildings will only see queue items for the building they are currently logged into. No data from another building is ever visible.
