Historical Reconstruction

Historical Reconstruction lets you rebuild levy and expense history for financial years where your building does not have complete dated payment records — for example, years before your building moved onto this platform. It never writes to your building's financial ledger directly. Every reconstruction goes through a reviewed, human-approved batch before anything is generated, and generated data still has to be synced through the same bank-feed pipeline as a real payment before it can affect any report.

Who can access this? Strata Admins, Strata Managers, and Super Admins can prepare batches. Approving, generating, syncing, and reversing a batch is restricted to Strata Admins and Super Admins. Applying a levy regeneration and reversing a batch are Super Admin only. Owners, tenants, and EC Members do not have access to this page.

Getting there

Dashboard → Financial → Historical Reconstruction. The page is only visible when the Historical Financial Reconstruction feature toggle is enabled for your building. If it is enabled but the separate Historical Reconstruction Posting toggle is off, you can still prepare and preview batches, but Approve/Generate/Sync/Reverse and levy-regeneration Apply stay disabled until posting is turned on — the page tells you this explicitly rather than just hiding the buttons.

Preparation versus posting

The workflow is split into two stages, gated by two separate feature toggles:

  • Preparation (create, extract, preview, submit for review, plan a levy regeneration) never changes anything a resident or owner can see. It is safe to explore.
  • Posting (approve, generate, sync, reverse, apply a levy regeneration) writes real data — generated transactions, synced bank rows, or regenerated levy items. These actions are locked behind a separate toggle and tighter role requirements precisely because they are not reversible in the same casual way preparation is.

Before you start: check for existing financial history

The Reconstruction Batches tab shows a status card as soon as the page loads, before you create anything: "No financial history found — ready to generate" (blue) if the building has no recorded levy payments yet for the last 3 financial years, or "Partial financial history found (N of M lot/year/fund periods already paid) — generating from the proposed budget will skip those periods" (amber) if some periods are already covered. Either way, you can proceed — the generator (below) automatically skips any lot/year/fund combination that already has a real recorded payment, so you never end up with duplicate levy payments for the same period.

Import & Generate — starting from a source document

Added 2026-07-27. If your building doesn't already have a proposed budget or fund closing balances entered in the platform — for example, you're onboarding a building using figures from an AGM pack, a spreadsheet handed over by the outgoing manager, or any other document your committee or manager has on hand — use the Import & Generate tab before creating a batch. It accepts a CSV or JSON file with any combination of these columns, and tolerates gaps in all of them:

  • Proposed Admin fund amount for a year
  • Proposed Sinking fund amount for a year
  • Closing balance per fund for a year
  • Actual spend per expense category for a year
These are declared figures, not verified transactions. Whatever you upload here is the source of truth you are supplying — the platform does not check it against a bank statement. Everything generated downstream from it is clearly labelled "Reconstructed / Estimated" (see the Reconciliation page) until a real bank connection confirms it independently.

After import, the wizard shows a coverage summary — which years and funds had data, and which were missing — so you can see exactly what will and won't be reconstructed before you proceed to Create Batch below. Missing data is skipped, not treated as zero.

Choosing how a batch generates its data

When you click Create Batch, choose a Generation source:

  • Generate from proposed budget (Admin/Sinking/GST) — the default, and the option you should use for almost every building. Works for any building: it computes one combined Admin+Sinking(+GST) payment per lot per quarter directly from your building's proposed levy budget and unit entitlements, and automatically skips any period that already has a real recorded payment (see the status card above). If you imported expense-category data via Import & Generate, the same batch also produces one dated expense transaction per category per year, merged into the same preview and manifest as the income side.
  • Link existing Demo Bank rows — an older option that only works if your building already has matching Demo Bank transaction rows created some other way. It does not generate any new data, only links what is already there. Most buildings should not need this option.

The batch workflow

Each reconstruction batch covers one financial-year range and moves through these stages in order:

Stage What it does Who
Create Starts a batch in "draft" status for a financial-year range and a reconstruction method. No data is written yet. Strata Admin / Manager / Super Admin
Extract Marks the batch's source facts as gathered (existing bank data, evidence documents you've already uploaded separately). Strata Admin / Manager / Super Admin
Preview Computes what the reconstruction would produce — expected transaction count, expected totals — without saving anything. Run this as many times as you like. Strata Admin / Manager / Super Admin
Submit for Review Recomputes the same calculation one more time (never trusts an old preview) and saves it as the batch's official manifest. This is the point of no casual return — the batch now needs a formal approval before anything else can happen. Strata Admin / Manager / Super Admin
Review A human check of the saved manifest, with optional notes. This does not approve anything by itself — see "Why approval may be unavailable" below. Strata Admin / Super Admin
Approve A second, genuinely different admin's sign-off on the reviewed manifest. See "Why approval may be unavailable" below. Strata Admin / Super Admin
Reject (added 2026-07-27) Sends a batch that's in "Needs Review" back to "Extracted" with a required reason, instead of approving it. Use this when the manifest looks wrong — a source figure needs correcting, or the reconstruction method chosen doesn't fit. The batch keeps its history; you re-run Preview and Submit for Review once the underlying data is fixed. Reject is only available from "Needs Review" — it cannot be used on a draft batch or one that's already been approved. Strata Admin / Super Admin
Generate Turns the approved manifest into staged bank-feed rows. Still not visible in any resident-facing report at this point. Strata Admin / Super Admin
Sync Runs the same bank-feed sync pipeline used for real bank statements, scoped to just this batch's rows. This is the step that actually makes the reconstructed data visible in matching, arrears, and levy reports. Strata Admin / Super Admin
Sync tells you the truth about what happened. If nothing matched or any row failed, the batch is marked "Failed", not "Synced" — you will never see a false "Synced" status for a sync that didn't actually move any data.

Why approval may be unavailable

Approval is a genuine two-person process, enforced by the platform, not just a confirmation dialog:

  1. Once a batch reaches "Needs Review," any Strata Admin or Super Admin sees a Review button. Clicking it records that you reviewed the manifest, with optional notes for whoever approves next.
  2. Once reviewed, a different Strata Admin or Super Admin sees an Approve button. If you were the one who clicked Review, the Approve button stays disabled for you — the platform will not let the same person both review and approve the same batch.
This means at least two people with the right role need to be involved. If your building only has one Strata Admin/Super Admin, you will need a second qualified person (for example, your managing agent's second admin, or a Super Admin) to complete the approval step.

What "Generated" and "Synced" mean

  • Generated means the reconstructed transactions now exist as staged records, matching the approved manifest exactly. Nothing outside this workflow can see them yet.
  • Synced means those staged records have been copied into your building's canonical bank transaction table — the same table real bank statement imports land in. From this point, the reconstructed data behaves exactly like a real payment for matching, arrears, and levy reporting purposes.
Check the actual counts, not just the status. If this building has previously had a batch generated and later archived/superseded (for example, an earlier rebuild), re-generating very similar transactions later can silently produce fewer new records than the manifest promised — the system correctly refuses to create an exact duplicate of something already on file, even if that existing copy is archived, rather than reviving the old copy. If a batch you approved for a specific gap doesn't seem to have closed that gap after Sync, ask your Super Admin to check the actual transaction counts for the affected years rather than assuming Generated/Synced status alone means every expected row landed.

Once a batch reaches Synced (or a later stage), a "Go to Payment Matching Review" button appears on the batch detail screen — it takes you straight to the same Payment Matching page used for real bank feeds, scoped to review how the reconstructed transactions were matched.

What Reverse does — and does not do

Reverse marks a batch as reversed and keeps a full, permanent record of that decision — it is never deleted. It requires a written reason (at least 10 characters) and typing the batch's ID to confirm, and it is restricted to Super Admin only.

Reverse does not undo ledger postings by itself. If a batch's transactions have already been posted to the ledger through the normal payment-matching pipeline, reversing the batch here only changes the batch's own status. Undoing the ledger entries themselves is a separate finance action your Super Admin needs to perform.

Levy Regeneration

The second tab, Levy Regeneration, recalculates GST-aware levy items for a financial-year range against an already-approved reconstruction batch. It follows the same preparation/posting split:

  1. Choose a From and To financial year and an approved governing batch (only approved batches appear in the selector).
  2. Click Generate Plan — a dry run. Nothing is written. You'll see, per year and fund (admin/sinking), the proposed budget total, the regenerated total, and the variance between them, plus a line-by-line breakdown per unit.
  3. If the plan reconciles cleanly, click Apply Regeneration (Super Admin only).
  4. If it does not reconcile, you must write a justification (at least 10 characters) explaining why you are proceeding anyway before Apply becomes available. That justification is permanently recorded alongside the change.

Rows the engine cannot confidently regenerate (for example, a unit that appears to have been overpaid relative to the new calculation) are flagged for manual review rather than silently applied.

Test / demo data

Only Super Admins can mark a new batch as test/demo data. This flag is never an ordinary checkbox available to every preparer — it exists so demo and test batches never get mixed into real production reporting for your building, and never appear in another user's dashboard cards, notifications, or reports. Test/demo batches, imports, and their generated data can be removed in one step through the platform's test-data cleanup, scoped to your building and financial year — real data is never touched by this cleanup regardless of the year you specify.

Building isolation

Every batch, manifest, and levy regeneration is strictly scoped to your building. Managers with access to multiple buildings will only see batches for the building they are currently logged into. No data from another building is ever visible here.
