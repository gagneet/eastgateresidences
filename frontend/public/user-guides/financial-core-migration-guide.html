1. What is changing and why?

The platform is upgrading its financial data engine from a document database (MongoDB) to a specialised relational database (PostgreSQL). This is an infrastructure change only — like replacing the engine in a car while keeping the same controls.

Why now?

  • Regulatory compliance. ACT 2026 legislation requires an auditable, double-entry trust ledger with cryptographic integrity — a requirement that a relational database handles natively and auditors can verify.
  • Audit trail. Every financial entry is now part of a tamper-evident hash chain. If any record were altered, the chain would break — making the ledger suitable for regulator or auditor inspection.
  • Accuracy. All money is stored as exact integer cents, eliminating floating-point rounding errors that can appear in document databases.
  • Performance. Financial reports, levy summaries, and reconciliation queries are significantly faster when run against a relational schema with proper indexes.

Nothing about your levies, payments or balances changes as a result of this work.

The remaining work is unglamorous and internal — most of the new database's tables are still empty, so each feature area moves across one at a time, and each one keeps the old system as an automatic fallback while it does. If a feature area has not moved yet, you cannot tell from the outside, and that is the point.

One thing we have not finished, stated plainly: the new system can tell you that a lot has paid an amount, but for part of the history it cannot yet say which specific levy each payment was applied to. Until that is reconciled, the older system remains the one we quote arrears from. No figure you see today depends on the unfinished part.

5. Rollback safety

The upgrade is fully reversible at any point before cutover. If any discrepancy is detected during the dual-write or reconciliation phase, the system automatically falls back to MongoDB-only mode and sends an alert to the system administrator.

⚠ Rollback guarantee. MongoDB financial collections are never deleted or made read-only until Phase 5 is complete and validated. The cutover only proceeds after 7 consecutive days of zero divergence.

6. Frequently asked questions

Will levy amounts or payment records change?
No. All historical data is migrated using deterministic identifiers — the same record produces the same PostgreSQL ID every time the migration runs. All financial figures are preserved exactly, in integer cents.
Do I need to re-enter any data?
No. The migration is fully automated. No manual data entry is required.
Will there be any downtime?
No planned downtime. Each phase is deployed with the application running. The cutover switch is a configuration change, not a restart.
How do I know if something goes wrong?
Divergence alerts are sent to the system administrator automatically. If you notice any unexpected behaviour in financial figures, contact your strata manager who can check the reconciliation reports in the admin panel.
Does this affect the ACT audit submission?
After cutover, the trust ledger will meet ACT 2026 requirements for a double-entry, hash-chained audit trail. The existing audit export tools continue to work; they will simply read from the new PostgreSQL ledger instead of MongoDB.
What is a "feature flag"?
A feature flag is an on/off switch in the system configuration. The financial_core_enabled flag controls whether new financial writes go to PostgreSQL. It is off by default and turned on per building only after the data migration and validation phases are complete.
