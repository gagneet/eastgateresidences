Owner Name Verification

When an owner registers or is approved, the system automatically checks their full_name against the strata roll using a 60 % token-overlap algorithm.

  • Visual flag: amber ⚠ (AlertTriangle) icon next to owner name in User Management (/dashboard/users)
  • Tooltip: "Owner name mismatch. Strata roll: <Primary Name> / <Secondary Name>"
  • Stored fields: user.is_name_flagged = true and user.flag_reason = "name_mismatch" in the database
  • Notification: approving admin + all Strata Managers receive bell notification + email titled "⚠ Owner Name Mismatch — Unit XX: Name"
  • Joint ownership: flag is cleared if name matches either owner_name or owner_name_b from the strata roll
  • Clearing the flag: correct full_name in user record → re-approve → flag clears automatically
  • Feature toggle: owner_name_verification in Feature Toggles (Governance category); disable to suppress all flags and notifications

Debt Recovery Board

Access the Debt Recovery Board at /dashboard/arrears to manage units with outstanding levy arrears.

Recovery Actions

Action Effect What changes in the UI
Send Notice Generates Section 83 PDF arrears notice; records first_notice_sent_at on first call Notice Sent column shows date; PDF downloads automatically
Refer DCA Sets dca_status = "referred" AND legal_referral_status = "referred" Recovery Status → "DCA REFERRED"; Legal/Plan → "LEGAL ACTION"
Update DCA Status Manually move through: eligible → referred → recovering → resolved → recalled Recovery Status badge updates
Add Contact Log Records communication (email, phone, letter, meeting) Contact Log dialog shows new entry

Column meanings

  • Recovery Status: tracks DCA escalation state (none/eligible/referred/recovering/resolved)
  • Legal/Plan: shows "PAYMENT PLAN" if unit has active plan, "LEGAL ACTION" if legal_referral_status = referred, otherwise "NO PLAN"
  • Notice Sent: date of first Section 83 notice (on unit detail page)

Sync arrears after data import

After uploading a new CSV or Excel financial import, run the bulk sync to keep dashboard figures accurate:

POST /api/owners-units/sync-arrears

This reconciles units.opening_arrears → unit_levy_ledger opening balances. Super Admin only.

Staff User Management

Super Admins have a dedicated interface to manage professional staff accounts and their building-level role assignments.

Creating Staff Accounts

Navigate to Management → Create Staff Account (/dashboard/admin/create-staff-user) to directly create active accounts for:

  • Strata Manager — full building management access (finance, compliance, governance, communications)
  • Real Estate Agent — OwnerHub access to manage properties, tenancies, inspections and rent ledger
  • Admin Staff — front-desk access (notices, parcels, requests, directory, maintenance)

Accounts created this way are immediately active (no approval flow). An optional welcome email with credentials is sent to the new staff member.

Viewing & Managing Staff Users

Navigate to Management → Staff User Management (/dashboard/admin/staff-users) to:

  • See all staff users across all buildings with search and role filters
  • View statistics: total staff, breakdown by type, number with elevated roles
  • Click any staff member to open their detail page

Staff User Detail & Role Elevation

The detail page (/dashboard/admin/staff-users/{id}) shows:

  • Profile: name, email, role badge, organisation, licence, status, last login
  • Building Assignments: which buildings this staff member has access to
  • Elevated Role Assignments: additional roles granted per building (Owner, EC Member, Secretary, Treasurer, Chairman)

Use the Assign Role button to grant a staff member an additional governance or ownership role for a specific building. Fields include:

  • Role (Owner / EC Member / Secretary / Treasurer / Chairman)
  • Building (dropdown of all active buildings)
  • Start and end dates (optional — for time-bounded committee terms)
  • Notes (e.g. "Elected at AGM 2026")
Data isolation guarantee: Role assignments are always scoped to a specific building. A staff member with roles in Building A cannot access data from Building B. The backend validates the building_id before any write.
EC position sync: Assigning a governance role (Chairman, Treasurer, Secretary, EC Member) also updates the legacy ec_position field on the user, ensuring full backward compatibility with existing governance checks.

Revoking Roles

Click the trash icon next to any role assignment to revoke it. The assignment record is preserved for audit purposes but is no longer active. If the user held no other EC roles, their ec_position field is cleared automatically.

Platform Admin vs Building Config

The sidebar configuration section is now split into two groups to reflect the separation of concerns between global platform administration and per-building configuration:

  • Platform Admin (Super Admin only): Feature Toggles, Access Control, Feature Access Controls, Audit Logs, Security & IP Logs, Scraper Settings, Technical Documentation. These control platform-wide behaviour and security.
  • Building Config (Super Admin, Strata Manager, Chairman): Site Settings, Digital Twin Architecture, Email Configuration, Credential Manager, Legal & Privacy. These settings are scoped per building and can be managed by building-level administrators.

Building Switcher

As a Super Admin you have access to all active buildings in the system. Use the Building Switcher in the left sidebar to switch your session context to any building:

  • The dropdown shows all active buildings. Click a building name to switch.
  • Switching issues a new JWT with the selected building_id claim — all building-scoped data (units, finance, announcements) refreshes automatically.
  • A browser page reload is triggered automatically to ensure all contexts reset correctly.
  • The POST /api/auth/switch-building endpoint is used internally. The previous token is replaced in localStorage.

Impersonation — Reading Names

When you open the Impersonate User dialog (account dropdown → Impersonate User), each resident is shown with two name fields:

  • Bold name (primary) — the official strata roll name from the units collection (e.g., "Mr Anthony McDonald & Ms Jane McDonald"). This is the legally authoritative name from the lot register and is always shown exactly as recorded in the strata roll.
  • Amber "Portal:" label — the name the resident typed when they registered on the portal (e.g., "Tony McDonald"). This may legitimately differ from the roll (nickname, maiden name, middle name omitted). It is shown for cross-referencing only.
  • Amber ⚠ icon — appears when the system has flagged a significant mismatch (>40% token difference) between the portal name and the roll name. Review the flag at Users → Approvals.
Search tip: You can search by either name. Typing "Tony" will match the portal name; typing "Anthony" will match the strata roll name. Both fields are searched simultaneously.
Privacy protection after impersonation: Once you begin an impersonation session, all PII fields in the resident's profile are automatically masked — the name field shows "Resident", email is partially masked (e.g., j***@example.com), phone numbers are masked, and address fields show REDACTED. This prevents accidental display or capture of personal data during screen-sharing or screen recordings. The strata roll name remains visible in the user list (it is a legally public record), but is not shown within the impersonated session itself.
Important — two name stores exist for legal reasons: The strata roll (units.owner_name) is the authoritative record under the ACT Strata Titles Act and must match the official lot register. The portal name (users.full_name) is operational only and cannot override the roll. If a resident's legal name changes (marriage, deed poll), update the strata roll via the Admin → Owners & Units page, not just the user profile.
