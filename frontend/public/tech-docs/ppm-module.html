PPM (Preventive Maintenance Plan) Module — Technical Documentation

Role note: chairman is not a top-level system role — it is ec_position=CHAIRMAN on a user whose role is ec_member. Role lists on this page naming "chairman" alongside real role names are shorthand for this; see permissions.md for the full contract.

Overview

The PPM module provides a full lifecycle management system for building maintenance schedules. It ingests data from an Excel spreadsheet (per-building PPM schedule), stores it in MongoDB, exposes 8 REST endpoints, and sends daily email notifications to managers and residents.

Source data: docs/finances/EastGate-UP13195-PPM-January2026.xlsx
Building 13195 statistics: 79 items · 15 sections · 8 compliance items
Multi-tenant: All endpoints resolve building_id from the caller's JWT token via the get_current_building FastAPI dependency.

Backend Architecture

API Endpoints

Method Path Auth Description
GET /api/ppm Any authenticated user List items — filtered by section/status/frequency/is_compliance. Managers see full fields; owners/tenants see limited public fields.
GET /api/ppm/sections Any authenticated user Aggregation: distinct sections with item_count, compliance_count, overdue_count.
GET /api/ppm/dashboard Any authenticated user Health summary: total_items, overdue_count, due_soon_count, compliance_overdue_count, health_score (0–100).
GET /api/ppm/upcoming Any authenticated user Items due within N days (default: 30, max: 365).
GET /api/ppm/overdue Any authenticated user All overdue items with computed days_overdue.
GET /api/ppm/{schedule_id} Any authenticated user Full detail of one PPM item including completion_log and notification_log.
PUT /api/ppm/{schedule_id} Manager roles only Update vendor_name, vendor_contact, notes, or next_due_date. Updating next_due_date also syncs open calendar events.
POST /api/ppm/{schedule_id}/complete Manager roles only Log completion — appends to completion_log, recomputes next_due_date, updates calendar events.

Seed Script

# Run from backend/ directory (activates venv automatically via sys.path)
venv/bin/python3 seeds/ppm_schedule.py

The seed is idempotent: upserts are keyed on (building_id, description, section). Running it twice produces the same 79 documents. Existing schedule_id values and completion_log / notification_log arrays are never overwritten by re-seeding (only mutable metadata fields are updated via $set; IDs are protected by $setOnInsert).

Notification System

Cron Schedule

Runs daily at 07:00 AEST via systemd timer: docs/deployment/eastgate-ppm-notifications.timer 

sudo systemctl enable --now eastgate-ppm-notifications.timer
sudo systemctl status eastgate-ppm-notifications.timer
sudo journalctl -u eastgate-ppm-notifications --since "today"

Notification Rules

Condition Audience Frequency
30 days before due All managers Once (threshold dedup)
14 days before due All managers Once (threshold dedup)
7 days before due All managers Once (threshold dedup)
0 days (due today) All managers Once (threshold dedup)
Overdue (any day) All managers Daily (new threshold each day)
≤7 days before due (compliance items only) All owners/tenants Once per week (7-day dedup)

Deduplication is managed via the notification_log array on each PPM item. Each entry records {date, threshold_days, sent_to, audience}. The cron checks for an existing entry matching today's date and the same threshold_days before sending.

Calendar Integration

PPM items are automatically represented as events in the events collection (event_type: "ppm"). Calendar events are:

  • Created at seed time for each item's next_due_date.
  • Completed (marked with completed_at) when POST /ppm/{id}/complete is called.
  • Inserted (new occurrence) when a completion is logged — for the recomputed next_due_date.
  • Updated (start_date synced) when PUT /ppm/{id} changes next_due_date.

Colour coding:

  • 🔴 Red — compliance items (is_compliance: true)
  • 🟠 Orange — items requiring a licenced contractor
  • 🟣 Purple — items with capital expenditure in the current year
  • 🔵 Blue — all other items

Security

  • XSS prevention: vendor_name and vendor_contact are sanitised with html.escape(); notes is sanitised with nh3.clean() before storage.
  • Role enforcement: PUT and POST /complete raise HTTP 403 for non-manager roles (checked server-side in the endpoint function, not just in the dependency).
  • Building isolation: Every DB query uses the JWT-resolved building_id from Depends(get_current_building). There is no way for a user to access another building's PPM data through these endpoints.
  • Input validation: Status filter input is validated against allowed values (overdue, due_soon, scheduled) — an invalid value raises HTTP 400.
  • Error handling: All DB calls are wrapped in try/except — MongoDB failures return HTTP 503 with a user-safe message rather than exposing stack traces.

Multi-Tenancy

All 8 endpoints use building_id: str = Depends(get_current_building) which resolves the building from the JWT token's building_id claim, then falls back to user.building_id, then to single-membership auto-resolve. The module-level constant _DEFAULT_BUILDING_ID = "13195" is retained for reference only — it is not used in any endpoint query.

The seed script (seeds/ppm_schedule.py) and cron (cron_ppm_notifications.py) use their own BUILDING_ID = "13195" constant since they run as standalone scripts without JWT context. For multi-building deployments, these should be parameterised or run separately per building.

Deployment Checklist

  1. Run the seed: venv/bin/python3 seeds/ppm_schedule.py
  2. Create indexes: venv/bin/python3 ../scripts/db/create_ppm_indexes.py
  3. Re-seed feature toggles: venv/bin/python3 seeds/feature_toggles.py
  4. Install systemd files: copy docs/deployment/eastgate-ppm-notifications.* to /etc/systemd/system/
  5. Enable timer: sudo systemctl enable --now eastgate-ppm-notifications.timer
  6. Restart backend: sudo systemctl restart eastgate-backend
  7. Verify: curl -H "Authorization: Bearer $TOKEN" https://eastgateresidences.com.au/api/ppm/dashboard
