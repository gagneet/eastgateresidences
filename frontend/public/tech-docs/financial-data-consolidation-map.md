# Financial Data Consolidation Map — Page → API → Service → Database

**Generated:** 2026-08-05
**Purpose:** Answer, for every frontend page/component that displays a financial
figure: *which router endpoint feeds it, which service function computes the
number, which database (MongoDB collection vs PostgreSQL table/column) is the
real source, and is that the correct/canonical source or a legacy/duplicate
one.* This is the missing piece between the conceptual
`financial-pages-mindmap.md` (target architecture) and the actual code.

This document is generated by tracing the live repository (routers, services,
`finance_route_cutover_service.py` policy table, `finance_calculation_registry.py`
source-field contract, and each page's API calls) — not from assumptions. Where
a page's data source could not be fully verified in this pass it is marked
`UNVERIFIED` rather than guessed.

## 1. The core problem this document addresses

The repo already contains **two different pieces of canonical infrastructure**
that were built to solve exactly the "which table/field is this number" problem,
but most of the 48 finance-related pages were never wired up to either of them:

1. **`backend/services/finance_calculation_registry.py`** — a hand-maintained,
   cached contract (`GET /finance/calculation-registry`) that lists, for ~10
   canonical financial labels (Annual Levy Commitment, YTD Levied, Ledger
   Payments Recorded, Amount Owing, Credit Balance, Collection Rate, Fund Cash
   Position, Budget vs Actual, Total Ownership Cost), the exact MongoDB
   `collection.field` paths **and** the exact PostgreSQL `schema.table.column`
   paths that back it, plus the formula and which frontend surfaces use it.
   Its own status block says: *"Existing finance UI pages are not rewired to
   fetch this registry at runtime yet."* Only `frontend/src/lib/finance/levyDisplay.ts`
   consumes it (for label text) — no page uses it as the source-of-truth for
   values yet.

2. **`backend/services/finance_route_cutover_service.py`** — a route-level
   policy table (`_ROUTE_POLICIES`) that governs the PostgreSQL-primary /
   MongoDB-fallback behaviour, but it only covers **8 route keys**:
   `finance.summary`, `finance.building_overview`,
   `finance.unit_dashboard_overview`, `finance.levy_kpi`,
   `finance.arrears_detail`, `finance.quarterly_budget`,
   `finance.unit_levy_ledger`, `finance.transactions`. Every other
   finance-adjacent route (trust accounting, levy fairness/scenarios/stability,
   GST/BAS, capital funding, investor intelligence, BI, insurance, council
   rates, water bills, reconciliation, AP, portfolio, owner-hub, savings,
   spending categories…) sits **outside this policy table entirely**.

A third pattern also exists ad hoc: some routers implement their own
try-Postgres-then-fall-back-to-Mongo logic inline, independent of both of the
above (e.g. `backend/routers/intelligence.py`'s `/intelligence/levy-fairness`
logs `"Postgres path unavailable (...), using MongoDB"` directly in the route
handler rather than going through `finance_route_cutover_service`).

**Net effect:** three different, inconsistent patterns for "where does this
number come from" exist side by side, which is almost certainly the root
cause of "most [pages] are currently not linked or have broken data" — a page
built against the canonical registry's semantics can disagree with a page
built against a router's private Mongo aggregation, because they're not
guaranteed to derive the number the same way.

**Recommendation (see §5):** treat `finance_calculation_registry.py`'s
`sources` blocks as the single canonical field mapping, extend
`finance_route_cutover_service._ROUTE_POLICIES` to cover every route named in
§3 below (not just the current 8), and migrate each page in the table one row
at a time onto whichever `canonical_key` it actually displays.
