Trust Accounting

Role note: chairman is not a top-level system role — it is ec_position=CHAIRMAN on a user whose role is ec_member. Role lists on this page naming "chairman" alongside real role names are shorthand for this; see permissions.md for the full contract.

The Trust Accounting module implements a double-entry bookkeeping system for strata trust funds. All monetary amounts are stored as integer cents to eliminate floating-point rounding errors. The system is fully multi-tenant — every collection record is partitioned by building_id and no cross-building queries are possible.

Cutover status. Trust writes still preserve the legacy path, but the read surfaces in routers/trust_accounting.py and routers/trust_reconciliation.py can now switch to PostgreSQL through trust_pg_ledger_enabled and trust_reconciliation_pg_enabled. The PostgreSQL read models live in backend/services/trust_read_service.py; MongoDB remains the compatibility fallback while a scheme is soaking.
⚠️ This document describes the legacy V1 trust ledger (`trust_ledger_accounts`, `trust_ledger_entries`, `trust_ledger_batches` — routers/trust_accounting.py, mounted at `/api/trust/*`). V1 is deprecated and staged for retirement (BUG-TRUST-001). The live system is V2 (`trust_accounts_v2`, `trust_transactions_v2` — routers/trust_phase1.py, mounted at `/api/trust/v2/*`), documented in trust-accounting.md (see its section 2b, "Current Cutover Surface," and section 4 for V2's collections). This HTML page is retained as a historical reference for the V1 ledger model — do not build new integrations against the routes/collections described below.

Overview

Strata corporations in the ACT are required by law to maintain separate trust accounts for the Admin Fund (day-to-day operating expenses) and the Sinking Fund / Capital Works Fund (long-term capital maintenance). This module enforces those legal boundaries at the data layer.

Admin Fund

  • Day-to-day operating expenses (insurance, gardens, cleaning)
  • Quarterly levy collections from owners
  • Supplier invoice disbursements via ABA batches
  • Account code prefix: 1001 (Trust Bank — Admin)

Capital Works Fund (Sinking)

  • Long-term capital maintenance and replacement
  • Sourced from sinking fund levy component
  • Ring-fenced — cannot be used for admin expenses
  • Account code: 1002 (Trust Bank — Capital Works)

Design Principles

  • All values stored as integer cents — no floats in the ledger
  • Every journal entry satisfies SUM(debits) == SUM(credits)
  • Immutability — posted entries are never modified; reversals create new entries
  • Period locks prevent backdating after periods are closed

Multi-Tenant Isolation

  • Every collection document carries building_id as the first indexed field
  • No cross-building aggregations are possible via the API
  • Trust config is embedded per building in the buildings collection
  • Biller codes, bank details and budgets are all per-building

Trust Config

Per-building trust configuration is embedded as a subdocument (trust_config) inside the buildings collection. This keeps all per-building financial parameters co-located with the building record and avoids a separate lookup on every request.

Collections

All collections are partitioned by building_id (string). The index on building_id is always the leading index component.

One document per account per building/fund. Defines the chart of accounts used for double-entry posting.

Posting Rules

Every financial event generates a balanced journal entry. Positive amounts only — the debit/credit column determines sign. Normal balances follow standard accounting convention: Asset and Expense accounts increase on debit; Liability, Income and Equity accounts increase on credit.

Immutability contract. The original trust_ledger_entries document is never deleted or modified. Reversals set is_reversed=true and voided_at on the original, and create a new equal-and-opposite entry with reversal_of_id pointing back. Both entries remain queryable in the audit trail.

API Endpoints

All trust endpoints require trust.view permission for reads and trust.manage for writes. Roles: super_admin and strata_manager have trust.manage; chairman and ec_member have trust.view.

Read-path split. The following read endpoints now have a PostgreSQL-backed path: GET /trust/accounts, GET /trust/journal, GET /trust/journal/{entry_id}, GET /trust/balance, GET /trust/trial-balance, GET /trust/reconciliation/runs, GET /trust/reconciliation/runs/{run_id}, GET /trust/reconciliation/runs/{run_id}/statement-lines, and GET /trust/reconciliation/runs/{run_id}/summary.

Period Lock Flow

Accounting periods follow a lifecycle from open through posting to locked and immutable. A period lock is irreversible — contact the super admin to investigate if a period must be amended after locking.

stateDiagram-v2 [*] --> Open : New period begins Open --> PostingActive : Strata Manager starts posting PostingActive --> PostingActive : Journal entries posted\n(levies, receipts, disbursements) PostingActive --> ReconciliationInProgress : Bank statement imported ReconciliationInProgress --> ReconciliationComplete : All lines matched or noted ReconciliationComplete --> Locked : POST /trust/period-locks\n(requires trust.manage) Locked --> [*] : Period is immutable\nNo backdating allowed
Period lifecycle — once locked, entries in that period are read-only. Corrections post into the next open period.
Backdating prevention. When a new entry is posted, the system checks whether the entry's period field matches a locked period in trust_period_locks. If it does, the request is rejected with HTTP 409. Reversals always use the current open period as the posting date, not the original entry's period.

Phase 2: Ledger Hardening

Phase 2 introduces formal period lifecycle management, Merkle-chained audit seals, and a three-way reconciliation requirement. These features harden the trust ledger against retroactive tampering and provide an auditable chain of custody for period close.

POST /trust/journal — Period-Guarded Journal Entry

The POST /trust/journal endpoint now accepts an optional period_id query parameter. When supplied, the endpoint enforces the period lifecycle rules before accepting the entry.

Cutover note: /api/trust/* is now the legacy V1 compatibility surface. Routed responses include deprecation headers and point callers to /api/trust/v2. New account and transaction reads should use the V2 computed-balance service behind /api/trust/v2/*; production access logs still need review before V1 writes are disabled.

Parameter Location Type Required Description
period_id query string string No ID of a financial_periods document. If supplied, the period must be in OPEN state or the request is rejected with HTTP 409. Omit for legacy / unguarded posting (backwards compatible).

When period_id is provided, the endpoint also stores debit_total_cents, credit_total_cents, and period_id on the created journal entry documents for downstream reporting.

HTTP 404 vs 409. If period_id refers to a period that does not exist for the building, the endpoint returns 404. If the period exists but its state is anything other than OPEN, it returns 409 with a reversal hint in the detail field directing the operator to post a reversal in the current open period instead.

Period States and Lifecycle

Financial periods (financial_periods collection) follow a strict state machine. Only OPEN periods accept new journal postings.

State Can Post? Description
OPEN Yes Active posting period. Journal entries accepted.
RECONCILING No Bank reconciliation in progress. Posting suspended pending three-way reconciliation completion.
CLOSED No Period is closed and reconciled. Merkle seal has been computed.
AUDITED No External auditor has reviewed and acknowledged the period.
LOCKED No Permanently immutable. AGM or regulatory sign-off applied.

Valid state transitions (enforced by validate_transition() in backend/domain/period_lifecycle.py): OPEN → RECONCILING → CLOSED → AUDITED → LOCKED. Any other transition raises a ValueError.

Domain Model Invariants

The following invariants are enforced by Pydantic validators in backend/domain/journals.py and will raise HTTP 422 if violated:

  • A journal must have at least 2 lines (≥1 debit, ≥1 credit).
  • Sum of all debit amounts must equal sum of all credit amounts exactly — integer cents, no float tolerance.
  • All amount_cents values must be positive integers (no negatives, no zero, no floats).

Merkle Seal

At period close, backend/workers/merkle_seal.py computes a tamper-evident SHA-256 Merkle root over all journal entries in the period. The seal is chained to the prior period's seal (the previous root hash is included in the hash input), and the building_id is included in each leaf hash to prevent cross-building substitution attacks.

Seal documents are stored in the trust_ledger_seals collection and also exported to the filesystem path configured by SEAL_EXPORT_PATH. In production this should be an S3-backed mount with 7-year Object Lock (NSW Strata Schemes Management Act 2015 s.180 compliance).

Verification: To verify a seal, recompute the Merkle root from the raw journal entries for the period and compare it to the stored merkle_root in trust_ledger_seals. A mismatch indicates retroactive tampering with the posted entries.

Three-Way Reconciliation

Before a period can transition from RECONCILING to CLOSED, three_way_reconcile() in backend/domain/reconciliation.py must pass with zero tolerance. The three-way check requires:

  • adjusted_bank balance == ledger balance == subledger balance
  • All three values are compared as integers (cents). No rounding or epsilon tolerance is applied.

The result is captured in a frozen ReconciliationResult dataclass. Any discrepancy surfaces as an error — investigate unmatched bank lines or missing subledger entries before retrying.

New Phase 2 Collections

Collection Purpose Key Fields
financial_periods Tracks the lifecycle state of each accounting period per building. building_id, period_id, state (PeriodState enum), opened_at, closed_at
trust_ledger_seals Stores Merkle seal records linking period entries to a tamper-evident root hash, chained to the prior period seal. building_id, period_id, merkle_root, prior_seal_hash, sealed_at, entry_count
reconciliation_items Stores individual items captured during three-way reconciliation for audit and dispute resolution. building_id, period_id, item_type, amount_cents, source (bank|ledger|subledger), status
