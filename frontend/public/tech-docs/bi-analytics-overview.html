BI Analytics Phase 2 — Overview

BI Analytics Phase 2 extends the platform from a single-building analytics view to a hierarchical, role-scoped intelligence workspace covering four access tiers: building, manager portfolio, agency, and platform.

All endpoints are served from backend/routers/bi.py (prefix /api/bi) and backed by backend/services/bi_service.py. The read path prefers the canonical PostgreSQL analytics schema when bi_pg_primary_enabled is true for the building; otherwise it falls back to MongoDB aggregations automatically.

Access Tiers

Tier URL Prefix Scope Role Gate Toggle
Building /bi/building/{building_id}/* One building's 14 KPI panels super_admin, strata_admin, strata_manager, ec_member bi_analytics_building_enabled
Owner /bi/owner/{owner_id}/* Investment analytics for one owner's lot(s) Owner (own lots only) or super_admin bi_analytics_building_enabled
Manager Portfolio /bi/manager/{manager_id}/* Assigned buildings only for a strata_manager super_admin, strata_admin, strata_manager (own portfolio) bi_portfolio_analytics_enabled
Agency /bi/agency/{agency_id}/* All buildings under one strata company super_admin, strata_admin bi_analytics_agency_enabled
Platform /bi/platform/* Cross-agency, all buildings super_admin only bi_analytics_platform_enabled
Management Entity /bi/management-entity/{id}/* Buildings under one management entity super_admin, strata_admin management_hierarchy_enabled

Feature Toggles

Each tier has an independent feature toggle. All are global-default true except bi_pg_primary_enabled, which is per-building and defaults to false.

Toggle Key Default Controls Depends On
bi_analytics_enabled true Legacy alias for building-tier (backward compat) —
bi_analytics_building_enabled true /bi/building/* and /bi/owner/* endpoint reads —
bi_portfolio_analytics_enabled true /bi/manager/* portfolio endpoints —
bi_analytics_agency_enabled true /bi/agency/* cross-building endpoints bi_analytics_platform_enabled
bi_analytics_platform_enabled true /bi/platform/* endpoints; super_admin only —
bi_pg_primary_enabled false Switches read from MongoDB fallback to PG analytics schema bi_analytics_enabled

Per-building activation: enable bi_pg_primary_enabled only after GET /api/bi/building/{id}/cutover-status returns all checks green.

Data Architecture

Read Path

Request → bi.py router
  ↓
bi_service.py — checks bi_pg_primary_enabled for building
  ├── [PG path ON]  → analytics.fact_levy_charge + analytics.fact_levy_payment
  │                   analytics.fact_arrears_snapshot
  │                   analytics.fact_work_order
  │                   analytics.fact_financial_balance
  │                   (Alembic 0052 — canonical_bi_schema)
  └── [PG path OFF] → MongoDB aggregations (fallback, always available)
       ↓
  Response + "source": "postgres_bi" | "mongo"

PostgreSQL Analytics Schema (Alembic 0052)

All BI fact tables live in the analytics schema. They are populated by ETL jobs triggered via POST /api/bi/admin/etl/run or the admin ETL status page.

Table Contents
analytics.fact_levy_charge + analytics.fact_levy_paymentMonthly Due-date Collection Rate per building (charges due as-of-today)
analytics.fact_arrears_snapshotArrears totals and hotspot lots per building (per-unit; no cross-unit netting)
analytics.fact_work_orderMonthly spend by category
analytics.fact_financial_balanceAdmin and sinking fund KPIs / full-year levy coverage (fund health) per building
analytics.fact_compliance_eventCompliance certificate status per building
analytics.fact_capex_plan + analytics.fact_capex_actualCapEx actuals vs. capital plan per building
analytics.fact_utility_billUtility usage (water, electricity) per unit

Metric contract (GAP-FIN-040): collection-rate panels report the Due-date Collection Rate only (charges due as-of-today; canonical get_collection_rate_metrics()). Full-Year Levy Coverage / Fund Health is a separate figure sourced from analytics.fact_financial_balance and must never be labelled "collection rate." Arrears snapshots are per-unit (unit_arrears_and_credit()) with no cross-unit netting.

ETL Status & Cutover Check

  • GET /api/bi/admin/etl-status — per-building ETL freshness and row counts
  • GET /api/bi/building/{id}/cutover-status — readiness checks before enabling PG primary
  • POST /api/bi/admin/etl/run — trigger ETL refresh (super_admin only)

Response Envelope

All BI endpoints return a standard wrapper:

{
  "data": { /* endpoint-specific payload */ },
  "building_id": "13195",
  "source": "postgres_bi" | "mongo"
}
