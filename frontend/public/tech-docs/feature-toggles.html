Feature Toggles

Role note: chairman is not a top-level system role — it is ec_position=CHAIRMAN on a user whose role is ec_member. Role lists on this page naming "chairman" alongside real role names are shorthand for this; see permissions.md for the full contract.

Feature toggles control the visibility of features, navigation items and UI sections across the platform. The system uses a three-tier resolution model: a global default (shared across all buildings) that can be overridden at building level or per individual user. This allows buildings and admins to enable or disable features independently without affecting other tenants.

Default enabled. If no toggle record exists for a given key (neither global nor per-building), the feature defaults to enabled = true. This ensures new deployments do not silently hide features before the seed script is run.
Phase E clean-break: DEFAULT_BUILDING_ID = "" — there is no implicit fallback to a hardcoded building ID. Every buildings (13195, 16244, 18932, and any future building) resolves toggles through the same 3-tier logic with equal treatment.

Overview

Three-Tier System

  • Tier 1 — User-level override — user_feature_access collection. Checked first; applies only to non-elevated users. Grants or denies a feature for one specific user regardless of building or global toggle.
  • Tier 2 — Building-level override — building_id = "13195" (or any other). Wins over the global default for all users of that building when no user-level override exists (or when elevation is active).
  • Tier 3 — Global default — building_id = null. Set once via the seed script. Applies to all buildings unless a building override exists.
  • Temporarily-elevated users bypass Tier 1 — only Tiers 2 and 3 apply to them.
  • Deleting a per-building override reverts the building to the global default.

Where Toggles Gate Behaviour

  • Nav items — DashboardLayout.tsx checks each toggle before rendering sidebar links.
  • Page access — route-level guards redirect to 404 or dashboard if disabled.
  • API endpoints — some endpoints check the toggle server-side and return 403 if disabled.
  • UI sections — individual widgets or tabs within a page can be toggle-gated.

Resolution Algorithm

When the frontend or backend needs to know if a feature is enabled, the following resolution order applies (first match wins). The algorithm runs for a specific (feature_key, building_id, user_id) triple. 

def resolve_toggle(feature_key: str, building_id: str, user: dict) -> bool:
    """
    Three-tier feature toggle resolution. First match wins.
    super_admin always bypasses. Elevation bypasses user-level override.
    """
    # super_admin hard bypass
    if user["role"] == "super_admin":
        return True

    # Tier 1: User-level override (skipped for elevated users)
    if not user.get("elevation_active"):
        user_override = db.user_feature_access.find_one({
            "user_id": user["_id"],
            "feature_key": feature_key
        })
        if user_override is not None:
            return user_override["is_enabled"]

    # Tier 2: Building-level override
    per_building = db.feature_toggles.find_one({
        "feature_key": feature_key,
        "building_id": building_id
    })
    if per_building is not None:
        return per_building["is_enabled"]

    # Tier 3: Global default
    global_default = db.feature_toggles.find_one({
        "feature_key": feature_key,
        "building_id": None
    })
    if global_default is not None:
        return global_default["is_enabled"]

    # Neither exists — default to enabled
    return True

Feature toggle resolution — user-level override (Tier 1, non-elevated only) → building override (Tier 2) → global default (Tier 3) → implicit enabled. Elevated users skip Tier 1.

Collection Schema

Toggles are stored in the feature_toggles MongoDB collection. Each document represents one toggle at one scope level (global or per-building).

Field Type Description
feature_key string Unique slug for this feature, e.g. "rental_certificates". Unique per building_id.
feature_name string Human-readable display name shown in the Feature Toggles admin page.
building_id string | null null = global default. A building_id string = per-building override. Compound unique index: (feature_key, building_id).
is_enabled boolean Whether the feature is enabled at this scope level.
category string Grouping category for the admin UI. See category list below.
description string Plain-English description of what this toggle controls.
icon string Lucide icon name used in the Feature Toggles admin page (e.g. "FileText").
routes string[] Frontend routes gated by this toggle. Informational — used to build the admin UI breadcrumb.
depends_on string[] Feature keys that must also be enabled for this feature to function. Informational — not auto-enforced.
roles string[] Optional role restriction — if set, only these roles can see the feature even when it is enabled.
created_at datetime ISO timestamp of first creation.
updated_at datetime ISO timestamp of last update.
updated_by string | null User ID of the last operator to change this toggle. null for system-seeded records.

User-Level Override Schema (user_feature_access)

Tier 1 overrides are stored in the user_feature_access collection (one document per user/feature pair). These are not applied to elevated users.

Field Type Description
user_id string References users._id
feature_key string References feature_toggles.feature_key
is_enabled boolean true = grant; false = deny
created_at / updated_at datetime ISO 8601 UTC

API Endpoints

All endpoints are in backend/routers/feature_toggles.py under the prefix /feature-toggles. Reads require any authenticated user; writes require super_admin role.

Method Path Role Description
GET /feature-toggles any authenticated List all toggles with resolved values for the current building. Returns a map of feature_key → {enabled, category, description}. Per-building overrides are merged with global defaults.
POST /feature-toggles super_admin Create a new toggle. Body: {feature_key, feature_name, building_id, is_enabled, category, description}. Returns 409 if (feature_key, building_id) already exists.
PUT /feature-toggles/{key} super_admin Update a toggle's is_enabled value (and optionally description, icon, routes). Scope (building_id) is specified in the request body. Creates a per-building override if one does not yet exist.
DELETE /feature-toggles/{key}/override/{building_id} super_admin Remove the per-building override for this key. After deletion the building reverts to the global default. Cannot delete global records (building_id=null) via this endpoint.
GET /feature-toggles/{key} any authenticated Get the resolved value for a single toggle key for the current building.
GET /feature-toggles/admin/all super_admin List all raw toggle documents (global + all per-building overrides) without resolution. Used by the Feature Toggles admin page.

Frontend Usage

Toggles gate navigation items in DashboardLayout.tsx and individual UI sections in page components. The useFeatureToggles() hook fetches the resolved toggle map for the current user's building on mount and caches it for the session. 

// Pattern in DashboardLayout.tsx
import { useFeatureToggles } from '@/hooks/useFeatureToggles';

const { data: toggles, isLoading } = useFeatureToggles();

// Helper — defaults to true if toggle is absent
const isEnabled = (key: string): boolean => toggles?.[key]?.enabled ?? true;

// Nav item gated by a single toggle
{isEnabled('rental_certificates') && (
  <NavItem
    href="/requests/rental-certificates"
    icon={FileCheck}
    label="Rental Certificates"
  />
)}

// Nav item gated by multiple toggles (ALL must be enabled)
{isEnabled('finance') && isEnabled('trust_accounting') && (
  <NavItem
    href="/financials/trust"
    icon={Landmark}
    label="Trust Accounting"
  />
)}

// Toggle-gated section within a page
{isEnabled('levy_fairness_explain') && (
  <Button onClick={openExplainDrawer}>Explain This Result</Button>
)}
Default-open principle. The isEnabled helper returns true when toggles?.[key] is undefined (toggle not yet seeded). This prevents accidental feature hiding during deployments where the seed script has not yet run.

Backend Toggle Check (Server-side)

# Pattern in FastAPI router when a feature is premium/gated
from routers.feature_toggles import resolve_toggle_for_building

@router.get("/trust/ledger-accounts")
async def list_accounts(current_user = Depends(get_current_user)):
    building_id = current_user["building_id"]
    if not await resolve_toggle_for_building("trust_accounting", building_id):
        raise HTTPException(status_code=403, detail="Trust Accounting is not enabled for this building")
    # ... proceed with query

How to Add a New Toggle

  1. Add the definition to backend/seeds/feature_toggles.py — append an entry to the DEFAULT_FEATURES list with at minimum: feature_key, feature_name, description, is_enabled, category, icon, routes, and depends_on. 
    {
    "feature_key": "my_new_feature",
    "feature_name": "My New Feature",
    "description": "A brief description of what this enables",
    "is_enabled": True,          # default state for all buildings
    "category": "governance",    # choose an existing category
    "icon": "Star",              # Lucide icon name
    "routes": ["/dashboard/my-new-feature"],
    "depends_on": []             # feature_keys this depends on
}
  2. Run the seed script to create the global default document: 
    cd backend && venv/bin/python3 seeds/feature_toggles.py
    The script is idempotent — existing toggles are patched (only depends_on is updated, never is_enabled). New toggles are created.
  3. Gate the frontend nav item in DashboardLayout.tsx: 
    {isEnabled('my_new_feature') && (
  <NavItem href="/dashboard/my-new-feature" icon={Star} label="My New Feature" />
)}
  4. Gate the backend endpoint (if the feature warrants server-side protection): 
    if not await resolve_toggle_for_building("my_new_feature", building_id):
    raise HTTPException(status_code=403, detail="Feature not enabled")
  5. Update the snapshot so CI has a current reference: 
    cd backend && venv/bin/python3 scripts/db/snapshot_all.py --collection feature_toggles
Do not add tests that assert toggle state. Tests should test feature behaviour, not whether a toggle is on or off. Toggle-gated tests should parametrize over both enabled and disabled states to ensure the gating itself is correct.

Three-Tier Example

The following example shows how the three-tier system enables a feature globally, disables it for one specific building, and grants it to one individual user even within that building. This is the recommended pattern for rolling out new features to demo buildings before production.

Step 1 — Global Default (seeded)

# Global default document in feature_toggles collection
{
    "feature_key": "rental_certificates",
    "building_id": null,         # <-- null means "global default" (Tier 3)
    "is_enabled": true,          # enabled for all buildings by default
    "category": "governance",
    "description": "Request and issue ACT Section 119A Rental Certificates"
}

Step 2 — Building-Level Override for East Gate (Tier 2)

# East Gate override document — created via PUT /feature-toggles/rental_certificates
{
    "feature_key": "rental_certificates",
    "building_id": "13195",      # <-- East Gate specific (Tier 2)
    "is_enabled": false,         # disabled for all East Gate users by default
    "updated_at": "2026-03-01T00:00:00Z",
    "updated_by": "user_abc123"
}

Step 3 — User-Level Override for One East Gate Admin (Tier 1)

# Grant access to one specific user despite building toggle being off
# Created via PUT /feature-toggles/user-overrides/rental_certificates
{
    "user_id": "user_xyz789",
    "feature_key": "rental_certificates",
    "is_enabled": true,          # <-- Tier 1: grants access for this user only
    "updated_at": "2026-03-15T00:00:00Z"
}

Resolution Result

Building building_id User Result Tier Applied
East Gate Residences "13195" user_xyz789 (admin) Enabled Tier 1 — user-level override grants access
East Gate Residences "13195" any other user Disabled Tier 2 — building override: is_enabled: false
Sierra, Gungahlin "16244" any user Enabled Tier 3 — global default: is_enabled: true
Harbourview Residences "18932" any user Enabled Tier 3 — global default: is_enabled: true
Any new building any any user Enabled Tier 3 — global default

To Revert East Gate to Global Default

# Remove the per-building override — East Gate now uses global default
DELETE /api/feature-toggles/rental_certificates/override/13195

# After this call, East Gate's resolved value = global default = true (enabled)
Seed script is safe to re-run. The seed script (seeds/feature_toggles.py) only creates or patches global default records (building_id=null). It never touches per-building overrides. Re-running the seed script after production configuration is safe.
