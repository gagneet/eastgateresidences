Next-Generation Levy Fairness Engine

Role note: chairman is not a top-level system role — it is ec_position=CHAIRMAN on a user whose role is ec_member. Role lists on this page naming "chairman" alongside real role names are shorthand for this; see permissions.md for the full contract.

The Levy Fairness Engine is a facility-level cost-centre allocation system that replaces legacy unit-entitlement (UOE) pro-rata levy distribution with an absolute dollar-value model. It is designed for mixed-use strata complexes where different unit types derive different benefits from shared facilities (e.g., only apartments benefit from lift maintenance; only garage holders benefit from carpark lighting).

Access restriction: The Levy Fairness page at /intelligence/levy-fairness is accessible to roles: ec_member, chairman, strata_manager, super_admin. Owners can view the read-only LEI/SEI summary via the Owner Dashboard. Recompute and transition-cap controls require EC-level access or above.

Architecture

The engine is composed of four Python service modules that interact with three MongoDB collections and produce a persisted result document used for all frontend reads.

simulate_levy_fairness_v2()          ← orchestrator (levy_fairness_service.py)
  ├─ get_unit_attributes()            ← facility_allocation_engine.py
  ├─ calculate_facility_allocation()  ← facility_allocation_engine.py  (per facility)
  ├─ apply_transition_caps()          ← levy_simulation_engine.py
  └─ run_monte_carlo_levy_simulation() ← monte_carlo_engine.py

Collections read:  units, facility_cost_centres, benefit_groups, unit_levy_ledger,
                   unit_attributes, capital_replacement_schedule, financial_summary,
                   facilities (fallback), building_assets (fallback)
Collection written: levy_fairness_results_v2

The orchestrator saves the full result to levy_fairness_results_v2 via an upsert, keyed on building_id. Subsequent GET requests read from this cache and only recompute when explicitly triggered via the POST endpoint or when no cached result exists.

Service Files

backend/services/levy_fairness_service.py

Main orchestrator. Exports simulate_levy_fairness_v2(building_id, max_change_percent, max_change_amount, run_monte_carlo). Execution flow:

  1. Load units (with building_id filter; fallback to all units if result is empty — supports legacy units that have no building_id field from Excel import).
  2. Load facility_cost_centres; if empty, derive virtual cost centres from the facilities + building_assets digital-twin collections (annualised replacement cost heuristic).
  3. Load unit_levy_ledger to get the current UOE-based levy per unit. Units with no ledger entry fall back to entitlement-proportional share of total_budget.
  4. For each facility, call calculate_facility_allocation() and accumulate per-unit benefit amounts.
  5. Call apply_transition_caps() to compute proposed levies subject to change limits.
  6. Compute LBFI, SEI, LEI metrics per unit and scheme-wide.
  7. Optionally run Monte Carlo simulation.
  8. Upsert result to levy_fairness_results_v2.

backend/services/facility_allocation_engine.py

Exports calculate_facility_allocation(facility, units, benefit_groups, unit_attributes) and get_unit_attributes(building_id).

Allocation driver logic:

  • unit_entitlement: cost × (UOE_i / Σ UOE) over eligible units.
  • equal_split: cost / N where N = number of eligible units.
  • area_weighted: cost × (area_i / Σ area) using unit_attributes.internal_area.
  • car_space_weighted: cost × (spaces_i / Σ spaces) using unit_attributes.car_spaces.
  • metered_usage: Weights from unit_attributes.metered_usage.
  • custom_weights: Weights from unit_attributes.custom_weight (defaults to 1.0).

If a facility has zero cost or no eligible units, it returns an empty dict (no allocation).

backend/services/levy_simulation_engine.py

Exports apply_transition_caps(fair_levies, current_levies, max_change_percent, max_change_amount). Iterative redistribution algorithm (up to 10 iterations) that:

  1. Computes per-unit maximum allowed levy from the cap formula.
  2. Identifies capped units and calculates total shortfall.
  3. Redistributes shortfall proportionally across units that are increasing but not yet at their cap.
  4. Repeats until shortfall < $0.01 or no redistribution capacity remains.

If both caps are provided, the more restrictive (lower ceiling) applies. Units with decreasing levies are never capped.

backend/services/monte_carlo_engine.py

Exports run_monte_carlo_levy_simulation(annual_budget, current_reserve, capital_schedule_10y, num_simulations=1000, years=10). Returns p50/p90/p95 reserve balances, special levy probability, and a sampled distribution list.

Algorithms: LBFI, LEI, SEI

All three metrics are derived from two quantities computed per unit: Benefit_i (fair share of total costs based on facility usage) and Levy_i (proposed levy after transition caps).

LBFI — Levy Benefit Fairness Index

LBFI_i = Levy_i / Benefit_i       (Benefit_i > 0.01)
LBFI_i = 1.0                       (Benefit_i ≤ 0.01, undefined — treated as fair)

LBFI = 1.0 is perfectly fair. LBFI > 1.0 means the unit is over-paying (cross-subsidising others). LBFI < 1.0 means the unit is under-paying (being cross-subsidised).

SEI — Subsidy Exposure Index (per unit)

SEI_i = |Levy_i - Benefit_i| / Levy_i     (Levy_i > 0.01)
SEI_i = 0.0                                (Levy_i ≤ 0.01)

SEI ranges from 0.0 (no subsidy distortion) upward. A value of 0.25 means 25% of the unit's levy either comes from or goes to cross-subsidies.

SEI_scheme — Scheme-Level Subsidy Exposure

SEI_scheme = Σ |Levy_i - Benefit_i| / total_budget

Represents total cross-subsidy as a fraction of the total budget. A perfectly fair allocation has SEI_scheme = 0.

LEI — Levy Equity Index

LEI = max(0, 100 × (1 - SEI_scheme))

A score from 0 to 100. Eastgate's baseline (pure UOE allocation) typically produces LEI ≈ 80–85 due to townhouses subsidising lift and rooftop costs. Introducing benefit groups and facility cost centres pushes LEI toward 95+.

Monte Carlo Simulation

Runs num_simulations (default 1,000) independent 10-year projections. Each simulation independently samples:

Variable Distribution Parameters
Inflation Triangular min=2%, mode=3%, max=5%
Maintenance spike multiplier Lognormal mean=0, sigma=0.25
Capital works overrun Triangular min=1.0, mode=1.15, max=1.40
Insurance premium growth Normal mean=6%, std=3%

For each year: reserve_new = reserve_old + annual_budget - expenses. A simulation "fails" if reserve ever goes negative. The special_levy_probability is the fraction of failed simulations × 100. Output: p50, p90, p95 final reserve balances and a sampled distribution list for charting.

Transition Caps

The apply_transition_caps() function allows strata managers to model a phased rollout of the fair levy model, protecting units from large sudden changes.

  • max_change_percent: No unit's levy can increase by more than X% of its current levy in one year.
  • max_change_amount: No unit's levy can increase by more than $X in one year.
  • When both are set, the more restrictive cap applies (lower of the two ceilings).
  • Shortfall redistribution: Revenue neutrality is preserved — shortfall from capped units is redistributed across units that are increasing and below their own cap, weighted by their proportional fair increase. Up to 10 redistribution iterations are performed.
  • If redistribution capacity is exhausted (all increasing units also hit their caps), the algorithm maintains the capped values even if total revenue falls short.

v2 Enhancements: Confidence, Distribution, Cross-Subsidy & Drivers

The following computed fields were added to simulate_levy_fairness_v2() output in the v2 enhancement pass. They are persisted alongside the existing fields in levy_fairness_results_v2.

Model Confidence (_compute_model_confidence)

Scores data quality on three factors (each 0–100), averaged to a single score:

  1. Levy data coverage — % of units with real ledger records (vs estimated via UOE share).
  2. Asset data quality — min(1, total_asset_budget / actual_total) × 100. Zero when no asset data.
  3. Benefit group granularity — min(100, specific_group_count × 25). Four or more specific groups = 100.

Band thresholds: score ≥ 75 → High; 50–74 → Medium; < 50 → Low. The factors array contains human-readable explanations of any detected deficiencies.

Levy Distribution Histogram (_build_distribution_histogram)

Builds a 10-bucket histogram over the range [min(current ∪ proposed), max(current ∪ proposed)]. Returns boundaries (11 values), current_counts and proposed_counts (10 values each), plus summary stats (mean, median, stdev) and equity_improvement = current_stdev − proposed_stdev. A positive equity_improvement means the proposed model reduces levy spread. Empty unit_impact returns empty bucket structures.

Cross-Subsidy Report (_build_cross_subsidy_report)

Groups units by unit_type and computes per-group totals. Each row in group_rows contains:

  • group — unit type string (e.g., "Apartment", "Townhouse")
  • current_total, fair_total, proposed_total — summed levies
  • current_share_pct, fair_share_pct — % of scheme total
  • net_subsidy — current_total − fair_total (positive = over-paying)
  • net_subsidy_per_unit — per-unit average cross-subsidy
  • role — "Contributor" (net_subsidy > 50), "Recipient" (net_subsidy < −50), "Neutral"

facility_rows lists each facility with its annual cost and % of total, sorted descending by cost. The full report can be downloaded as CSV via GET /intelligence/levy-fairness/cross-subsidy-report.csv.

Per-Unit Drivers

During facility allocation accumulation, the orchestrator builds a unit_drivers map keyed by unit_number. Each entry is a list of {"facility_name": ..., "facility_id": ..., "amount": ...} dicts, one per facility that allocates cost to that unit. This list is attached as drivers on each unit_impact entry and is also returned by the per-unit explain endpoint.

Levy Stability Score Engine

Service: backend/services/levy_stability_service.py. Computes a composite 0–100 stability score from four weighted components. Cached in levy_stability_results collection.

Score Components

Component Weight Data Source Algorithm
Reserve Adequacy 35% sinking_fund_plan, unit_levy_ledger SFAR = (current_reserve + projected_levies_3yr) / planned_capital_3yr. Capped 0–100.
Capital Shock Risk 30% capital_replacement_schedule, capital_shock_risks Inverse of CSI severity. High CSI in next 5yr = lower score.
Levy Volatility 20% unit_levy_ledger (multi-year) CV (coefficient of variation) of annual levy totals over last 5yr. Lower CV = higher score.
Funding Sufficiency 15% budgets, unit_levy_ledger Actual levy income / budget requirement. Fully funded = 100, under-funded proportionally lower.
