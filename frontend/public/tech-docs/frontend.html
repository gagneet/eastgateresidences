Routing Architecture

The app uses the Next.js 16 App Router (migrated from CRA). Dashboard routes live under frontend/src/app/(dashboard)/dashboard/. The root /dashboard page dispatches to a role-specific sub-dashboard component based on the authenticated user's role.

Dashboard Role Dispatch

File: frontend/src/app/(dashboard)/dashboard/page.tsx

// Role dispatch logic in page.tsx
const showManagement = isAdmin() || isManager() || isECMember();

// Roles → showManagement=true: super_admin, chairman, strata_manager, ec_member
// Roles → showManagement=false: owner, tenant, guest

{showManagement
  ? <ManagementDashboard data={data} />   // Building-wide KPIs, finance, arrears
  : isTenant
    ? <TenantDashboard data={data} />      // Tenant-specific view
    : <OwnerDashboard data={data} />       // Personal unit, levy status, market pulse
}
⚠ Critical pattern — named exports: ManagementDashboard, OwnerDashboard, and TenantDashboard all use named exports (export function X). They must be imported as named imports: import { ManagementDashboard } from "./ManagementDashboard". Using a default import resolves to undefined, causing a blank page with no console error. (Fixed in Session 57 — commit d3f3a15.)

Next Estimated Payment — next_payment_adjusted

The primary amount shown in the FinancialHero card is sourced from ownerUnit?.next_payment_adjusted, which is populated by the Session-53 algorithm in backend/server.py (both the /owners-units list endpoint and the /owners-units/{unit} single-unit endpoint):

// Session-53 next_payment_adjusted algorithm (backend)
net_credit       = effective_total_paid - opening_arrears
periods_funded   = floor(max(0, net_credit) / period_levy)
outstanding      = (periods_funded + 1) × period_levy - net_credit

// Before grace (due_date + 14 days):
next_payment = outstanding_current
next_due     = due_dates[periods_funded]

// After grace:
next_payment = period_levy + outstanding_current
next_due     = due_dates[periods_funded + 1]

// Fully paid:
next_payment = 0.0, next_due = None

This means advance payments are reflected automatically — a user who pays 3 quarters in advance sees only the next instalment amount, not the full-year balance (balance_due is NOT used as the primary display value).

Do not use levyStatus?.balance_due for the "amount due" hero metric. balance_due is the full-year remaining balance and overstates the amount for users who have made advance payments. Always use ownerUnit?.next_payment_adjusted (with levyStatus?.amount_due as fallback only).

regular/page.tsx — selectedBuilding Dependency Fix

The fetchData useCallback in regular/page.tsx includes selectedBuilding?.id in its dependency array. This ensures the personal dashboard re-fetches when the active building context changes (e.g., multi-building strata managers switching buildings). Without this dependency, the dashboard would display stale data from the previously selected building.

// regular/page.tsx — correct dependency array
const fetchData = useCallback(async () => {
  // ... fetch /owners-units/{unit}, /levy-status ...
}, [selectedBuilding?.id]);  // ← required for multi-building support

AuthContext — Global Auth State

frontend/src/contexts/AuthContext.tsx — wraps the entire app and provides auth state to all components with strict TypeScript interfaces.

// What AuthContext provides (AuthContextType):
const {
  // State
  user,             // { id, email, full_name, role, unit_number, permissions, ... }
  isAuthenticated,  // boolean
  loading,          // boolean — true during initial token validation
  token,            // JWT string
  selectedBuilding, // active building context (multi-tenant)
  availableBuildings, // list of memberships for building switcher

  // Auth actions
  login(email, password),   // → sets user + token, stores in localStorage
  logout(),                 // → clears state + localStorage
  register(userData),       // → POSTs to /api/auth/register
  switchBuilding(buildingId), // → POST /auth/switch-building, refresh context

  // Permission checks
  hasPermission(permission),           // e.g. hasPermission("can_view_finances")
  isAdmin(),                           // super_admin or chairman
  isManager(),                         // admin | chairman | strata_manager | ec_member
  hasFeatureAccess(featureKey),        // checks feature_toggles for this key

  // Notifications (polled every 30s)
  notifications,             // array of user notifications
  unreadCount,               // integer badge count
  pendingApprovalsCount,     // integer — for tenant approval badge
  markNotificationRead(id),
  markAllRead(),
} = useAuth();
Axios interceptor: The AuthContext configures an Axios instance that automatically attaches Authorization: Bearer <token> to every request, and handles 401 responses by calling logout().
Building switcher: When availableBuildings has multiple entries, the header renders a building selector that calls switchBuilding and refreshes the dashboard with the new tenant context.
UUID vs plan-number — switch-building loop guard (commit b9bc1a0c): The Building interface has two distinct ID fields:
  • id — the UUID (e.g. "abc-123-scheme-uuid-east-gate"). Used as the primary key in Postgres core.schemes and sent in the POST /auth/switch-building request body.
  • building_id — the human-readable plan number (e.g. "13195"). This is what create_token() encodes in the JWT building_id claim.
AuthContext.fetchUser guards against infinite loops by comparing jwtBuildingId (decoded from the JWT building_id claim) against currentBuildingId (selectedBuilding.building_id — the plan number). Previously the code compared against currentId (UUID), which was never equal to the JWT claim, triggering a switch call every render → new token → re-render loop. Always use building_id (plan number) for loop-guard comparisons and id (UUID) for API calls to /auth/switch-building.

Next.js "use client" Directive

All components that use React hooks (useState, useEffect, useCallback, useRouter, usePathname, etc.) or browser APIs must include "use client"; as the very first line. Without it, Next.js App Router treats the file as a Server Component and throws at runtime when hooks are called.

Files requiring this directive:

  • components/layout/DashboardLayout.tsx
  • pages/dashboard/*.tsx — all page components that use hooks
  • Any .tsx file outside app/(dashboard) that uses React state
Migration checklist: When renaming a .jsx file to .tsx, verify the first line is "use client"; if the component uses any React hook or browser API (window, document, sessionStorage).

useEffect Dependency Array Rules

When a useCallback-wrapped function's dependencies include values derived from context (e.g. hasPermission, canManage), adding the function reference to a useEffect dependency array creates an infinite re-render loop if the context value is not memoised. Pattern to avoid this:

  • FinancePage: useEffect(() => { fetchData(); }, [selectedYear, activeTab]) — use stable data values, not function refs
  • MaintenancePage: useEffect(() => { fetchData(); }, []) with // eslint-disable-next-line react-hooks/exhaustive-deps — run once on mount when the fetch depends on role-derived flags
Rule: Never use any[] for API response arrays. Define a named interface (e.g. CommunicationHistoryEntry) in the matching type module and use it. This makes unknown API shapes explicit and catches field renames at compile time.

How to Add a New Page

  1. Create the page component in frontend/src/pages/dashboard/NewPage.jsx
  2. Import it in frontend/src/App.js
  3. Add a route inside the dashboard routes block, wrapped in ProtectedRoute
  4. Add a sidebar link in frontend/src/components/layout/DashboardLayout.jsx — wrap with a feature toggle check if needed
  5. If it needs a feature toggle, add the key to backend/seeds/feature_toggles.py and run the seed 
// App.js — add inside dashboard routes
import NewPage from './pages/dashboard/NewPage';

<Route path="new-feature" element={
  <ProtectedRoute featureKey="new_feature" allowRoles={['owner','ec_member','super_admin']}>
    <NewPage />
  </ProtectedRoute>
} />

// DashboardLayout.jsx — add to relevant sidebar section
{hasFeatureAccess('new_feature') && (
  <SidebarItem href="/dashboard/new-feature" icon={<IconName />} label="New Feature" />
)}
