On 2026-07-15 the contract was tightened again: a chairperson appointment is represented on ec_member, not on strata_admin.

This addendum records the canonical contract for the chairman concept across the platform, and lists the older documentation files that still describe chairman as a top-level role. It does not change behaviour — it clarifies wording so readers of the older docs do not assume UserRole.CHAIRMAN exists.

Canonical contract

  • Top-level roles are defined in backend/models/user.py UserRole enum: SUPER_ADMIN, STRATA_ADMIN, STRATA_MANAGER, EC_MEMBER, OWNER, TENANT, GUEST, plus internal/staff roles. UserRole.CHAIRMAN was removed by Alembic migration 0025 and commit 67fbc4a5 (2026-05-03).
  • Chairman is now an EC position on a user whose top-level role is ec_member. Organisation administration remains strata_admin; do not use that role as a chairperson carrier. The position lives in the ec_position field with the value ECPosition.CHAIRMAN.
  • Backend role guards use _effective_role(user), not raw user["role"]. Current role resolution returns the canonical role string; it does not create a top-level "chairman" role from ec_position. Routers that need chairperson-specific gating must check the EC position or an explicit permission flag rather than accepting chairman as a login role. Example role guard: 
    _role = current_user.get("effective_role") or current_user.get("role", "guest")
if _role not in {UserRole.SUPER_ADMIN, UserRole.EC_MEMBER, UserRole.STRATA_MANAGER}:
    raise HTTPException(status_code=403, ...)
  • Frontend helpers should treat chairperson as EC appointment state or permission state, not as a standalone login role. Front-end code should always go through the helpers rather than comparing role strings directly.
  • Graph relations in services/authorization_engine.py RELATION_PERMISSION_MAP["chairman"] use "chairman" as a relation tag, not as a top-level role. That is expected and supported.

What this addendum does not do

  • It does not rename any code identifier or remove "chairman" from RELATION_PERMISSION_MAP, EC_POSITION_MAP, or AuthContext.tsx.
  • It does not template “East Gate” mentions in the user-guide HTML. The 33 templated guides (per gap F-022, commit 0ec43f3c) already use data-bldg tokens; remaining mentions are East-Gate-specific by design (e.g. east_gate_inclusions.html) and should not be globally rewritten.
  • It does not flip any feature toggle. The financial-cutover toggles seeded by Alembic 0031 remain at is_enabled = false.
