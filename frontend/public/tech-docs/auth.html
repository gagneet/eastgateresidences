Auth & Permissions

JWT-based authentication with role-based access control. 10 user roles, 15 permission flags, and 63+ feature toggles control what each user can see and do.

JWT Authentication

Token Details

  • Algorithm: HS256
  • Expiry (standard): 24 hours (JWT_EXPIRATION_HOURS)
  • Expiry (guest — hard cap): min(24h, stay end_date, 364 days)
  • Secret: JWT_SECRET env var
  • Payload: { user_id, email, role, exp, tenant_id, [building_id], [impersonator_id] }
  • Transport: Authorization: Bearer <token> header
  • Storage: localStorage on the client

Token Validation

Every protected endpoint calls get_current_user(token) via FastAPI Depends():

  1. Decode JWT → get user_id
  2. Look up user in users collection
  3. Check is_active == true
  4. Check is_approved == true
  5. Return user document
No token refresh. Tokens expire after 24 hours. Users must log in again. The frontend detects 401 responses and auto-redirects to /login.
Guest JWT Hard Cap. Guest tokens are enforced with a 364-day maximum regardless of JWT_EXPIRATION_HOURS. At login, the backend looks up the guest's active user_units.end_date and mints a token expiring at min(standard_expiry, end_date, now + 364 days). This prevents a guest from holding a perpetually-valid session token beyond their permitted stay period. The same cap is applied at registration, on /auth/switch-building, and on any building token reissue.

Key Implementation Details

Bell Notification Collection

All registration bell notifications write to db.user_notifications (NOT db.notifications).

  • db.user_notifications — per-user bell icon (what the UI reads)
  • db.notifications — admin broadcast board (separate system)

Code location: routers/auth.py — register() function handles all three registration paths (new owner, tenant/guest, returning archived user).

Admin Email / Bell Search Link

Every admin notification (bell + email) includes a pre-populated search link so admins jump directly to the registrant:

/admin/users?tab=owners&search=Avneet+Rooprai
  • Tab: owners for owner role, residents for all others
  • Name is URL-encoded via urllib.parse.quote_plus()
  • Frontend reads ?search= on mount and pre-fills the search box

Postgres Dual-Write & Invitation-Based Registration (Phase E)

Phase E: Dual-Write. POST /api/auth/register now writes to both MongoDB (legacy) and Postgres (core.users) via identity_repo.create_user_for_registration(). The Postgres write is non-fatal — if it fails, the MongoDB record is still created and the user receives a JWT. JWT tokens now always include a tenant_id UUID claim in addition to the legacy building_id string.

Invitation Flow

Admins can pre-invite users via POST /api/admin/invitations (admin_invitations.py). This creates a core.user_invitations row and emails the recipient a time-limited claim link.

  1. Admin sends invite — stores SHA-256 of raw token in core.user_invitations.claim_token_sha256; raw token is never stored in DB.
  2. Recipient visits /register?invitation_token=<raw>; form pre-fills from prefill_* columns if provided.
  3. On submit, invitation_token is passed to POST /api/auth/register. Backend calls identity_repo.find_invitation_by_token(), which hashes the token and queries using the RLS bypass sentinel (00000000-0000-0000-0000-000000000000) so the lookup succeeds before the invitee has a tenant_id (migration 0015_rls_invitation_bypass).
  4. On match, claim_invitation() stamps claimed_at / claimed_user_id. The new JWT includes tenant_id and building_id from the invitation record.

Request Profile Info Endpoint

POST /api/users/{user_id}/request-profile-info — Super Admin / Building Admin only (can_manage_users)

  • Sends a bell notification to the target user (db.user_notifications.insert_one)
  • Sends an email with a profile-update link
  • Sets user status = info_requested
  • Returns 403 if target is super_admin
  • Returns 404 if user not found

Implementation: server.py — request_profile_info() function.

Returning Archived User

When a previously archived user submits the registration form with the same email, the original archived record is preserved intact (7-year compliance retention). New details are captured in a pending_return_details sub-document for admin review.

  1. The archived audit fields (archived_at, archived_by, archived_reason, status="archived") are not overwritten — they remain on the document for compliance. Only these three fields are written via $set:
    • pending_return_details — object containing full_name, phone, unit_number, by_laws_acknowledged, requested_at, and optionally end_date.
    • password_hash — updated to the new password so the user can log in immediately after admin restore (no forced password reset).
    • return_requested_at — ISO timestamp of the return request.
  2. Bell notifications sent to building-scoped staff reviewers via _get_staff_registration_reviewers(building_id) — this helper uses a two-step query (memberships.distinct → users.find) so only staff who are members of this building are notified (cross-building isolation). Roles included: super_admin (global, always), building_admin, ec_member, strata_manager (building-scoped via membership).
  3. Email sent to each reviewer with an old-vs-new detail table (name, unit, end date changes). Links to /admin/expired-accounts.
  4. API returns 409 Conflict with body {"code": "archived_user_return_request", "message": "..."}.
  5. Frontend (RegisterPage.jsx) detects code === "archived_user_return_request" and shows a blue informational banner instead of a red error toast.

Restore Endpoint — POST /users/{user_id}/restore (super_admin only)

When a super admin clicks Restore from the Expired Accounts page (in order):

  1. Role guard: 403 if caller is not super_admin.
  2. Load user: 404 if not found; 400 if status != "archived".
  3. Pre-conflict check: scans user's existing user_units for primary-occupancy conflicts before any writes — 409 if a conflicting active occupant exists.
  4. Build $set: status=active, is_active=True, is_approved=True, restored_at, restored_by, restore_reason; plus full_name, phone, end_date, by_laws_acknowledged from pending_return_details (if present); plus unit_number if pending_return_details.unit_number is set.
  5. Apply $unset: archived_at, archived_by, archived_reason, pending_return_details.
  6. Unit change path — if pending_return_details.unit_number differs from current unit_number:
    • Second conflict guard on new unit → 409 if occupied.
    • Deactivates old user_units (is_active=false, actual_end_date=now).
    • Inserts a new user_units record for the new unit (scoped to building_id, start_date=today).
    Otherwise: reactivates existing user_units via update_many(is_active=True).
  7. Re-activates building membership via memberships upsert (unconditional — always happens regardless of unit change).

Composite index {building_id: 1, user_id: 1} on user_units is created at app startup for efficient restore lookups.

Login sequence — JWT includes building_id and tenant_id (auto-scoped on login)
Multi-tenant login: /auth/login auto-resolves building_id into the JWT: first from user.building_id, then from single membership, then returns 403 if neither resolves (DEFAULT_BUILDING_ID = "" — Phase E clean-break; no implicit fallback to a hardcoded building). Multi-building users can call /auth/switch-building to mint a new JWT scoped to a different building.
Switch-building loop guard (fixed commit b9bc1a0c): The JWT building_id claim is the human-readable plan number (e.g. "13195"), not the UUID. The Building object returned by GET /buildings/me has two separate fields: id (UUID) and building_id (plan number). AuthContext.fetchUser compares jwtBuildingId against currentBuildingId (plan number), NOT against currentId (UUID). Without this distinction, the comparison was always false, triggering a switch-building call on every token rotation and creating an infinite loop. When calling POST /auth/switch-building the frontend sends { building_id: building.id } — the UUID — which the backend accepts.
Hash compatibility: Login verifies password_hash with a fallback to legacy hashed_password.

Feature Toggle System (63 Toggles)

The platform uses a 3-tier resolution model — first match wins — to determine whether a user can access a given feature:

  1. User-level override — stored in user_feature_access collection ({user_id, feature_key, is_enabled}). Checked first for non-elevated users. Can grant or deny a feature independently of the building or global toggle. Skipped entirely for temporarily-elevated users — only the building/global toggle applies to them.
  2. Building-level override — stored in feature_toggles with a specific building_id. Applies to all users of that building when no user-level override exists (or when elevation is active).
  3. Global default — stored in feature_toggles with building_id = null. Shared across all buildings; falls back to enabled = true if no document exists.
Effective access formula: super_admin → always true · elevation active → building/global toggle · user_override exists → user_override.is_enabled · else → building or global toggle. See Feature Toggles for full resolution algorithm and examples.

Frontend Integration

The frontend checks feature access via hasFeatureAccess(featureKey) from AuthContext.js. The context fetches the user's effective access map on login and caches it. Navigation items in DashboardLayout.jsx conditionally render based on this map. Attempting to navigate to a gated route without access shows a 403-style redirect.

Seeding Toggles

All 63 toggles are defined in backend/seeds/feature_toggles.py. The seed is upsert-safe — running it multiple times only inserts missing entries. To add toggles for a new deployment:

cd backend
python3 -c "import asyncio; from seeds.feature_toggles import seed_feature_toggles; asyncio.run(seed_feature_toggles())"

Or use the one-off scripts in scripts/db/seed_new_feature_toggles_*.py for adding batches of new toggles without re-running the full seed.

Access Control Pages

Two dedicated admin pages provide UI-driven management of the permission and feature access systems.

Access Control Management (/admin/user-permissions)

Manages the 14 boolean permissions.* flags per user. Changes are stored in the custom_permissions field of the user document.

  • Left panel: searchable, role-filterable user list with override count badges.
  • Right panel: 6 grouped permission categories, each permission showing current state, role default label, and Elevated/Restricted badges.
  • Unsaved changes bar: amber sticky bar listing the count of pending changes; Save Changes calls PUT /api/users/{id} with only the permissions delta.
  • Role Defaults reset: one-click button removes all custom_permissions overrides and reverts to role defaults.

Elevation vs Restriction Detection

The frontend hardcodes a ROLE_DEFAULTS map mirroring backend/models/user.py DEFAULT_PERMISSIONS. A permission is flagged as Elevated if it is true when the role default is false, and Restricted if it is false when the role default is true.

Feature Access Controls (/admin/user-feature-permissions)

Manages per-user feature overrides in the user_feature_access collection. Reads effective access via GET /api/feature-toggles/user/{user_id}.

  • Inline 3-state selector: Site Default (DELETE override) / Grant (POST is_enabled:true) / Deny (POST is_enabled:false). Changes apply immediately on click.
  • Effective badge: green check or red X computed from site toggle + override + role bypass.
  • Filters: feature search, category dropdown, "Overrides only" toggle button.
  • Column layout: Feature name (4 cols) | Site Toggle (2) | Override (4) | Effective (2).
  • User summary: shows selected user's role, Grant count, Deny count chips, and Clear All Overrides button.

Super Admin Bypass

The super_admin role bypasses all feature toggle checks. Its effective access is always true regardless of site toggle or per-user overrides. This is enforced on both the backend (GET /api/feature-toggles/user/{id} returns all-true for super_admin) and the frontend (hard bypass in hasFeatureAccess()).

Adding a New Feature Toggle

  1. Add the entry to backend/seeds/feature_toggles.py (all fields required: feature_key, feature_name, description, is_enabled, category, icon, routes).
  2. Run the seed or the one-off upsert script.
  3. Add the Lucide-react icon to ICON_MAP in FeatureTogglesPage.jsx (verify the icon name exists in v0.507 first).
  4. Wrap the relevant frontend route/nav item with hasFeatureAccess('your_feature_key').
Icon compatibility: Verify any new icon name against the installed lucide-react version before committing. Run: node -e "const l=require('./node_modules/lucide-react'); console.log('YourIconName' in l)" from the frontend/ directory.

Rate Limiting

All sensitive auth endpoints are protected by per-IP rate limits using slowapi. A shared limiter and dynamic helper from utils/rate_limit.py are used across the entire application. Base limits are configured in Site Settings and scaled by a global multiplier; the rate_limiting feature toggle can disable enforcement.

Endpoint Limits

Endpoint Limit
POST /auth/register 5 / minute
POST /auth/login 10 / minute
POST /auth/forgot-password 5 / minute
POST /auth/reset-password 5 / minute
POST /auth/change-password 10 / minute
POST /auth/registration-decision 10 / minute

Effective limits = base value × global multiplier from Site Settings.

Implementation

  • Rate limiting key: client IP address (get_remote_address)
  • Exceeded limit returns HTTP 429 Too Many Requests
  • Retry-After header included in 429 response
  • Global control via rate_limiting feature toggle
  • Site Settings define per-endpoint base limits + global multiplier (changes propagate within ~1 minute)
  • _DummyLimiter fallback: if slowapi is not installed, rate limiting is silently disabled (no crash)
  • Test bypass: set DISABLE_RATE_LIMIT=1 in the backend environment to skip all slowapi enforcement without touching the toggle. Used by the E2E security suite to prevent parallel login calls from hitting 429 during beforeAll token acquisition. 
# utils/rate_limit.py
from utils.rate_limit import rate_limit

    ...
# .env (dev/test only — never set in production)

Frontend handling: AuthContext.js axios interceptor converts 429 responses into a error.rateLimitMessage property with a user-friendly string. The register() function surfaces this directly so registration pages can display "Too many attempts. Please wait a moment."

Auth Router Architecture

All auth logic lives in backend/routers/auth.py as the single source of truth. This router is included in server.py via api_router.include_router(auth_router, tags=["Auth"]).

Endpoints in routers/auth.py

  • POST /auth/register — new user registration
  • POST /auth/login — JWT login with audit trail
  • GET /auth/me — current user profile
  • POST /auth/impersonate — super admin impersonation
  • GET /auth/memberships — list all building memberships for the authenticated user. For super_admin, synthesises entries from the buildings collection. Each entry's id field is the building UUID (not prefixed — changed from the old sa_<uuid> format in commit b9bc1a0c).
  • POST /auth/switch-building — mint a new JWT scoped to a different building. Request body: { "building_id": "<building UUID>" }.
  • POST /auth/forgot-password — send reset link
  • POST /auth/reset-password — consume reset token
  • POST /auth/change-password — authenticated password change
  • GET /auth/registration-decision — owner approve/reject form
  • POST /auth/registration-decision — process owner decision
  • GET /mail/access — retrieve mail credentials
  • PUT /mail/update-password — self-service mail password
  • PUT /mail/admin-update-password — admin mail password
  • POST /admin/reset-user-passwords — bulk password reset
  • POST /admin/create-staff-user — super admin direct staff account creation (immediately active)

Staff User Management Endpoints (routers/staff_management.py)

Super Admin only. Provides staff-specific user management with building-scoped role assignment.

  • GET /admin/staff-users — list all strata_manager / real_estate_agent / reception users (all buildings, excludes archived)
  • GET /admin/staff-users/buildings — list active buildings for role-assignment dropdowns
  • GET /admin/staff-users/{user_id} — staff user detail: profile + building memberships + active RBAC role assignments
  • POST /admin/staff-users/{user_id}/building-roles — assign an elevated role (owner, ec_member, secretary, treasurer, building_admin) to a staff user for a specific building. Writes to user_roles (RBAC) and updates legacy ec_position for EC roles. Creates building membership if not already a member.
  • DELETE /admin/staff-users/{user_id}/building-roles/{assignment_id} — soft-revoke role assignment (sets is_active=False, preserves record for audit). Clears ec_position if no active EC roles remain.
Data isolation: building_id is validated against the buildings collection before any write. Users can only hold roles in buildings that actually exist. Cross-building data leaks are prevented at the API layer.
RBAC integration: Role assignments are written to the user_roles collection (same as POST /api/auth/rbac/users/{id}/roles). The staff management endpoints provide a higher-level UX-friendly wrapper that also handles building membership creation and legacy field synchronisation.

Helpers in routers/auth.py

  • _calculate_risk_score() — compare login context vs last login
  • _log_login_attempt() — write audit record to login_audit_logs
  • _send_suspicious_login_email() — alert on risk score ≥ 50
  • _log_password_change() — write to password_change_audit
  • _reg_decision_html_result() — render HTML result page
  • _validate_reg_decision_token() — validate one-click approval token
  • _get_portal_url() — reads FRONTEND_URL env var
server.py still provides: send_email_async, get_email_settings, hash_password, verify_password, create_token, get_current_user — these are shared utilities imported by routers/auth.py.
IP extraction — always from headers (2026-03-09 fix): _log_login_attempt() extracts the real client IP using the full header priority chain regardless of whether MaxMind GeoIP (geoip2) is installed. Without this fix, the GEO_AVAILABLE=False branch fell back to request.client.host = 127.0.0.1 because login requests arrive from Next.js (internal, via BACKEND_INTERNAL_URL), not directly from the browser. The priority order is: CF-Connecting-IP → X-Real-IP → first entry of X-Forwarded-For → request.client.host (direct connections only). GeoIP lookup (country, city, ISP) remains gated on GEO_AVAILABLE.

auth.ts (Next.js): The NextAuth authorize() callback forwards CF-Connecting-IP, X-Real-IP, X-Forwarded-For, and CF-IPCountry headers from the incoming request to the backend login call. Nginx forwards all Cloudflare headers with proxy_set_header CF-Connecting-IP $http_cf_connecting_ip.

RBAC + ABAC System (Session 63)

Added in Session 63, the platform now runs a 3-layer authorization model that is fully backward-compatible with the original boolean-flags system:

  1. Legacy layer — original user.role string + boolean Permission flags. Untouched.
  2. RBAC layer — user_roles, role_permissions MongoDB collections. Building-scoped, time-bounded assignments.
  3. ReBAC / Zanzibar layer — relationship_tuples graph. BFS traversal derives permissions from ownership/committee relationships.

Backend Integration

require_permission_v2("slug")

New decorator in backend/utils/permissions.py. Use alongside (or instead of) the existing @require_permission():

from utils.permissions import require_permission_v2

@router.get("/financials")
@require_permission_v2("financial.view")
async def get_financials(building_id: str, current_user = Depends(get_current_user)):
    ...

The decorator tries the new RBAC layer first; if it finds no active user_roles it falls back to the legacy boolean map, then raises 403 if denied. SUPER_ADMIN always bypasses.

user_can(user_id, slug, building_id, resource)

Central async function in backend/services/permission_service.py. Used by the decorator and callable directly from business logic:

from services.permission_service import user_can

allowed = await user_can(str(user.id), "financial.approve_invoice", building_id=building_id)
if not allowed:
    raise HTTPException(403, "Insufficient permissions")

ABAC Hard-Deny Rules

  • building.config — denied for ALL non-SUPER_ADMIN users regardless of RBAC grants
  • financial.* — owner must own a unit in the target building
  • Cross-building: user with role in Building A cannot act on Building B
