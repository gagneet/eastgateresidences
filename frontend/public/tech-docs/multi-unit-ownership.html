Multi-Unit Ownership

Allows a single owner account to be linked to multiple lots within the same Owner Corporation. The active unit is tracked as a JWT claim and can be switched at runtime without re-authentication.

Data Model

user_units collection (building-scoped)

Field Type Notes
id string (UUID) Primary key
user_id string References users.id
unit_number string Lot number (e.g. UA001)
role_at_unit string Always "owner" currently
is_primary bool True for the first registered unit
is_active bool False = deactivated link (never hard-deleted)
building_id string Partition key — auto-injected by TenantScopedDatabase
start_date string (ISO date) Date the link was created
is_test_data bool True = hard-deletable by test teardown

Changes to users

owned_units: List[str] is a computed field populated by _enrich_owned_units() from user_units — it is not stored on the user document.

Changes to UserCreate (Pydantic)

additional_unit_numbers: List[str] = Field(default_factory=list, max_length=10)

Optional list of extra units to link at registration time. Owner role only. Validated against the units collection, deduplicated, and stripped of the primary unit if it appears.

API Endpoints

Method Path Auth Description
POST /auth/register Public Extended to accept additional_unit_numbers[]. Returns 409 owner_exists_add_unit if the email already belongs to an active owner.
GET /auth/me Bearer Response now includes owned_units: string[] populated from user_units.
POST /auth/switch-unit Bearer (owner) Body: {"unit_number": "UA010"}. Validates user-unit link, re-issues JWT with unit_number claim. Returns new token + updated user.
GET /auth/my-units Bearer (owner) Returns all active user_units for the current user, enriched with unit type from the units collection.
POST /auth/add-unit Bearer (owner) Body: {"unit_number": "TH002"}. Creates a new user_units record (inactive until admin approval). Notifies all admins.

Error codes

Code HTTP Meaning
owner_exists_add_unit 409 Email already registered as an owner — use /auth/add-unit instead
unit_already_linked 400 The user is already linked to this unit
unit_not_found 400 The unit_number does not exist in the units collection

JWT / Unit Context

The active unit is tracked in the JWT payload as a unit_number claim. When the user switches unit:

  1. POST /auth/switch-unit validates the user-unit link in user_units.
  2. A new JWT is issued with unit_number set to the requested lot.
  3. get_current_user() in backend/utils/auth.py reads the unit_number claim and injects it into user["unit_number"] for the request lifetime.

This means all owner-scoped DB queries (levy ledger, maintenance requests) automatically see the correct unit without any mutation to the user document.

Frontend Components

UnitSwitcher (frontend/src/components/layout/UnitSwitcher.tsx)

  • Rendered in DashboardLayout sidebar, below BuildingSwitcher.
  • Hidden when hasFeatureAccess('multi_unit_ownership') is false or user role is not owner/manager.
  • Single unit: static display. Multiple units: Radix DropdownMenu with active badge.
  • Calls switchUnit(unitNumber) from AuthContext which posts to /auth/switch-unit and refreshes the token.

AuthContext additions

Property / Method Type Description
selectedUnit string | null Currently active unit number
availableUnits string[] All units linked to the current user
switchUnit(unit) (string) => Promise<void> Switches active unit, re-issues JWT
addUnit(unit) (string) => Promise<void> Adds a new unit link (pending approval)

RegisterPage additions

After the primary unit is selected, a "I own additional units" checkbox appears. When checked, dynamic unit selectors allow up to 9 additional lots. The additional_unit_numbers[] array is sent in the registration payload.

If the backend returns owner_exists_add_unit (409), the form shows a toast directing the user to log in and use Add Unit from their profile.
