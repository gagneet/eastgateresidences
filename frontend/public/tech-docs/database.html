Live database status — verified 2026-08-19: PostgreSQL is the system of record. Which store serves a read is per-domain AND per-building, decided by core.domain_cutover_status — not by a single global switch. East Gate (13195) is promoted across all eight domains (finance_ledger, identity_core, governance, occupancy, settings, trust_ledger, trust_reconciliation, powerhouse_conversations): read=postgres, write=postgres, with MongoDB as its DR mirror. Every other building is still served by MongoDB. PostgreSQL is at Alembic 0104_manager_fn_scoping with 230 tables across 15 non-system schemas, of which only 53 hold rows — 177 are empty. MongoDB holds 226 collections, 153 non-empty; of those, 13 have a populated PostgreSQL home, 12 map to an empty table, and 128 have no PostgreSQL target at all (including unit_levy_ledger). Promotion is not the constraint — the routers are: 10 of 133 consult the control plane, 103 call db.<collection> directly. Verified live 2026-08-29. See the live PostgreSQL data inventory.

Database Schema

Two stores, by design. PostgreSQL (SQLAlchemy 2.x + asyncpg, Alembic migrations, row-level security) is the system of record and holds the financial core, identity and audit data. MongoDB (Motor async driver, no ORM, no migrations — Pydantic validates at runtime, collections initialised via seed scripts) still serves every building not yet promoted, and is the DR mirror for those that are. The MongoDB collection reference below therefore remains live and accurate; it is not a legacy appendix.

MongoDB architecture: Documents in the same collection may have slightly different fields — this is normal for MongoDB. All new fields have defaults in Pydantic models. Schema changes = edit the model + restart backend.

// FORMULA: net_balance = (admin_opening + admin_levied - admin_paid)
//                      + (sinking_opening + sinking_levied - sinking_paid)
//
// API FIELD MAPPING:
//   balance_owing  (in /owners-units/{unit} response)  = max(0, net_balance)
//   balance_credit (in /owners-units/{unit} response)  = abs(min(0, net_balance))
//   balance_due    (in /levy-status/{unit} response)   = total_annual + prev_year_balance - levy_payments.total
//
// "Total Remaining" on the Owner Dashboard = levy_status.balance_due (authoritative)
//   fallback order: levy_status.balance_due ?? owner_unit.balance_owing ?? owner_unit.net_balance
//
// CRITICAL: levy_payments.building_id must match '13195' (plan number, NOT old slug 'eastgate_residences').
// If levy_payments uses the old slug, the levy-status endpoint finds zero payments and shows
// balance_due = total_annual instead of total_annual - total_paid.
// Session 67 fix: migrated all collections to use building_id='13195'.
//
// FULL-YEAR LEVY COVERAGE (a.k.a. the Fund Health denominator — NOT "Collection Rate"):
//   sum(total_paid) / sum(FULL annual total_levied) × 100
// FY2026 actuals (as of 2026-03-16):
//   total_levied  = $440,374.90  (87 units, UOE 82–161, rates $34.087 admin + $9.9505 sinking /UOE)
//   total_paid    = $27,206.89   (credit units' pre-payments from strata roll CSV)
//   opening_arrears total = $2,794.98  (18 units with prior-year debt)
//   full_year_coverage = 6.2%   (only Q1 was due on this date — this is coverage, not collection rate)
//
// DUE-DATE COLLECTION RATE is a DIFFERENT, canonical metric (GAP-FIN-040):
//   get_collection_rate_metrics() → domain/finance/formulas/collection.py::due_date_collection_rate()
//   = receipts allocated to charges DUE AS-OF-TODAY / charges DUE AS-OF-TODAY
//   (no future/not-yet-due amounts on either side; per-unit, never cross-unit netted).
// "Collected in Advance" (unapplied credit + receipts for not-yet-due periods) is a THIRD,
// separately-surfaced figure. These three metrics must never be conflated or share a label.
//
// BACKEND RULE: Arrears calculations use ONLY unit_levy_ledger.total_paid (DEFT/bank strata-roll
// imports). Do NOT use levy_payments (portal Stripe records) to reduce opening_arrears:
// levy_payments records are current-year levy instalments, not prior-year arrears clearance.
// Using portal payments to offset opening_arrears incorrectly hides genuine prior-year debts.
//
// ARREARS DATA SOURCE (post GAP-FIN-040 — calculation singularity):
//   ALL arrears surfaces call the ONE canonical helper:
//     get_arrears_metrics() → domain/finance/formulas/arrears.py::unit_arrears_and_credit()
//   get_arrears_board (routers/finance.py) and get_top_arrears (server.py) both now delegate
//   to unit_arrears_and_credit() — they no longer compute arrears inline from raw
//   opening_arrears/total_paid/net_balance (the earlier three-way divergence is gone).
//   Arrears is a PER-UNIT obligation, grace-aware: a credit on one unit never nets against
//   another unit's arrears; a unit in credit shows its real credit, never a silent $0.
//   Deriving arrears from a raw net_balance>0 aggregate, or reading
//   balance_owing/total_closing/strata_web_balance for arrears outside the canonical helpers,
//   now FAILS the build (tests/backend/test_finance_calculation_singularity_guardrail.py).
//   (has_portal_account still flags whether an owner is registered in the portal.)
//
// EXPECTED FY2026 ARREARS (18 units, $2,794.97 total):
//   UA042 $963.31 | TH004 $580.01 | TH014 $366.00 | TH011 $294.00 | UA070 $226.15
//   UA001 $154.00 | TH007  $97.33 | TH008  $20.25 | TH015  $20.23 | UA060  $15.41

Levy Schedule Computation — FY-Split Rule

The canonical function for computing levy due dates is compute_period_due_dates() in backend/utils/finance_helpers.py.

Financial Year split rule (ACT strata FY = July to June):

  • Due months ≥ 7 (July–December) belong to calendar year levy_year − 1 (the FY start year).
  • Due months < 7 (January–June) belong to calendar year levy_year (the FY end year). 
# CALENDAR-YEAR MODEL (East Gate Residences):
# levy_year = plain calendar year (Jan–Dec). All due months fall within levy_year.
# There is NO financial-year split.
#
# Example: levy_year=2025, due_months=[3,6,9,12], day_type="first"
#   2025-03-01  grace: 2025-03-15  (Q1)
#   2025-06-01  grace: 2025-06-15  (Q2)
#   2025-09-01  grace: 2025-09-15  (Q3)
#   2025-12-01  grace: 2025-12-15  (Q4) ← East Gate confirmed Q4 2025 = Dec 1, 2025
#
# Example: levy_year=2026, due_months=[3,6,9,12], day_type="first"
#   2026-03-01  grace: 2026-03-15  (Q1)
#   2026-06-01  grace: 2026-06-15  (Q2)
#   2026-09-01  grace: 2026-09-15  (Q3)
#   2026-12-01  grace: 2026-12-15  (Q4)
#
# As of 2026-03-16 for FY2026:
#   periods_past_grace = 1  (only Mar 15 2026 grace has passed)
#
# Default: levy_due_day_type = "first", levy_due_day = 1

Grace Period and Arrears Calculation

# TWO SEPARATE METRICS (must NOT be combined):
#
# ⚠️ SUPERSEDED for the arrears FIGURE (GAP-FIN-040): the true_arrears derivation shown in (1)
#    below — max(0, opening_arrears - ledger.total_paid) — is NO LONGER how arrears is computed.
#    All arrears surfaces (Arrears Recovery Board, Top Arrears, dashboards) now call the canonical
#    get_arrears_metrics() → unit_arrears_and_credit(), which trusts net_balance directly and is
#    grace-aware and per-unit (credits never net across units). Reconstructing arrears from
#    opening_arrears + periods_overdue is guardrail-forbidden. The formulas below are retained to
#    explain the field semantics, not as the current arrears calculation.
#
# COLLECTION/COVERAGE axis — THREE distinct metrics that must never be conflated or share a label:
#   a. Due-date Collection Rate — get_collection_rate_metrics() (charges due as-of-today only)
#   b. Full-Year Levy Coverage / Fund Health — denominator is the FULL annual levy
#   c. Collected in Advance — unapplied credit + receipts for not-yet-due periods
#
# 1. opening_arrears  = prior-year carry-forward debt
#    → Shown on Arrears Recovery Board and Top Arrears widget
#    → true_arrears = max(0, opening_arrears - ledger.total_paid)  [SUPERSEDED — see note above]
#    → days_overdue = (today - last_past_grace_from_prior_year).days
#       Prior year = levy_year - 1. Last past grace = last deadline of prior year's schedule.
#       Example: FY2026 opening_arrears; prior year = 2025; last grace = Dec 15 2025
#                (Mar 16 2026 - Dec 15 2025).days = 91 days overdue
#       Both Arrears Recovery Board and Top Arrears widget use this SAME formula.
#
# 2. net_balance      = opening_arrears + total_levied - total_paid (current-year outstanding)
#    → Shown on Owner Dashboard as "Total Remaining"
#    → Do NOT display on Arrears Recovery Board
#
# periods_past_grace = count of CURRENT YEAR due dates where: today > due_date + 14 days
# (used for outstanding levy calculation; NOT added to true_arrears on the board)
#
# Severity thresholds (based on days_overdue):
#   days_overdue > 90  → critical
#   days_overdue > 60  → serious
#   days_overdue > 14  → overdue
#   else               → current
