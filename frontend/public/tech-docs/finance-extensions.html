1. NSW Payment Plans

GAP-JUR-NSW-002  |  Router: backend/routers/payment_plans.py  |  Tag: Finance

Implements the NSW Form 1 payment plan process under sections 83A–83C of the Strata Schemes Management Act 2015 (SSMA 2015). Owners in levy arrears may formally request a payment plan; the owners corporation must respond within 28 days. The router manages the full lifecycle from request through to completion or cancellation.

All buildings on the platform can use this feature. The NSW compliance framing (28-day rule) is informational — the system does not auto-enforce it, but the submission timestamp on each record enables manual tracking.

Payment Plans — API Endpoints

Prefix: /payment-plans. Collection: payment_plans (building-scoped).

POST /api/payment-plans

Submit a payment plan request. Any authenticated user may submit for their own unit. Managers may submit on behalf of an owner. Returns 201 with the created document.

Field Type Required Notes
unit_number string Yes Lot/unit with arrears.
outstanding_amount_cents int > 0 Yes Total arrears in cents.
requested_instalment_cents int > 0 Yes Proposed instalment per period (cents).
instalment_frequency string Yes weekly, fortnightly, or monthly.
proposed_start_date string Yes ISO-8601 proposed start date.
hardship_reason string No Max 2000 chars. Optional hardship statement.
notes string No Max 1000 chars.

Errors: 400 invalid instalment_frequency.

GET /api/payment-plans

List payment plans. Managers see all plans; owners see only their own (owner_id == current_user.id). Paginated.

Query param Type Notes
status string? Filter by status. Must be a valid PLAN_STATUSES value.
unit_number string? Filter by unit. Manager only (owners are always scoped to their own unit).
page int Default 1.
page_size int Default 20, max 100.

Response: { data: [...], total: int, page: int, page_size: int }

GET /api/payment-plans/{plan_id}

Get a single plan by its UUID id field. Non-managers receive 403 if the plan's owner_id does not match their user ID.

POST /api/payment-plans/{plan_id}/approve

Approve a payment plan request. Manager only. Plan must be in requested status.

Field Type Required Notes
approved_instalment_cents int > 0 Yes Approved instalment per period (may differ from requested).
instalment_frequency string Yes weekly, fortnightly, monthly.
instalment_count int > 0 Yes Total number of instalments in the plan.
start_date string Yes ISO-8601 first instalment date.
notes string No Max 1000 chars.

Errors: 404 not found, 409 plan not in requested state, 400 invalid frequency.

POST /api/payment-plans/{plan_id}/decline

Decline a payment plan request. Manager only. Plan must be in requested status. Body: { "reason": "..." } (min 10, max 2000 chars).

Errors: 404 not found, 409 plan not in requested state.

PUT /api/payment-plans/{plan_id}/status

Update plan status to active, completed, or cancelled. Manager only. Cannot update a plan already in a terminal status (declined, completed, cancelled).

Field Type Notes
status string One of: active, completed, cancelled.
notes string? Optional update notes.

Errors: 404 not found, 409 plan is in terminal status.

Payment Plans — Security Notes

Concern Mitigation
Building isolation All queries include building_id. UUID id field is looked up with {"id": plan_id, "building_id": building_id}.
Owner access scoping _can_view(user, plan) returns True for managers (all plans) or non-managers only when plan.owner_id == user.id.
Role guard _require_manager() checks effective_role or role. Approve/decline/status update are manager-only.
State guard Approve and decline only work on requested plans (409 otherwise). Status update blocked on terminal states.
Retention Records are not hard-deleted. Maintain for 7-year statutory period.

2. Levy Reminder Settings

GAP-FIN-012  |  Router: backend/routers/levy_reminders.py  |  Tag: Levy Reminders

Admin-configurable reminder cadence for overdue levy notices. Settings are stored in levy_reminder_settings (building-scoped) and read by the existing cron/cron_levy_reminders.py cron job on each run. This router provides the admin UI surface for configuring and triggering reminders.

Category financial
Default enabled (global, building_id = null)
Allowed roles super_admin, chairman, strata_manager, ec_member, admin_staff
Nav path /financials/levy-reminders

Levy Reminders — API Endpoints

GET /api/levy-reminders/settings

Return the levy reminder cadence config for the current building. Falls back to defaults if no building-specific settings have been saved yet. Response includes is_default: true when returning defaults.

Default response:

{
  "building_id": "<building_id>",
  "enabled": true,
  "pre_due_days": [14, 7, 3],
  "overdue_days": [1, 7, 14, 30],
  "overdue_threshold_cents": 100,
  "channels": { "email": true, "in_app": true, "sms": false },
  "max_escalation_tier": 4,
  "is_default": true              // true when no building-specific settings saved
}

PUT /api/levy-reminders/settings

Update levy reminder config (upsert). Partial update — only provided fields are changed.

Field Type Notes
enabled bool Master on/off switch for this building.
pre_due_days int[] Days before due date to send courtesy reminders. E.g. [14, 7, 3].
overdue_days int[] Days after due date for each escalation tier. E.g. [1, 7, 14, 30].
overdue_threshold_cents int ≥ 0 Skip overdue notice if balance below this (cents). Default 100 = $1.00.
channels object { email: bool, in_app: bool, sms: bool }. SMS is not yet wired.
max_escalation_tier int 1–10 Stop sending overdue tiers after this count. Default 4.

POST /api/levy-reminders/trigger

Manually trigger a levy reminder run for this building. Dry-run is the default.

Query param Type Notes
dry_run bool Default true. When true: returns preview list, no emails/notifications sent. Set false to dispatch live.

Logic:

  1. Loads settings (or defaults if not configured).
  2. Queries unit_levy_ledger for current year units with outstanding balance ≥ threshold.
  3. Returns a list of { unit_number, outstanding_cents, outstanding_aud } objects.
  4. If dry_run=false and units found: fires asyncio.create_task(run_levy_reminders(building_id, tier=1)).

Response:

{
  "dry_run": true,
  "overdue_unit_count": 3,
  "overdue_units": [
    { "unit_number": "5", "outstanding_cents": 51000, "outstanding_aud": 510.0 },
    ...
  ],
  "message": "Dry run complete — 3 unit(s) would receive reminders."
}

GET /api/levy-reminders/log

List recent reminder dispatch events from audit_logs. Filters: action: {$in: ["levy_reminder_triggered", "levy_reminder_sent"]}. Paginated, sorted by created_at DESC.

Levy Reminders — Cron Integration

The trigger endpoint fires cron/cron_levy_reminders.py:run_levy_reminders() as an asyncio.create_task (fire-and-forget). The cron job is also scheduled externally (systemd timer or PM2 cron) for automated daily runs.

The cron job reads levy_reminder_settings (falling back to _DEFAULT_SETTINGS if absent) to determine cadence. No code change is needed in the cron when settings are updated via the API — the next run picks up the new config automatically.

Collection used: levy_reminder_settings (building-scoped; upserted on PUT).

Audit events written: levy_reminder_settings_updated (on PUT settings), levy_reminder_triggered (on POST trigger), levy_reminder_sent (written by cron job).

3. Arrears Risk Scoring

GAP-FIN-006  |  Router: backend/routers/arrears_risk.py  |  Tag: Finance

Exposes a rule-based predictive risk score for units with outstanding levies. The scoring engine lives in backend/services/arrears_analytics.py. This router is a thin wrapper that calls compute_arrears_risk(db, building_id) and returns the results. Owners cannot access any endpoint — this is a finance/management-only view.

Allowed roles super_admin, chairman, strata_manager, ec_member, admin_staff (finance access only)

Arrears Risk — API Endpoints

All endpoints require finance access. Owners, tenants, and guests receive 403.

GET /api/arrears-risk/summary

Band distribution and totals for the building's arrears risk profile. Calls compute_arrears_risk(db, building_id) and aggregates the results.

Response:

{
  "building_id": "<building_id>",
  "units_with_arrears": 7,
  "total_outstanding_aud": 18420.50,
  "band_distribution": {
    "CRITICAL": 1,
    "HIGH": 2,
    "MODERATE": 3,
    "LOW": 1
  },
  "hardship_flagged": 2,
  "form1_eligible": 3
}

GET /api/arrears-risk

Risk-scored list of all units with outstanding levies, sorted by score descending (highest risk first). Calls compute_arrears_risk(db, building_id).

Response: { data: [...], total: int } — see unit risk shape below.

GET /api/arrears-risk/{unit_number}

Risk score for a single unit. If the unit has no arrears (no match in the scored list), returns a zero-risk response rather than 404:

{
  "unit_number": "42",
  "outstanding_aud": 0.0,
  "score": 0,
  "band": "LOW",
  "signals": [],
  "hardship_flag": false,
  "form1_eligible": false
}

Arrears Risk — Scoring Logic

Scoring is performed by services/arrears_analytics.py:compute_arrears_risk(). The router does not contain scoring logic — it is a pure delegation layer.

Risk bands

Band Score range Meaning
LOW 0–24 Minor arrears, low risk of escalation
MODERATE 25–49 Moderate arrears; monitor
HIGH 50–74 Significant arrears; proactive contact warranted
CRITICAL 75–100 High arrears with escalation signals; legal referral may apply

Risk signals

Signal Description
overdue_90d Balance has been outstanding for 90+ days
overdue_180d Balance has been outstanding for 180+ days
repeat_offender Unit has had arrears in multiple prior periods
legal_action_risk Outstanding amount exceeds typical legal referral threshold
hardship_flag Owner has indicated hardship (e.g. via a payment plan hardship statement)
form1_eligible Unit meets criteria for a NSW Form 1 payment plan request

Unit risk document shape

{
  "unit_number": "5",
  "outstanding_aud": 3060.00,
  "score": 72,
  "band": "HIGH",
  "signals": ["overdue_90d", "repeat_offender"],
  "hardship_flag": false,
  "form1_eligible": true
}

Arrears Risk — Security Notes

Concern Mitigation
Owner access blocked _require_finance() explicitly excludes owner, tenant, and guest roles. Risk scores are sensitive financial data not for resident consumption.
Building isolation compute_arrears_risk(db, building_id) is always called with the authenticated user's building_id. Cross-building access is not possible.
Role guard Uses effective_role or role — never raw user["role"]. Handles elevated users correctly.
No data stored Risk scores are computed on-the-fly from the levy ledger. No risk scores are persisted — always reflects current data.
