External API v1

The External API provides programmatic access to StrataOS building data for third-party integrations — property management software, service provider portals, accounting packages, and IoT devices.

Base URL: https://your-strataos-domain/api/v1
All endpoints require an API key unless marked Public.
Performance & contract tests. The External API v1 ships with dedicated perf/smoke scripts: a k6 benchmark (tests/performance/external_api_benchmark.ts, all /v1 reads + opt-in writes) and a newman-runnable Postman collection (tests/performance/postman/strataos_external_api_v1.postman_collection.json, each request asserting status + a response-time budget). An OpenAPI drift guard (scripts/validation/validate_external_api_openapi.py) keeps this reference in sync with the live router. See the Testing → Performance page.

Overview

The External API follows REST conventions:

  • All requests and responses use JSON (Content-Type: application/json)
  • Authentication via X-API-Key header
  • HTTP status codes follow standard semantics (200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests, 503 Service Unavailable)
  • All timestamps are ISO 8601 UTC (e.g. 2026-03-09T04:00:00Z)
  • Monetary values are in Australian Dollars (AUD)
  • Pagination uses ?skip=0&limit=50 query params (max limit: 200)
Property Value

Protocol HTTPS only (HTTP redirected)
Format JSON

API Version v1 (stable)

Authentication

All API calls except GET /health require an API key passed in the X-API-Key header. GET /scopes requires a valid API key but does not require a specific scope.

API Key Format

egst_<32-character-random-token>
Example: egst_Kx9mPqR2vTnL8wJcYd4hBzAeUfGs6WiN
  • Prefix: egst_ (East Gate Strata)
  • Keys are generated using secrets.token_urlsafe(32)
  • The raw key is shown ONCE at creation — store it securely (password manager, vault). It cannot be retrieved again.
  • Only the SHA-256 hash is stored in MongoDB (api_keys collection)

Request Example

curl -H "X-API-Key: egst_Kx9mPqR2vTnL8wJcYd4hBzAeUfGs6WiN" \
     https://eastgateresidences.com.au/api/v1/building

Authentication Errors

Status Reason
401 Missing or invalid API key
401 Key has been revoked (is_active: false)
401 Key has expired (expires_at in the past)
403 Key does not have the required scope

Scopes

Each API key is granted a list of scopes that determine what it can access. Scopes follow a action:resource pattern.

Scope Access Granted
read:building Building info, unit list, unit details
read:finance Finance summary, budget categories, transactions, levy balances, OC summaries
read:maintenance Maintenance requests, defect list
write:maintenance Report new defects / maintenance requests
read:work-orders Work order list and details
write:work-orders Update work order status
write:service Service provider: submit quotes and invoices
manage:webhooks Register, list, and delete outbound webhooks
admin All scopes (full access)
Principle of least privilege: Grant only the scopes your integration actually needs. Service providers should only receive read:work-orders, write:work-orders, and write:service. Accounting integrations should receive read:finance only.

Creating & Managing API Keys

API keys are managed via the portal UI (Admin Console → API Keys) or directly via the internal API using a JWT bearer token.

Create a Key (Internal API — JWT Auth)

POST /api/v1/api-keys
Authorization: Bearer <jwt-token>
Content-Type: application/json

{
  "name": "Accounting Integration — Xero",
  "description": "Read-only access for Xero reconciliation",
  "scopes": ["read:finance"],
  "expires_at": "2027-01-01T00:00:00Z"
}

Response (201):

{
  "id": "key_abc123",
  "name": "Accounting Integration — Xero",
  "scopes": ["read:finance"],
  "is_active": true,
  "created_at": "2026-03-09T04:00:00Z",
  "expires_at": "2027-01-01T00:00:00Z",
  "last_used_at": null,
  "created_by": "administrator@eastgateresidences.com.au",
  "raw_key": "egst_Kx9mPqR2vTnL8wJcYd4hBzAeUfGs6WiN"
}
⚠ Save the raw_key immediately. It will never be shown again. If lost, revoke and create a new key.

List Keys

GET /api/v1/api-keys?include_inactive=false
Authorization: Bearer <jwt-token>

Revoke a Key

DELETE /api/v1/api-keys/{key_id}
Authorization: Bearer <jwt-token>

Revoked keys return HTTP 401 immediately and cannot be re-activated — create a new key instead.

Postman Setup Guide

This guide walks you through configuring Postman to test all External API endpoints with automatic API key injection.

Cutover-aware environment. The shipped Postman environment now includes buildingId, financial_year, bank_provider, and bank_mode so the same collection can exercise mock banking, PostgreSQL-backed finance reads, and legacy Mongo fallback during phased rollout.

Step 1 — Create a Postman Workspace

  1. Open Postman and click Workspaces → Create Workspace
  2. Name it StrataOS External API
  3. Set visibility to Personal (or Team if sharing)

Step 2 — Create a Collection

  1. Click Collections → + New Collection
  2. Name: StrataOS External API v1
  3. Add a description: External API for East Gate Residences strata management platform

Step 3 — Set Collection Variables

In the collection, click Variables tab and add:

Variable Initial Value Current Value
base_url https://eastgateresidences.com.au/api/v1 (same)
api_key egst_your_key_here paste your real key
jwt_token (empty) paste JWT for key management calls

Step 4 — Set Collection-Level Authentication

  1. Go to the collection Authorization tab
  2. Type: API Key
  3. Key: X-API-Key
  4. Value: {{api_key}}
  5. Add to: Header

All requests in the collection will automatically send the X-API-Key header. You can override on individual requests where JWT auth is needed instead (e.g. key management endpoints).

Step 5 — Create Request Folders

Organise requests into folders matching the API sections:

📁 Eastgate External API v1
  📁 Health & Info
  📁 Building & Units
  📁 Finance
  📁 Maintenance
  📁 Work Orders
  📁 Service Provider
  📁 Owners Corporation
  📁 Webhooks
  📁 API Key Management (JWT auth)

Step 6 — Add Sample Requests

Step 7 — Environment for Local Development

Create a separate Postman Environment for local testing:

Variable Local Value Production Value

Step 8 — Import via OpenAPI (Optional)

The browser-facing OpenAPI export is generated into the public tech-docs pack. Import that copy when you want Postman to match the same auth model as Swagger UI:

  1. Download: /tech-docs/strataos-openapi.json, or open /tech-docs/swagger.html for browser testing.
  2. In Postman: Import → File → strataos-openapi.json
  3. Select Postman Collection v2.1
  4. Prefer the generated collection at /tech-docs/postman/strataos_demo_collection.json when you want auth helpers, demo variables, and the building_id=demo safety default.
The public Swagger UI at /tech-docs/swagger.html loads /tech-docs/strataos-openapi.json. It is the validated browser entry point for trying generated routes. All External API routes appear under the External API v1 tag.

HMAC Signature Verification

If you provided a secret, each webhook delivery includes an X-Webhook-Signature header. Verify it to ensure the payload is genuine:

# Python example
import hmac, hashlib

def verify_webhook(payload_bytes: bytes, signature_header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(
        secret.encode(), payload_bytes, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, signature_header)

# Node.js example
const crypto = require('crypto');
function verifyWebhook(payloadBuffer, signatureHeader, secret) {
  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(payloadBuffer)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expected), Buffer.from(signatureHeader)
  );
}

Error Reference

All errors follow the standard FastAPI error format:

{
  "detail": "Human-readable error message"
}
HTTP Status Meaning Common Cause
400 Bad Request Invalid request body, missing required field, invalid date format
401 Unauthorized Missing X-API-Key header, invalid key, expired key, revoked key
403 Forbidden API key does not have required scope
404 Not Found Unit number, work order ID, or other resource not found
422 Validation Error Request body fails Pydantic validation — check detail array for field errors
429 Too Many Requests Rate limit exceeded — back off and retry after the Retry-After header value
503 Service Unavailable External API feature toggle is disabled by administrator

Rate Limits

The External API inherits the same rate limiting as the main API (configured in backend/utils/rate_limit.py). Limits are applied per IP address and can be scaled by the global rate limit multiplier or disabled via the rate_limiting feature toggle.

  • Default: 100 requests / minute per IP
  • If exceeded: HTTP 429 with Retry-After header
  • Implement exponential backoff in your integration for resilience
# Retry-After example in Python
import time, requests

def call_api_with_retry(url, headers, max_retries=3):
    for attempt in range(max_retries):
        resp = requests.get(url, headers=headers)
        if resp.status_code == 429:
            wait = int(resp.headers.get('Retry-After', 5)) * (2 ** attempt)
            time.sleep(wait)
            continue
        return resp
    raise Exception("Rate limit exceeded after retries")

Feature Toggle

The External API is controlled by the external_api feature toggle. Finance read-source selection is controlled separately by the canonical finance cutover toggles.

  • Toggle key: external_api
  • Default: Enabled
  • When disabled: all /api/v1/* endpoints return HTTP 503
  • Manage via: Admin Console → Feature Toggles

Finance cutover toggles for these endpoints:

  • financial_integration_layer_v2 — umbrella gate
  • financial_pg_reads_enabled — enables PostgreSQL current-balance reads
  • external_api_finance_pg_enabled — activates the external finance read-model path

Generated Postman artifacts use X-API-Key: {{api_key}} for partner-facing /api/v1/* requests. The key-management endpoints under /api/v1/api-keys remain JWT bearer-authenticated admin operations because they create and revoke external keys.

The health check endpoint (GET /api/v1/health) is public, but it is still mounted under the External API router and therefore follows the external_api feature-toggle gate.
