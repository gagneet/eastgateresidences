Onboarding Financial Pipeline — the ONE Path

How every financial fact for an onboarded building reaches the screen through exactly one path: sources → Financial Evidence Gateway ("Demo Bank") → financial_core GL posting → PostgreSQL finance.* ledger → read services → UI. Grounded in the controlling contract docs/architecture/financial-summary-analysis-of-issues.md, the canonical narrative docs/architecture/onboarding/04_onboarding_financial_data_flow.md, and the workflow spec docs/finances/onboarding-reconstruction-workflow-canonical-spec.md. This page documents the future-state target and flags clearly which parts are shipped vs planned.

Nothing constructs financial truth outside this path. No frontend, importer, one-off script, or report computes collection rate / arrears / fund balance / levy allocation independently, and none posts to the GL except through the Gateway → financial_core posting service. A bespoke "read a source document and post straight to the GL" script is the banned pattern (real incident: two disconnected 2021–2025 expense totals — $415,031.21 staged vs $1,502,451.24 GL-posted — diverged 3.6× because one bypassed the Gateway).

Two entry scenarios feed one pipeline: a new building for a Strata Manager (no prior StrataOS data), and an existing building migrating to StrataOS (its data lives in the manager's system / portal). Both converge on the same Gateway. The code is building-agnostic; per-Strata-Manager scrapers are input adapters, not business logic (East Gate / Civium are inputs, never logic).

2. The CREATE → DISPLAY → RECONCILE lifecycle

Every onboarded financial fact moves through three stages. The pipeline supports all three; we do not wait for perfect source data.

StageWhat happensKey rule
CREATE From whatever we can pull (portal current-state, AGM PDF, CSV, the budget page), CREATE derived historical Levy + Expense transactions tagged reconstructed_historical. This alone is enough to start displaying a complete financial view. Derived is an assumption, not evidence — the derivation assumes every unit paid exactly its levy, on time, every period. Each row carries an "assumed, not verified" quality flag.
DISPLAY The PostgreSQL finance.* ledger, built from those derived transactions, serves the UI immediately. Frontends render backend-calculated view models — they never compute accounting results independently. Missing ≠ zero.
RECONCILE When real data later arrives (Bank/Trust feed, a fresh scrape, or a PDF/CSV), reconcile ONLY the transactions we ourselves derived: adjust a date, adjust an amount (interest, fees, rounding), and upgrade provenance — one derived transaction at a time, idempotently, never double-counting. Forward, not repair: we CREATE a coherent derived truth and reconcile that — we do not forensically repair a source system's corrupted records. Un-derivable data is SURFACED as a bounded exception, never silently "fixed."
The portal is a verification signal, never a source. The portal exposes only the current net per unit — not the transactions behind it. A scrape is compared against the GL-calculated balance; it never overwrites a journal or a derived ledger field. An unexplained variance is a visible reconciliation exception, never force-matched. Posting a portal-derived value as a journal is the banned "old wrong path" that once produced a $1.77M duplicate credit.

3. Typed evidence records (the controlled vocabulary)

The Gateway ("Demo Bank" in shorthand) is not just bank lines — it is a set of typed evidence records, each converted to integer cents at ingestion and posted to the GL by financial_core. All inputs use the same envelope but retain their correct accounting meaning. This is the authoritative vocabulary from the controlling contract's evidence-type table:

Evidence typeExampleAccounting treatment
bank_receiptReal owner paymentBank transaction → allocation → receipt journal
bank_paymentSupplier paymentBank transaction → AP/expense allocation
reconstructed_receiptModelled 2021 owner paymentSynthetic bank evidence → historical authorisation → journal
reconstructed_expense_paymentHistorical category paidSynthetic bank evidence → historical expense posting
accrued_expenseYear-end category expense without a payment dateExpense/AP journal; not falsely presented as a confirmed bank movement
budget_approvalAGM-approved category budgetBudget ledger, not GL cash
levy_chargeQuarterly Admin/Sinking levyOwner AR and levy-income journal (a charge is not a fake bank line)
portal_balance_snapshotScraped lot balanceExternal reconciliation evidence; never a journal by itself
opening_balanceOnboarding position (per lot/fund)Authorised opening-balance journal; never back-solved from the portal
adjustmentCorrection after reconciliationExplicit, dated, dual-control adjustment/reversal — never a silent overwrite

The onboarding narrative (§2 of 04_onboarding_financial_data_flow.md) uses the onboarding-specific subset of these — budget_approval, levy_charge, reconstructed_receipt, reconstructed_expense, opening_balance, portal_balance_snapshot, adjustment — with provenance tags (document_derived, reconstructed_historical, strata_web_portal_scrape, portal_reconciliation).

Amounts are paid == charged by construction on the levy side. The payment amount is copied from the charge's total_cents (GST-inclusive), never re-derived — this is what kills the recurring ~10% GST-mismatch bug. Cents are the only ledger truth, converted once at the ingestion boundary (demo_bank/ingestion.py's amount_cents), never re-derived ad hoc at each call site and never inside backend/domain/ (float-banned there, test-enforced).

4. Phase 1 (derived) → Phase 2 (real feed supersession by tag)

The core invariant: a reconstructed (derived) transaction is an assumption, not evidence, until a real Bank/Trust feed confirms it. The derivation cannot distinguish a unit that paid on schedule (derived = real) from one that paid late / short / over / not at all (derived ≠ real). Those mismatched units cannot be resolved by re-deriving — only a real feed (or per-payment history we do not have) turns them from assumed into evidenced.

PhaseGoalProvenancePrerequisite?
Phase 1 — derived Perfect the historical derived pipeline with no Bank/Trust involved: annual Admin/Sinking fund totals (±GST) per year, UOE per unit per year, payment periods per year, and current per-unit status → a fully-tagged reconstructed_historical ledger in PG (mirrored to Mongo). Every row tagged reconstructed_historical; source tag mandatory on every row so Phase 2 is a WHERE source=… supersede, not a forensic exercise. Ships now on honest synthetic data — self-sufficient, never depends on the portal scraper, never reconciles against Mongo.
Phase 2 — real feed supersession Once a connected Trust/Bank account carries historical records (may be none, or partial), reconcile the derived ledger against it. A highest-trust evidence source that supersedes the derived layer for the transactions it covers. bank_reconciled supersedes reconstructed_historical for covered periods; derived rows stay authoritative everywhere the feed is silent. Supersession is reverse-then-replace, never in-place mutation (keeps audit + GL clean). Not a prerequisite for Phase 1 going live. A real Bank/Trust connector is simply another evidence source on the same evidence → reconcile-derived → supersede path — no pipeline rework when connectivity lands.

5. Definition of "done" — two anchors, not one

A building is onboarded when its reconstructed financials pass reconciliation evidence, not when code runs (four states: understood → implemented → verified → promoted). Phase-1 done =

  1. Gross levied per year/fund == the period-aware approved GST-inclusive budget — full annual budget for closed years; budget prorated to periods-charged-to-date for the current year. (unit_levy_ledger.total_levied is YTD-charged-to-date by design, not the full annual levy — mid-year it is ~half the annual budget because ~half the quarters are charged. This "exactly 2.0000× / halved!" observation is NOT a bug; do not re-chase it.)
  2. The derived ledger's net balance reconciles to the portal (best external anchor, or the manually-entered current balance for portal-less buildings).
  3. Every row is tagged reconstructed_historical.
  4. Internal invariants hold: integer cents, balanced journals, idempotent replay, single intake path.
  5. Any residual per-unit variance against the anchor is captured as one bounded, tagged portal_reconciliation adjustment — a residual larger than ~one period's levy is a signal of a systematic bug: halt and flag, do not auto-post.
Mongo is a downstream mirror, never a reconciliation source and never a promotion gate. "Done" is NOT "matches Mongo," NOT "matches per-payment reality," and NOT net-reconciliation alone. Never treat one store's stored/computed value as ground truth — both were derived from CSV/PDF imports and can independently drift.

6. FUTURE STATE — the target architecture

These are the deliberate end-state commitments (not all shipped — see §7):

  • PostgreSQL is the serving source of record. The frontend reads the PostgreSQL finance.* ledger tables to display financials. PG-primary reads flip only when reconciliation is clean — the schema existing is not the same as reads being promoted.
  • MongoDB becomes a DR-only mirror. A scheduled (≈daily) sync propagates PG → Mongo via the outbox relay / change-stream workers, so Mongo staleness can't recur silently. Mongo is never a reconciliation source and never a promotion gate.
  • Portal snapshots are first-class PG reconciliation controls. Per-unit portal-vs-ledger variance is a first-class, bounded, interest-aware control (a net-credit unit accrues no interest adjustment) — surfaced as visible exceptions, routed to the sanctioned resolution (reverse-then-regenerate / matching), never a new portal-derived journal.
  • Fund-level bank reconciliation is a first-class PG control. Admin + Capital Works/Sinking fund balances reconcile against real bank/trust movements once a feed connects, per fund, with GST components where the OC is GST-registered.
  • Provenance tags are a controlled vocabulary. SHIPPED 2026-08-10 Every row carries a mandatory transaction_origin / source tag from a fixed, CHECK-constrained set (document_derived, reconstructed_historical, strata_web_portal_scrape, portal_reconciliation, bank_reconciled, and others), enforced NOT NULL on finance.bank_transactions (migration 0085) — every row across all schemes backfilled and validated live — so Phase 2 supersession is a precedence rule, not a forensic exercise.
  • Every financial API response states its basis (numerator/denominator), source, as_of, and quality/reconciliation status. Collection Rate, Fund Health, and Collected-in-Advance stay three distinct metrics with three labels — never collapsed.

7. Shipped vs Planned — the gap register (G1–G8)

Live-verified for East Gate: finance.arrears_detail, finance.levy_kpi, finance.summary, and finance.unit_dashboard_overview all serve PostgreSQL. finance.building_overview remains on Mongo — correctly, for a real, tracked, open product decision (does PG's collected figure include unapplied/credit-ahead cash the way Mongo's does — GAP-FIN-056 Item 2a), not a readiness gap. The 2026-08-09 promotion session also made an explicit architectural call: Mongo disagreeing with PG is no longer treated as evidence PG is wrong (PG is the system of record); a route promotes once it has a real, substantively-verified comparator on an explicit allowlist, domain mode, and the feature toggle — not once Mongo happens to agree.

8. GST is a rule, not just a manual flag

An Owners Corporation is a non-profit body, so GST registration is compulsory when annual (ex-GST) income is $150,000 or more, and voluntary below it. When registered, GST (10%) is added to levies and to each owner's due amount. Canonical determination point: backend/services/gst_service.py::parse_levy_gst_settings — today it reads a manual gst_registered flag (default True) and the $150k threshold is NOT yet applied (a gap). The rule to codify: gst_registered = (annual_ex_gst_income_cents >= 15_000_000) OR manual_gst_registered_flag, returning a gst_registration_compulsory flag + basis so a threshold-driven change is surfaced, never silent.
