PostgreSQL Financial Core

This document describes the PostgreSQL-backed financial core and the current cutover contract used to move financial reads and writes off MongoDB safely. StrataOS uses a strangler-fig pattern: MongoDB remains available as the legacy fallback while PostgreSQL becomes the canonical finance source per scheme behind explicit cutover controls. The current verified state on 2026-07-24 is: East Gate identity is PostgreSQL read/write, while finance, trust ledger, trust reconciliation, and governance are in PostgreSQL shadow mode. MongoDB still serves live finance/trust/governance reads and writes until shadow-read divergence is clean enough to promote. The write path lives under backend/services/financial_core/; current cutover checks are codified in backend/scripts/postgres_cutover_p0_readiness.py.

2026-07-24 live PostgreSQL inventory. Alembic is at 0071_powerhouse_cmd_foundation. East Gate table counts were inspected with its real PostgreSQL tenant context: finance.journal_entries has 3,198 rows, finance.journal_lines has 6,396 rows, finance.bank_transactions has 2,855 rows, finance.receipts has 2,221 rows, finance.levy_items has 957 rows, and finance.evidence_documents has 10 rows. Full field-level inventory: PostgreSQL live data inventory.

Strangler-fig migration. The PostgreSQL financial core does not replace MongoDB in a big-bang cutover. Both stores run concurrently under a feature flag. The adapter layer transparently routes reads and writes to the correct store based on the building's flag state. No existing MongoDB-backed endpoints change behaviour while the flag is OFF.

1. Architecture Overview

Financial requests still enter through the existing FastAPI routers. Cutover is now controlled through the umbrella feature financial_integration_layer_v2 plus explicit child toggles. Write paths activate through financial_pg_writes_enabled; current-balance read paths activate through financial_pg_reads_enabled and route-specific child toggles such as external_api_finance_pg_enabled, trust_pg_ledger_enabled, and trust_reconciliation_pg_enabled.

flowchart TD FE[Next.js UI] --> API[FastAPI Routes] API --> FLAG{financial_integration_layer_v2 + child toggle?} FLAG -- OFF --> MONGO[(MongoDB legacy)] FLAG -- ON --> ADAPTER[FinancialCoreAdapter / Read Services] ADAPTER --> SVC[FinancialCoreService] ADAPTER --> READS[financial_read_service + trust_read_service] SVC --> PG[(PostgreSQL)] READS --> PG SVC --> OUTBOX[core.outbox] OUTBOX -- async relay --> MONGO
Request routing under the strangler-fig pattern — MongoDB serves as both legacy store and eventual archive target via the outbox relay.

Canonical cutover toggles

The canonical source is PostgreSQL config, not ad-hoc Mongo flags. Toggles are stored in core.feature_toggles / core.feature_toggle_overrides; banking runtime selection lives in core.building_settings.

  • financial_integration_layer_v2 — umbrella gate for all finance cutover work
  • financial_pg_writes_enabled — enables PostgreSQL financial writes
  • financial_pg_reads_enabled — enables PostgreSQL current-balance reads
  • external_api_finance_pg_enabled — repoints external finance API reads to PostgreSQL
  • trust_pg_ledger_enabled — repoints trust ledger read endpoints to PostgreSQL
  • trust_reconciliation_pg_enabled — repoints trust reconciliation read endpoints
  • bank_integration_abstraction_enabled — enables provider-neutral bank runtime selection
  • banking.provider / banking.mode — select mock, csv_replay, basiq, or macquarie_deft with mock, sandbox, or live mode
Default state: OFF. Every child toggle is gated by the umbrella feature, so a scheme cannot accidentally enable one read/write slice without first opting into the broader finance cutover.

2. PostgreSQL Schema

The database is partitioned into twelve application schemas. Each schema groups tables by bounded context, allowing independent permission grants and future extraction into separate services. The 2026-07-24 live inventory inspected 202 application base tables: access 8, ai_assist 7, analytics 26, communications 23, compliance 23, core 43, documents 6, finance 30, governance 8, modules 4, ops 18, and sustainability 6. Forty-four tables currently contain data for the East Gate tenant context or global catalogue context.

Key Tables — finance schema

The live schema is at Alembic 0079_opening_balance_evidence. The finance schema has 30 base tables; the populated East Gate tables are accounting_periods, bank_transactions, evidence_documents, financial_cutover_config, financial_onboarding_audit, funds, gl_accounts, journal_entries, journal_lines, levy_items, levy_runs, receipt_allocations, receipts, and trust_accounts. Empty finance tables are listed in the live inventory.

Table(s) Role
journal_entries + journal_lines Double-entry, append-only general ledger. Every financial event produces a balanced pair of debit/credit lines. Immutability enforced by PL/pgSQL trigger (migration 0007).
levy_rules, levy_runs, levy_items Levy engine — rules define the schedule, runs materialise a period's levy batch, items are per-lot charge records.
receipts + receipt_allocations Payment recording. A receipt captures the inbound payment; allocations distribute it across outstanding levy items.
bank_transactions + reconciliation_runs Bank statement import and matching. Reconciliation runs record the outcome of matching bank transactions to receipts.
trust_accounts, funds, gl_accounts, accounting_periods Chart of accounts and fund structure — admin fund, sinking fund, trust bank accounts, and period boundaries.
Money invariant — BIGINT cents only. All monetary amounts in every finance schema table are stored as BIGINT representing integer cents. NUMERIC and floating-point types are prohibited for money columns. Division that would produce a fractional cent must be resolved with an explicit rounding rule before storage. Violations are caught by a CHECK constraint on insert.

3. FinancialCoreService API

backend/services/financial_core/service.py is the sole authorised writer to PostgreSQL. No FastAPI route handler, plugin, background job, or migration script may issue INSERT / UPDATE / DELETE statements against the finance schema outside of this service.

Public Methods

create_levy(cmd: CreateLevyCommand) -> Levy
record_payment(cmd: RecordPaymentCommand) -> Receipt
allocate_payment(cmd: AllocatePaymentCommand) -> list[PaymentAllocation]
generate_arrears(cmd: GenerateArrearsCommand) -> ArrearsReport
reverse_entry(cmd: ReverseEntryCommand) -> JournalEntry
reconcile_bank_transaction(cmd: ReconcileBankTxCommand) -> ReconcileResult

Command Pattern

Each method accepts a command value object (a frozen Pydantic model). Commands carry all input data required to complete the operation; callers may not pass raw dicts or keyword arguments to these methods. The service:

  1. Validates business invariants (e.g., levy amounts > 0, accounting period open, sufficient balance).
  2. Calls registered plugin hooks in declaration order (see § 5 Plugin System).
  3. Writes to PostgreSQL and inserts the corresponding outbox event in the same database transaction.
  4. Returns a typed result object; never raises silently.
No direct DB access from routes. Route handlers obtain a FinancialCoreAdapter via dependency injection. The adapter calls service methods. Any attempt to bypass the adapter (e.g., importing session directly in a router file) is a policy violation and will fail code review.

Migration Commands

# Run all migrations (requires DATABASE_URL in backend/.env)
cd backend && venv/bin/alembic upgrade head

# Check current revision
cd backend && venv/bin/alembic current

# Generate SQL for a specific migration (dry-run)
cd backend && venv/bin/alembic upgrade 0009 --sql
Run order matters. Migrations must be applied sequentially. Skipping a revision will cause a foreign-key or schema reference error in the next migration. If alembic current shows (head), no action is needed.

5. Plugin System

Plugins live in backend/plugins/. They extend FinancialCoreService behaviour without modifying core service code. Plugins are discovered at startup and registered against the hook registry.

What Plugins Can Do

  • Validate commands before execution.
  • Enrich or transform commands (adding jurisdiction-specific fields).
  • Log custom audit events.
  • Generate compliance artefacts triggered by financial events.
  • Declare the capabilities they provide.

What Plugins Cannot Do

Plugins may not write to the ledger directly. A plugin that attempts a direct INSERT into finance.journal_entries will be blocked by RLS (the plugin executes under the strataos_app role without BYPASSRLS). All ledger changes must go through a service command.

Hook Types

Hook Signature Behaviour
validate_command (cmd) → None Raise ValueError to block the command. Called before any DB writes.
enrich_command (cmd) → cmd Return an enriched (but still immutable) copy of the command. Must not mutate in place.
enrich_template (tmpl) → tmpl Add jurisdiction-specific fields to a document or PDF template before rendering.
log_event (event) → None Non-blocking audit logging. Exceptions are caught and logged; they do not roll back the transaction.
generate_artefact (ctx) → Artefact Produce a compliance document (PDF, JSON disclosure record, etc.) as a side-effect of a command.
expose_capability () → Capability Declare what capabilities the plugin provides so the service registry can query them.

Example: ACT 2026 Reform Plugin

backend/plugins/examples/act_plugin.py implements the validate_command hook to enforce ACT 2026 levy reform rules. It blocks any CreateLevyCommand where total_levy_cents <= 0, raising a descriptive ValueError that the route layer surfaces as an HTTP 422 response. 

class ACTReformPlugin:
    def validate_command(self, cmd):
        if isinstance(cmd, CreateLevyCommand):
            if cmd.total_levy_cents <= 0:
                raise ValueError(
                    "ACT 2026 reform: levy amount must be positive (got "
                    f"{cmd.total_levy_cents} cents)"
                )

6. Transactional Outbox (ADR-003)

The outbox pattern guarantees that every PostgreSQL financial write is eventually reflected in MongoDB's events collection — even if the relay worker crashes mid-flight.

How It Works

  1. FinancialCoreService performs the financial write and inserts a row into core.outbox within the same database transaction. Either both succeed or both roll back — there is no window where a ledger write exists without a corresponding outbox entry.
  2. backend/workers/outbox_relay.py polls core.outbox for rows where published_at IS NULL every 5 seconds.
  3. For each pending row, the relay writes the event payload to the MongoDB events collection.
  4. On successful MongoDB write, the relay marks the outbox row published_at = now().
  5. If the relay crashes before marking a row, the row remains unpublished and will be re-processed on the next poll cycle. Event consumers must therefore be idempotent (the event payload includes the originating journal_entry_id as a stable deduplication key).
At-least-once delivery. The outbox provides at-least-once semantics, not exactly-once. MongoDB consumers that react to outbox-relayed events must use the journal_entry_id or event_id field to skip duplicate processing.

Running the Relay

# Start the outbox relay worker (runs as a background loop)
cd backend && venv/bin/python3 -m workers.outbox_relay

In production, the relay is managed as a systemd service alongside the main backend process. Check docs/deployment/ for the unit file.

7. Row-Level Security (ADR-004)

Every tenant-scoped table in PostgreSQL enforces Row-Level Security (RLS) so that a misconfigured query or a compromised application role cannot read or write another tenant's data at the database level — not just at the application layer.

Configuration

  • Every tenant-scoped table is created with ENABLE ROW LEVEL SECURITY and FORCE ROW LEVEL SECURITY.
  • The SELECT / INSERT / UPDATE / DELETE policy on each table is: 
    USING (tenant_id = core.current_tenant_id())
  • core.current_tenant_id() is a stable SQL function that reads the app.tenant_id GUC (Grand Unified Configuration parameter) set via SET LOCAL app.tenant_id = '...' at the start of each request's database session.

Session Setup

backend/db_postgres/session.py exposes a set_tenant(session, tenant_id) helper that must be called before any query on a tenant-scoped table. The FastAPI dependency get_pg_session() calls this automatically using the resolved building_id from the JWT. 

async with get_pg_session() as session:
    # tenant_id is already set — RLS is active
    result = await session.execute(select(JournalEntry))

Roles

Role BYPASSRLS Purpose
strataos_app No Runtime application role. RLS is always enforced. Used by FastAPI and the outbox relay.
strataos_migrate Yes Migration role. BYPASSRLS granted exclusively for schema changes via Alembic. Must not be used at runtime.
Never use strataos_migrate in application code. The migration role holds BYPASSRLS and is exclusively for Alembic. Using it in a route or service would silently disable all tenant isolation at the database level.

8. Environment Variables

Variable Required Description
DATABASE_URL Optional (warn if absent) PostgreSQL connection string in asyncpg format:
postgresql+asyncpg://user:pass@host/db
If not set, the application starts in MongoDB-only mode and logs a warning. No PostgreSQL operations are attempted.
Graceful degradation. The absence of DATABASE_URL is not a fatal startup error. The application initialises normally with the PostgreSQL session factory in a "disabled" state. Any call that reaches FinancialCoreAdapter while DATABASE_URL is unset will raise a FinancialCoreUnavailableError, which the adapter logs and converts to a 503 response — preserving the MongoDB fallback path.

9. Cutover Runbook Summary

Full step-by-step instructions are in the migration runbooks. The current high-level sequence is:

  1. Start with Acme Demo. Apply Alembic through head, seed the canonical cutover toggles, and set financial_integration_layer_v2 plus financial_pg_writes_enabled for the demo scheme.
  2. Switch the current-balance read slices. Enable financial_pg_reads_enabled together with external_api_finance_pg_enabled, trust_pg_ledger_enabled, and trust_reconciliation_pg_enabled as each surface is validated.
  3. Keep banking provider-neutral. Set banking.provider and banking.mode in core.building_settings. This wave supports mock and csv_replay; live-provider keys remain additive later.
  4. Soak and compare. Run dual-write/shadow-read comparison until divergence is acceptable for the selected surface. Keep Mongo fallback available while a scheme is soaking.
  5. Promote East Gate after demo soak. Repeat the same toggle sequence for East Gate only after the demo scheme is stable and the rollback switches are documented.
Do not rush the reconciliation window. Any divergence detected during step 4 must be investigated and resolved before restarting the 7-day counter. Proceeding with known divergence risks corrupting financial records for real owners.
