File Upload Security

Magika-based content scanning · 14 protected endpoints · Extension-spoofing prevention
Added Apr 2026

What this covers: The Magika ML file-scanning barrier integrated into every file upload endpoint, the EMAIL_PROVIDER environment variable fix, and the Trial Leads (lead generation) system. For database schema see docs/architecture/database_schema_full_2026.json. For role-based access see docs/architecture/role_based_access_architecture.md.

Overview

Every file upload endpoint in the application now passes uploaded bytes through Google Magika — an ML model that identifies the true file type from content, regardless of the file extension or Content-Type header the client sends.

This closes the classic extension-spoofing attack vector: a Windows executable renamed to invoice.pdf is detected as pe and rejected before any persistence or processing occurs.

Reference: github.com/google/magika — Google's content-type detection tool, trained on millions of files. Identifies 200+ file types from byte content in ~5 ms per file. Used by VirusTotal for file triage.

Architecture

All upload validation is centralised in one utility module:

backend/utils/file_scan.py   ← single source of truth for upload security
backend/routers/             ← 14 endpoints that call scan_upload()
backend/requirements.txt     ← magika>=0.6.1 added

The Magika model is loaded once at startup (lazy singleton) and reused across all requests. Inference runs in a dedicated thread pool to avoid blocking the async event loop:

# utils/file_scan.py — core scan function
async def scan_upload(
    content: bytes,
    *,
    context: str,           # "document" | "image" | "csv" | "pdf" | "converter"
    filename: str = "",     # for logging only — not used for type detection
    max_size_bytes: int = None,
) -> ScanResult: ...

How Magika Works

Magika uses a lightweight neural network (DL model, ~few MB) to classify file content. Unlike python-magic (which relies on libmagic heuristics), Magika was trained on millions of real-world files and achieves >99% accuracy on common file types.

  • Input: first N bytes of the file (reads only what it needs — fast for large files)
  • Output: label, mime_type, group, score (confidence 0.0–1.0)
  • Speed: ~5 ms per file after model load; model loaded once at startup
  • Thread-safe: yes — the model is read-only after load

The ScanResult dataclass returned by scan_upload():

@dataclass
class ScanResult:
    label: str       # Magika label, e.g. "pdf", "shell", "pe"
    mime_type: str   # Standard MIME type, e.g. "application/pdf"
    score: float     # Confidence 0.0–1.0
    group: str       # Category: "document", "code", "binary", "image", etc.

Blocked Labels

These labels are always rejected regardless of upload context. The check is performed before the per-context allowlist check.

Category Magika Labels Why Blocked
Native executables pe elf macho dex apk jar class msi cab Executable code — can be launched server-side or distributed to users
Shell scripts shell powershell batch Can be executed by the OS — remote code execution if stored and run
Interpreted scripts python perl php ruby vba Interpreted code — RCE / macro execution risk
Web scripts javascript typescript XSS / client-side code execution if served back
Embedded database sqlite No legitimate upload use case; may contain PII
Important: The label strings above are Magika's actual output labels — not MIME types, not extensions. For example, Magika labels all POSIX shell scripts (bash, sh, zsh) as shell, not bash. Windows batch files are batch, not bat. Always verify actual labels via m.identify_bytes(content).output.label if adding new entries.

Upload Contexts

Each endpoint specifies a context that selects the appropriate per-context allowlist. If the detected label is not in the allowlist, the upload is rejected with HTTP 400.

Context Size Limit Allowed Labels (examples) Used By
document 25 MB pdf, docx, xlsx, pptx, rtf, txt, csv, jpeg, png, gif, webp, svg, unknown General document uploads
image 10 MB jpeg, png, gif, webp, bmp, tiff, heic Maintenance photo uploads (strict — no SVG, PDF, etc.)
csv 10 MB csv, tsv, txt, unknown Financial imports, reconciliation imports (lenient — encoding variants may be detected as txt/unknown)
pdf 50 MB pdf (only) Financial document ingestion (strict)
converter 20 MB pdf, docx, xlsx, pptx, html, csv, markdown, jpeg, png, svg, unknown Document converter (broad — supports many input types)
Why csv allows unknown: CSV files with unusual encodings (Windows-1252, Latin-1) or without headers are sometimes classified as unknown by Magika. Since CSV content is never executed and is parsed into structured DB records, allowing unknown here is safe. The financial import endpoint still enforces its own Content-Type header check and 10 MB size limit.

Request Flow

Every upload endpoint follows this sequence (mermaid sequence diagram):

sequenceDiagram
    participant C as Client
    participant R as FastAPI Router
    participant S as scan_upload()
    participant T as Thread Pool
    participant M as Magika Model
    participant D as MongoDB / FS

    C->>R: POST /api/.../upload (multipart)
    R->>R: Auth check (JWT + permission)
    R->>R: content = await file.read()
    R->>S: await scan_upload(content, context=X)

    Note over S: 1. Empty check
    alt content is empty
        S-->>R: HTTPException 400 "Empty file"
        R-->>C: 400 Bad Request
    end

    Note over S: 2. Size check
    alt len(content) > limit
        S-->>R: HTTPException 413 "File too large"
        R-->>C: 413 Payload Too Large
    end

    Note over S: 3. Magika scan (async, thread pool)
    S->>T: run_in_executor(_scan_sync, content)
    T->>M: m.identify_bytes(content)
    M-->>T: MagikaResult {label, mime, score}
    T-->>S: ScanResult

    Note over S: 4. Blocked-labels gate
    alt label in BLOCKED_LABELS
        S-->>R: HTTPException 400 "Not permitted"
        R-->>C: 400 Bad Request
    end

    Note over S: 5. Context allowlist gate
    alt label not in context_allowlist
        S-->>R: HTTPException 400 "Content mismatch"
        R-->>C: 400 Bad Request
    end

    S-->>R: ScanResult (OK)
    R->>D: Persist / process file
    R-->>C: 200 OK

Fail-Open Design

If the magika package is not installed (e.g., a minimal dev environment), the application continues to work with degraded security:

  • Size limits are still enforced.
  • A WARNING is logged: "File type scan skipped (Magika unavailable)"
  • The upload proceeds; ScanResult(label="unknown", score=0.0) is returned.
  • Blocked-labels and context-allowlist checks are skipped.
Production requirement: magika must be installed in the backend venv. Run pip install magika>=0.6.1 or include it in the install step. The fail-open design exists only to prevent total outage during dependency issues — not as a permanent operating mode. 
# Check Magika is working
cd backend
venv/bin/python -c "from magika import Magika; m = Magika(); print(m.identify_bytes(b'%PDF').output.label)"
# Expected output: txt  (short snippet — real PDFs return "pdf")

EMAIL_PROVIDER Environment Variable Fix

Prior to this session, the EMAIL_PROVIDER variable defined in backend/.env was never imported into config.py. As a result, get_email_settings() always fell back to Resend (if RESEND_API_KEY was set), silently ignoring a configured SMTP override.

Fix

# backend/config.py (added)
EMAIL_PROVIDER = os.getenv('EMAIL_PROVIDER', '')  # 'resend' | 'sendgrid' | 'smtp'

# backend/utils/email.py — fallback chain now honours the env var
default_provider = EMAIL_PROVIDER or ("resend" if RESEND_API_KEY else "smtp")

Priority Order

Email provider resolution (first match wins):

  1. db.email_settings record — persisted UI configuration (highest priority)
  2. EMAIL_PROVIDER env var — explicit env override
  3. RESEND_API_KEY present → Resend
  4. Fallback → SMTP

Test Patterns — Mocking scan_upload

In tests for upload endpoints, patch _scan_sync to avoid running real Magika inference:

from unittest.mock import patch
from utils.file_scan import ScanResult

with patch("utils.file_scan._scan_sync",
           return_value=ScanResult(label="pdf", mime_type="application/pdf",
                                   score=0.99, group="document")):
    # call your upload endpoint
    result = await my_upload_endpoint(file=mock_file, ...)

# To simulate Magika unavailable (fail-open):
with patch("utils.file_scan._scan_sync", return_value=None):
    result = await scan_upload(b"content", context="document")

Adding New Upload Endpoints

Any new UploadFile endpoint must call scan_upload() after reading the file bytes:

from utils.file_scan import scan_upload

@router.post("/my-feature/upload")
async def upload_file(
    file: UploadFile = File(...),
    current_user: dict = Depends(get_current_user),
):
    content = await file.read()

    # REQUIRED — security barrier
    await scan_upload(content, context="document", filename=file.filename or "")

    # ... persist content ...

Choose the context that most closely matches the intended file type:

  • "document" — general attachments (PDFs, Office docs, images)
  • "image" — photos only (JPEG, PNG, GIF, WebP)
  • "csv" — CSV/TSV data imports
  • "pdf" — strict PDF-only (financial reports)
  • "converter" — broad format support for document conversion

To add a new context, edit utils/file_scan.py:

  1. Add a frozenset of allowed labels to CONTEXT_ALLOWLISTS
  2. Add a size limit to _DEFAULT_SIZE_LIMITS
  3. Add tests in test_file_scan.py covering: allowed type passes, blocked type rejected, dangerous label rejected
Never allow a label that is in BLOCKED_LABELS inside any context allowlist. The blocked-label gate runs first, but defence-in-depth requires the allowlist to also not contain dangerous types. The test suite asserts this invariant automatically.
