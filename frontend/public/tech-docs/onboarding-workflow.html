Onboarding Workflow

SM organisations + buildings + self-managed schemes (May 2026)

Overview

Three paths land in the same Postgres data model (core.tenants + core.schemes):

  1. Trial-request approval. Public form → SA reviews → atomic tenant + invitation creation. Future work; see Status.
  2. SA direct create (SM-managed). SA fills POST /api/admin/sm-organisations form. Creates one tenant; primary admin invitation sent.
  3. SA direct create (self-managed). SA fills POST /api/admin/sm-organisations/self-managed. Atomic: tenant + scheme + EC admin invitation.

Financial-only onboarding (historical reconstruction) — added 2026-07-26

A separate, later-stage flow for a building that has already completed the three paths above (scheme + tenant already exist) and now needs prior years' financial history added or filled in — for example a building migrating from another platform, or one with a partial history that only needs the gaps closed. It never creates a scheme or tenant. Router: backend/routers/financial_onboarding.py (prefix /api/financials). Full endpoint contract: docs/architecture/onboarding/02_endpoint_contracts.md §3.

Where to find it: Dashboard → Financial → Financial Onboarding (/admin/financial-onboarding, a building-selector wrapper) or Historical Reconstruction directly (/financials/historical-reconstruction). Both are gated by the historical_financial_reconstruction feature toggle, which — together with historical_reconstruction_posting — was flipped from disabled to enabled by default globally in this same change (both classified ADMIN_ONLY in backend/core/toggle_classification.py, safe to bulk-enable). Before this, the nav items were wired into the sidebar but invisible.

Generating financial history: two source modes

Creating a reconstruction batch now offers a Generation source choice:

  • Generate from proposed budget (Admin/Sinking/GST) — the new default (reconstruction_method = "generate_from_budget_v1"). Building- agnostic: works for any building, not just East Gate. Computes one combined Admin+Sinking(+GST) Demo Bank transaction per lot per quarter directly from the building's proposed levy budget and unit entitlements (services/reconstruction_generators/budget_levy_generator.py). Before generating anything, the page calls GET .../historical-data-status and shows either "No financial history found — ready to generate" or "Partial financial history found (N of M lot/year/fund periods already paid) — generation will skip those". The generator itself dedups against finance.levy_items.paid_cents: any lot/year/fund combination that already shows a real recorded payment is skipped entirely rather than duplicated — the same mechanism covers both "some history already exists" and "no history exists" without separate code paths.
  • Link existing Demo Bank rows — the original, East-Gate-only path (any other reconstruction_method value, e.g. gst_uoe_largest_remainder_v5). Only links pre-existing demo_bank_transactions rows that already happen to exist; does not generate new ones. Hidden by default in the UI, kept for backward compatibility.

From batch to visible data

A batch moves through draft → extracted → needs_review → approved → generation_ready → generated → syncing → synced/matching/partially_posted/posted (or failed/reversed/superseded). Approval is a genuine two-person control: POST .../review and POST .../approve are separate endpoints, and the server rejects an approval attempt by the same user who recorded the review. Once a batch reaches synced/matching/partially_posted/posted, the page shows a "Go to Payment Matching Review" button linking to /financials/matching — the existing matching-review page, which needed no changes for this feature.

Invariants enforced at DB level

  • Active-only ABN uniqueness — partial unique index tenants_abn_unique_active WHERE status = 'active'.
  • Self-managed 1:1 — trigger schemes_self_managed_one_per_tenant blocks a second non-archived scheme insert under any tenant where is_self_managed=TRUE.
  • One open trial per email — partial unique index trial_requests_email_open_unique WHERE status = 'submitted'.

Endpoints

SM-Organisation administration (super-admin only)

  • POST /api/admin/sm-organisations — direct-create SM-managed tenant + invitation
  • POST /api/admin/sm-organisations/self-managed — atomic tenant + scheme + EC invitation
  • GET /api/admin/sm-organisations[?include_self_managed=true&status=active]
  • GET /api/admin/sm-organisations/{tenant_id}
  • GET /api/admin/sm-organisations/{tenant_id}/schemes
  • GET /api/admin/sm-organisations/{tenant_id}/members
  • PATCH /api/admin/sm-organisations/{tenant_id}

Building / scheme onboarding (SA, strata_admin, or strata_manager)

  • POST /api/onboarding/scheme/start — create scheme + onboarding session (SA must supply tenant_id; strata_admin/manager forced to own tenant)
  • GET /api/onboarding/scheme/{session_id}
  • PATCH /api/onboarding/scheme/{session_id} — update step_data
  • POST /api/onboarding/scheme/{session_id}/lots — bulk-import lots, idempotent on (scheme_id, lot_number)
  • POST /api/onboarding/scheme/{session_id}/finalize — post genesis journals, dispatch invitations, mark complete

Multi-tenant isolation

Every endpoint resolves tenant_id from the caller's JWT claim, not from URL parameters or request body for non-SA callers. For SA callers, the body's tenant_id is validated against core.tenants before any write. Postgres RLS on core.lots, core.schemes, core.user_invitations blocks any cross-tenant read or write that bypasses the application layer. See tests/backend/test_onboarding_e2e.py for the live cross-tenant isolation assertion.
