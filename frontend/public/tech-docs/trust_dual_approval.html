Trust Dual-Approval (GAP-FIN-011)

Role note: chairman is not a top-level system role — it is ec_position=CHAIRMAN on a user whose role is ec_member. Role lists on this page naming "chairman" alongside real role names are shorthand for this; see permissions.md for the full contract.
Cutover note: this guide documents the legacy V1 /api/trust/batches* API in routers/trust_accounting.py. Routed V1 responses emit deprecation headers. There is not yet a V2 batch/ABA dual-approval replacement, so Stage 2 V1 write retirement must first decide whether this workflow is replaced or retired after production access-log review.

Technical reference for the ABA batch second-approval workflow

Overview

ABA payment batches with a total value ≥ $5,000 require two separate EC-level approvers. The first approver initiates the approval; the second approver (a different person) finalises it. This implements a four-eyes control on high-value outgoing payments.

Scope: ABA batches only. Non-ABA batches (e.g. manual payments) go directly to approved regardless of value. A separate workflow for ad-hoc special payments > $10,000 is planned (GAP-FIN-011 outstanding scope).

State machine

pending  ──[approve, total < $5k]──────────────────▶  approved
pending  ──[approve, ABA + total ≥ $5k]────────────▶  pending_second_approval
pending_second_approval  ──[second-approve, diff user]▶  approved
Status Meaning
pending Batch created, awaiting first approval
pending_second_approval First approval recorded; ABA ≥ $5k — awaiting second approver
approved Fully approved; ABA file generated (if applicable)

API endpoints

POST /api/trust/batches/{batch_id}/approve

First approval. Requires ec_member, chairman, strata_manager, treasurer, or super_admin role (effective_role aware).

Condition Result
Batch is not pending HTTP 400
Batch not found / wrong building HTTP 404
Insufficient role HTTP 403
ABA batch, total < $5,000 200 — status → approved, ABA file generated
ABA batch, total ≥ $5,000 200 — status → pending_second_approval
Non-ABA batch (any value) 200 — status → approved
POST /api/trust/batches/{batch_id}/second-approve

Second approval. Same role requirements. The second approver's user ID must differ from the first approver's.

Condition Result
Batch is not pending_second_approval HTTP 400
Same user as first approver HTTP 403 — "different person" message
Success 200 — status → approved, ABA file generated, audit log written

Response shape

// POST /trust/batches/{id}/approve — dual-approval triggered
{
  "message": "First approval recorded. A second approver is required (total $6,500.00 ≥ $5,000).",
  "batch_id": "...",
  "status": "pending_second_approval",
  "dual_approval_required": true,
  "aba_generated": false
}

// POST /trust/batches/{id}/second-approve — success
{
  "message": "Second approval complete. Batch approved.",
  "batch_id": "...",
  "status": "approved",
  "aba_generated": true
}

Threshold constant

Defined in backend/routers/trust_accounting.py:

_DUAL_APPROVAL_THRESHOLD = 5_000.00  # GAP-FIN-011

To change the threshold, update this constant and redeploy. No DB config.

Audit trail

Both approve and second-approve write to the audit_logs collection via asyncio.create_task(create_audit_log(...)) (fire-and-forget). Fields recorded:

  • action: payment_batch_approved / payment_batch_second_approved
  • user_id, user_name
  • details.total_amount, details.dual_approval_required
  • details.first_approver (second-approve only)
  • building_id

Role guard implementation

Uses the effective_role pattern to support temp-elevated owners:

def _require_finance_role(current_user: dict) -> dict:
    allowed = {"super_admin", "strata_manager", "strata_admin",
               "ec_member", "treasurer", "admin"}
    effective_role = current_user.get("effective_role") or current_user.get("role", "guest")
    if effective_role not in allowed:
        raise HTTPException(403, "Trust accounting access requires strata manager or EC role.")
    return current_user
