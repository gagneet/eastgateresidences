Mongo → Postgres Finance Sync

The missing half of the dual-storage pattern. Shipped 2026-08-28.

The gap

workers/outbox_relay.py moves events Postgres → MongoDB — its own header says so. It is an audit log, not a ledger sync. Nothing ever ran the other way.

Meanwhile MongoDB is what actually serves finance for East Gate: core.domain_cutover_status had no finance_ledger row, so require_domain_source failed closed to Mongo. Every live finance write landed in Mongo and nothing carried it back — Postgres drifted by exactly the volume of live activity, silently. Measured 2026-08-28: 42 of 87 lots disagreed with the operator's portal scrape.

Updated 2026-08-29. The finance_ledger row is back — all eight East Gate domains are now postgres_write / promoted. And the drift is closed: the nightly check reports 87/87 lots matching, $0.00 net gap, 0 payments missing from Postgres, with the FY2026 unit ledger agreeing to the cent on both sides ($220,187.56 levied / $212,146.26 paid).

This module had never actually run. It shipped complete and unit-tested, but until 2026-08-29 its only caller was a manual scripts/data_repair/ CLI — nothing in workers/, cron/, routers/ or server.py referenced it, so the DR position it protects was never measured. It now runs daily at 03:30 as workers/scheduler.py::finance_dr_drift_check: read-only, drift reported rather than raised, and emitting Demo Bank intake candidates left a deliberate human action via --apply. A unit test on a pure function cannot detect “nothing calls this”; tests/backend/test_finance_dr_sync_wiring.py asserts the wiring.

A feature toggle does not decide the serving source. It only means a PostgreSQL path exists. core.domain_cutover_status is the runtime authority.

What it deliberately does not do

The obvious implementation — copy levy_payments into finance.receipts — is the one thing that must not be built.

Demo Bank is the only door into finance. A direct mirror would manufacture financial facts in Postgres that never passed intake. That failure is already on record twice: East Gate's two disconnected 2021-2025 expense totals ($415,031.21 staged vs $1,502,451.24 GL-posted) diverged 3.6× because two pipelines wrote the same facts and neither checked the other.

So the sync diffs, and emits what is missing as Demo Bank candidates (requires_review=True). Those travel the normal intake → matching → approval → GL route. It never posts a journal entry and never writes finance.*.

Matching rule

Key is (unit_number, amount_cents, payment_date).

PropertyWhy
Not id Mongo and Postgres carry different identifiers for the same fact, and reconstructed history was posted by different scripts — no shared surrogate key exists.
Multiset, not set Two genuine payments of the same amount on the same day are two facts. Set semantics would under-report exactly the duplicate-shaped drift this exists to find.
Confirmed only A pending or rejected Mongo row is not a financial fact yet; emitting it as intake would create one.
Cents at the boundary, once levy_payments.amount is a dollar float — a documented, still-live violation of the cents-only rule. Converted at the adapter edge, never re-derived.

finance.owner_credit_balances

Created by migration 0004, given RLS by 0008, and left with no writer for its entire life. PR #736 added one, but it fires on allocation — so it records credit from that moment forward and could never see over-payments already held.

The consequence: Postgres derives a lot's position from levy_items as charged − paid, and paid_cents never exceeds the charge, so Postgres could not represent a negative balance at all. The portal showed 34 lots holding $35,675.42 of credit; Postgres showed zero, because there was nowhere for it to live.

The backfill reads from compute_lot_true_balances — the canonical owner of that concept. Calling the owner matters: the formula is easy and the filters are the hard part. A hand-written copy that omitted the reversal-parity join and the retired_at check reported $19,000–$30,000 of phantom credit on lots holding none.

Running it

Both scripts are dry-run by default and building-agnostic.

python3 backend/scripts/data_repair/sync_mongo_payments_to_postgres.py --building-id 13195
python3 backend/scripts/data_repair/sync_mongo_payments_to_postgres.py --building-id 13195 --apply

python3 backend/scripts/data_repair/backfill_owner_credit_balances.py \
    --building-id 13195 --financial-year 2026 --apply
