Strata Portal Sync — Technical Reference

Last updated: 2026-06-29. Covers the Civium portal sync bridge: how data flows from portal scrape into review snapshots, levy accounting collections, API endpoints, data precedence rules, and multi-tenant constraints.

1. Overview

The sync feature bridges Civium portal data into the levy accounting collections. Two sync paths exist:

  • Browser scrape — initiated from /admin/strata-sync. Launches a headless browser subprocess that logs in to the Civium portal, navigates financial pages, and writes snapshot data.
  • Push ingest — POST /api/strata/sync/push. Accepts a structured JSON payload for programmatic or Postman-driven ingests without a browser session.

Both paths write to the same snapshot collections and trigger the same bridge logic to populate levy accounting collections. For PostgreSQL finance cutover review, the separate ingestion script backend/scripts/ingest/civium_portal_ingest.py upserts clean dated review documents into staging_civium_snapshots; that staging path never writes directly to annual_levies, levy_payments, or unit_levy_ledger.

2. Data Flow

A two-layer write model applies after every sync:

Layer 1 — Snapshot collections (always written)

Collection Contents
strata_financials Budget vs actual per category from the portal
strata_owners Per-unit balance, levy status, and owner name
bank_accounts Admin fund and sinking fund bank balances
building_summaries Arrears total, collection rate, lot count, risk level

PostgreSQL cutover review snapshot

The finance cutover pipeline also derives a dated MongoDB staging document in staging_civium_snapshots for strata-manager review and super-admin approval. Approval marks the snapshot only; promotion to PostgreSQL happens later through explicit dry-run/apply scripts and never through the finance router's read endpoints.

Layer 2 — Levy accounting collections (written by bridge after every sync)

Collection Write behaviour
levy_categories Always upserted from portal budget line items
annual_levies Created as is_synthetic=True if no record exists; income fields only updated for synthetic records
unit_levy_ledger Created with data_source="scraper" if missing; net_balance always refreshed; levied/paid recalculated only for scraper records
Finance pages read exclusively from the Layer 2 accounting collections. The Layer 1 snapshot collections are the source-of-truth for portal actuals but are not the primary read path for levy calculations.

3. API Endpoints

POST /api/strata/sync/start

Launches the browser scraper subprocess. Returns a job ID. Role required: admin, chairman, or strata_manager.

{
  "job_id": "sync_20260417_143022",
  "status": "started",
  "building_id": "13195"
}

POST /api/strata/sync/pin

Submits the 2FA PIN to the running scraper process during the Civium login flow. Must be called while a scrape job is in the awaiting_pin state.

{
  "job_id": "sync_20260417_143022",
  "pin": "123456"
}

POST /api/strata/sync/confirm

Confirms or discards a scraped data preview. Set "action": "confirm" to commit the snapshot to all collections, or "action": "discard" to abort without writing.

{
  "job_id": "sync_20260417_143022",
  "action": "confirm"
}

POST /api/strata/sync/push

Direct data push for programmatic ingest (Postman, CI scripts). Accepts the full snapshot payload and bypasses the browser session entirely. Same bridge logic runs as after a browser scrape.

{
  "building_id": "13195",
  "financials": [...],
  "owners": [...],
  "bank_accounts": [...],
  "building_summary": {...}
}

GET /api/strata/sync/status

Returns metadata for the last sync job for the authenticated building.

{
  "job_id": "sync_20260417_143022",
  "status": "complete",
  "synced_at": "2026-04-17T14:31:05Z",
  "building_id": "13195",
  "records_written": {
    "strata_financials": 42,
    "strata_owners": 87,
    "bank_accounts": 2,
    "levy_categories": 42,
    "unit_levy_ledger": 87
  }
}

GET /api/strata/financials

Returns all synced budget line items for the authenticated building from the strata_financials snapshot collection.

{
  "building_id": "13195",
  "synced_at": "2026-04-17T14:31:05Z",
  "categories": [
    {
      "category": "Insurance",
      "fund": "admin",
      "planned": 42000.00,
      "actual": 41500.00,
      "variance": 500.00
    }
  ]
}

GET /api/strata/owners

Returns all synced owner levy positions for the authenticated building from the strata_owners snapshot collection.

{
  "building_id": "13195",
  "synced_at": "2026-04-17T14:31:05Z",
  "owners": [
    {
      "unit_number": "101",
      "owner_name": "Jane Smith",
      "net_balance": -250.00,
      "status": "arrears"
    }
  ]
}

4. Bridge Logic

After every successful sync (browser or push), the bridge runs the following upserts in order:

levy_categories

  • Always upserted from portal budget line items unless the building has the disable_strata_sync_direct_write feature toggle enabled — see below.
  • Fields written: building_id, plan_id, category, fund, planned_amount, data_source="scraper".
  • Portal budget lines are always authoritative — categories are never protected from sync overwrites.

Exception: disable_strata_sync_direct_write (East Gate, added 2026-08-19)

For any building with this toggle enabled (East Gate, 13195, is the only one today), run_scraper.py writes only Layer 1 (strata_financials, strata_owners, bank_accounts, building_summaries) — the levy_categories/annual_levies/unit_levy_ledger bridge above is skipped entirely. Per the Financial Evidence Gateway policy, a raw scrape must pass a human review step before it can change a category "actual" figure a dashboard displays.

backend/scripts/reconcile_scraped_financials_to_categories.py is that review step's tooling — it never runs automatically:

  • --preview (default, read-only): diffs strata_financials' scraped actual against levy_categories' stored actual_amount, classifying each category as NEW / UPDATE / UNCHANGED / SKIPPED, plus two review-only classifications never eligible for --apply: ARCHIVED_CONFLICT (the scraped name matches only an archived, already-consolidated category — comparing against its stale figure, or re-inserting under the archived name, would silently undo the consolidation) and DUPLICATE_LIVE_CATEGORY (more than one live, same-fund doc shares the name — no single record to safely target).
  • --apply --authorised-by <uuid> --executed-by <uuid>: re-diffs (never trusts a stale preview) and feeds only the NEW/UPDATE rows through the same reviewed import_gap_tolerant_financial_data() used for the canonical AGM-PDF rebuild. Both identities must be distinct (dual control) and resolve to a real, active, eligible-role (super_admin/strata_admin/strata_manager) users doc.

Never posts to the GL directly — that remains the separate reconstruction-batch pipeline's job via /financials/historical-reconstruction.

annual_levies

  • If no record exists for the year+building combination, a new record is created with is_synthetic=True.
  • For is_synthetic=True records, income fields (proposed_admin_expenses, proposed_sinking_expenses) are updated on every sync.
  • For is_synthetic=False records (CSV upload / AGM-ratified), income fields are never overwritten by the bridge. Only non-income metadata may be updated.

unit_levy_ledger

  • If no ledger record exists for a unit+year+building, one is created with data_source="scraper".
  • net_balance is always refreshed from the portal value regardless of data_source.
  • total_levied and total_paid are recalculated only for records where data_source="scraper".

5. Data Precedence

Source is_synthetic / data_source Bridge behaviour
CSV upload / AGM-ratified data is_synthetic=False Income fields protected — bridge never overwrites
Portal scraper / push ingest is_synthetic=True / data_source="scraper" All fields refreshed on every sync
levy_categories (all sources) Always data_source="scraper" Portal is always authoritative; always upserted
Never set is_synthetic=False on a record unless it has been verified against AGM minutes or a signed CSV import. Doing so permanently shields that record from portal sync updates.

6. Multi-Tenant Rules

  • All sync operations are scoped to building_id derived from the authenticated user's session. Never accept a raw building_id parameter from the request body without server-side validation against the user's context.
  • plan_id is written alongside building_id in all synced records for legacy compatibility. See backend/database.py for the $or query alias.
  • Roles required for sync endpoints: admin, chairman, or strata_manager. Read endpoints (/api/strata/financials, /api/strata/owners) require can_view_finances permission.
  • Sync jobs are isolated per building — a job started for building 13195 cannot write to building 16244.

7. One-time Migration

For deployments that already have snapshot data in the Layer 1 collections but have not yet run the bridge, execute the backfill migration to populate the levy accounting collections:

cd backend && venv/bin/python3 seeds/migrate_strata_sync_to_financial.py

The script uses idempotent upserts and is safe to re-run. It will not overwrite is_synthetic=False records in annual_levies.

8. Financial Import Precision Note

In financial_import_service.py, the fields proposed_admin_expenses and proposed_sinking_expenses represent the levy income targets — the total amount owners are expected to pay into each fund for the year. They are not the fund expenditures (i.e. what the OC spends from the fund).

This distinction matters when calculating per-UOE levy rates:

per_uoe_admin = proposed_admin_expenses / total_unit_entitlements
per_uoe_sinking = proposed_sinking_expenses / total_unit_entitlements

Using expenditure figures instead of income targets will produce incorrect levy rates, particularly when the budget includes carry-over from the prior year or interest income offsets.
