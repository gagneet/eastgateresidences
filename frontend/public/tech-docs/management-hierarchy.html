Management Hierarchy

The management hierarchy feature provides a unified abstraction for representing how a strata scheme is professionally managed — covering agency management, self-managed owner corporations, independent managers, and transitional/unknown states. It was introduced in PR #452 (Alembic 0056–0057).

PostgreSQL only. All management hierarchy data is Postgres-native (core schema). There is no MongoDB collection for this feature. The feature is gated by the management_hierarchy_enabled toggle.

Overview

A strata management company (the agency) may manage many buildings. Within an agency, one or more management entities group buildings. Individual managers are then appointed to specific schemes. This three-level hierarchy replaces the previous flat agency→building direct link. 

core.tenants (agency/org)
  └── core.management_entities  (entity_type: agency | self_managed_oc | independent_manager | unknown)
        └── core.scheme_management_assignments  (is_primary=TRUE, status='active')
              └── core.schemes  (a single strata scheme / building)
                    └── core.scheme_manager_appointments  (individual user appointment)
                          └── core.users  (the appointed manager)

The pre-existing core.agencies table is not removed. Existing agency rows are cross-referenced via management_entities.source_agency_id.

Data Model

Resolution precedence — to answer "who manages this building", walk:

  1. core.scheme_management_assignments WHERE is_primary = TRUE AND status = 'active'
  2. Join to core.management_entities — check entity_type
  3. For entity_type = 'agency', cross-reference core.agencies via source_agency_id
  4. For individual managers, check core.scheme_manager_appointments WHERE status = 'active'
Unique constraint. Only one active primary assignment per scheme is permitted (enforced by uq_sma_scheme_primary_active on (scheme_id, is_primary, status)).

Management Modes

The mode field on EnsureHierarchyRequest drives entity creation. Valid values:

Mode entity_type created Description
agency_managed agency A licensed strata management agency manages the building. Requires source_agency_id.
self_managed self_managed_oc The owners corporation manages itself — no external agency. is_self_managed = TRUE.
independent_manager independent_manager Sole-trader or unlicensed-entity manager. is_independent = TRUE.
unknown unknown Transitional/placeholder state. Entity status is set to pending.

Access Scopes

The service function require_management_hierarchy_access() in backend/services/management_hierarchy_service.py resolves a caller's access scope and enforces read/write gates. Scopes in order of privilege:

Scope Who Sensitive fields returned
platform super_admin Full (ABN, email, phone, legal_name)
agency Caller is an admin of the agency that owns the entity Full
management_entity Caller has explicit management entity membership Full
scheme Caller is an assigned strata_manager for the scheme Limited (name, entity_type, status)
building EC member of the scheme Limited (name, entity_type, status)

Scopes platform | agency | management_entity receive full entity fields. Scopes scheme | building receive filtered fields only (ABN, email, phone, legal_name are omitted).

Security Model

UUIDs are identifiers, not authorisation. Knowing a management_entity_id or scheme_id UUID does not grant access. Every endpoint calls require_management_hierarchy_access() which enforces explicit scheme/entity/agency membership before serving any data.

Access is denied (HTTP 403) unless the caller satisfies one of:

  • Is a super_admin (platform scope)
  • Is an admin of the agency that owns the management entity (agency scope)
  • Has explicit management entity membership (management_entity scope)
  • Is an assigned strata_manager for the scheme (scheme scope)
  • Is an ec_member of the scheme (building scope)

Write operations (ensure, create_appointment) additionally require strata_admin or super_admin role — EC members and strata managers cannot create hierarchy records.

Feature Toggle

KeyDefaultScope
management_hierarchy_enabled enabled Global (building_id = NULL). Per-building override supported.

When disabled, the /management-hierarchy/* endpoints return 403. The toggle is seeded by backend/seeds/feature_toggles.py and resolvable via the standard 3-tier toggle resolution (user-level → building-level → global default).

Roles

RoleScopeNotes
super_admin Platform Full read/write on all entities and appointments
strata_admin Company-wide (tenant scope) Can ensure hierarchy and create appointments for schemes in their tenant
strata_manager Allocated buildings only Read access to assigned schemes; cannot create hierarchy records
ec_member Own scheme only Read access to scheme hierarchy; sensitive fields filtered

Use current_user.get("effective_role") or current_user.get("role", "guest") — never current_user["role"] directly. Raw role is "owner" for temporarily elevated users; effective_role resolves the elevated value.

ValueDescriptionRequires EC approval

independent_strata_managerSole-trader or unlicensed managerNo

building_managerOn-site building manager (operational, not strata)No

EC-internal and volunteer appointment types require approved_by_ec = true before they grant manager-level access. Agency and independent appointments take effect immediately.
