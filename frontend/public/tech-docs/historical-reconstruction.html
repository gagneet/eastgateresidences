Historical Reconstruction And Levy Regeneration

Reference for the reconstruction-batch review/approval workflow and GST-aware historical levy-item regeneration (PR #514, Phase 0B — July 2026, contract-corrected 2026-07-19).

Production tenant rule. These endpoints mutate financial-evidence and ledger-adjacent data. Never run against a live building's real financial years without explicit sign-off; use a test/demo building or is_test_data=true for exploration.

Data Flow

[human-supplied evidence / existing demo_bank_transactions rows]
  -> POST .../reconstruction-batches                (create, status=draft)
  -> POST .../reconstruction-batches/{id}/extract    (status=extracted)
  -> POST .../reconstruction-batches/{id}/generate-preview   (dry-run manifest, no status change)
  -> POST .../reconstruction-batches/{id}/submit-review      (persists manifest, status=needs_review)
  -> POST .../reconstruction-batches/{id}/review     (dual-control step 1: human review, does not approve)
  -> POST .../reconstruction-batches/{id}/approve    (dual-control step 2: DIFFERENT authenticated user, status=approved)
  -> POST .../reconstruction-batches/{id}/generate   (materialises demo_bank_transactions rows)
  -> POST .../reconstruction-batches/{id}/sync       (real bank_feeds sync, scoped to this batch)
  -> [optional] POST .../reconstruction-batches/{id}/reverse

Separately, once a batch is approved:
  -> POST .../levy-items/regenerate-plan   (dry-run GST-aware plan, from_year/to_year)
  -> POST .../levy-items/regenerate-apply  (writes finance.levy_items, requires approved governing batch)

Reconstruction batches and their manifests are MongoDB documents (demo_bank_reconstruction_batches, demo_bank_reconstruction_manifests) — never Postgres tables. Levy-item regeneration writes to Postgres finance.levy_items. The two stores are linked only by convention via reconstruction_batch_id — there is no database-enforced foreign key across them.

Auth And Building Context

  • Auth is action-specific, not one role per router — see the table above. This mirrors the router's own _RECONSTRUCTION_*_ROLES constants exactly.
  • Every endpoint resolves building_id via _assert_building_access() — non-super_admin callers can only act on their own current building.
  • review and approve both always derive their identity from the authenticated caller — neither request body carries an identity field. approve additionally requires the caller to be a DIFFERENT authenticated user than whoever called review (403 otherwise) — genuine dual control enforced server-side, not just a UI confirmation dialog.

Behavior Notes (corrected 2026-07-19)

  • /sync performs a real sync. Previously this endpoint unconditionally marked the batch synced without ever calling the bank-feed sync pipeline. It now calls bank_feeds.run_bank_feed_sync() scoped to this batch via a new reconstruction_batch_id filter on BankFeedSyncRequest. Zero matched transactions or any per-row failure moves the batch to failed, never a false synced.
  • /reverse is not a ledger reversal. It marks the batch reversed and records a full audit trail, but does not itself post reversing journal entries. Pair with FinancialCoreService.reverse_and_replace_posted_levy_journals for the ledger-side reversal once a batch has actually been posted.
  • Genuine dual control, not a single combined call. POST .../review and POST .../approve are now separate endpoints. approve requires reviewed_by to already be set, rejects (403) if the approver is the same user as the reviewer, and re-checks (409) that the persisted manifest hash still matches what was reviewed before transitioning to approved. Both identities still always derive from the authenticated caller, never a client-supplied field.
  • regenerate-apply requires a recorded override justification. When the freshly recomputed plan does not reconcile, override_reconciliation_mismatch=true requires a non-empty override_reason (min 10 characters) — the endpoint previously referenced "a recorded justification" in its error message with no field to record one in.

Behavior Notes (corrected 2026-08-01)

"Idempotent" on /generate has a serious gotcha: it will not revive an archived row. The underlying upsert matches purely on a deterministic idempotency_key (hash of account_ref + posted_date + amount_cents + direction + description) via Mongo's $setOnInsert. If a row with that exact key already exists — even if it is is_archived: true from a previous, since-superseded batch — the upsert matches it and does nothing. It does not un-archive it, does not attach the new batch's provenance, and does not create a fresh active row. Confirmed live 2026-08-01 for East Gate: a fully reviewed and approved batch intended to backfill 176 missing expense rows across 2021-2025 only produced 33 new active rows (all 2026) — the rest silently matched pre-existing archived documents from an older, already-superseded batch and left them untouched. This is not a caching or refresh problem in the UI; the rows are genuinely still archived. If a rebuild/archive-then-regenerate cycle is ever repeated for a building, expect this every time content is byte-identical to something previously archived, and plan for an explicit un-archive step for the confirmed-correct rows rather than assuming /generate alone will make them live. Resolved for East Gate's specific 176 rows via scripts/finances/unarchive_approved_expense_backfill.py (dry-run by default; matches by idempotency_key against an approved manifest, refuses to touch anything with an unexpected sync_status).
The current-year expense clamp makes re-running /generate on the open financial year produce genuine duplicates, not matches. expense_category_generator.py::_expense_effective_date() sets posted_date = min(anchor, today) for the still-open current year. Two batches generated on different calendar days therefore get different posted_dates for the identical category/amount/fund, which changes the idempotency key — the second run inserts a fresh, genuinely duplicate row instead of matching the first. Confirmed live 2026-08-01: reactivating the 176 rows above (see above) also surfaced 33 same-day duplicate 2026 rows from two batches generated one day apart, already synced to Postgres as two separate unmatched finance.bank_transactions rows. Safe to remove only because neither copy had reached match_review_queue or a journal/receipt — always verify that before deleting either side. Cleaned up via scripts/finances/fix_2026_expense_duplicate_from_backfill.py.
The reconciliation-summary fix (below) needed two more corrections after its first live check. _synthetic_bank_totals_by_year_fund()'s initial fix (match provenance_class instead of a stale source_type) was necessary but not sufficient: (1) amount_cents is always a positive magnitude regardless of credit/debit, so without an explicit direction: "credit" filter the query silently summed expense debits into what must be an income-only total — caught because backfilling the missing 2021-2025 expense rows above roughly tripled this function's output for expense-heavy years; (2) the current generator writes every owner-payment credit row to one combined OPERATING-{building_id} account_ref with the real admin/sinking split living only in each row's allocations[], so classifying fund purely from account_ref attributed 100% of that income to "admin" and made sinking-fund income vanish from the report entirely. Both are fixed in services/levy_generation_service.py.
  • Reconciliation Summary used to always read empty. levy_generation_service._synthetic_bank_totals_by_year_fund() (which backs demo_bank_payment_total_cents in the reconciliation-summary response) matched source_type: "synthetic_from_budget" and grouped by a $levy_year field — both belong only to the older migration_026/027 generator. The current generator (budget_levy_generator.py / expense_category_generator.py, via the vendored package's import_historical_reconstruction()) tags rows source_type: "historical_reconstruction" and never persists a year field at all. The query matched zero rows for any building on the current generator, permanently — this looked like a UI refresh bug but was a stale field reference. Fixed to match provenance_class: "reconstruction" (set by both generators) and group by $ifNull: ["$levy_year", "$strata_year"].
  • Audit History "By" column showed "unknown" for every entry. Every create_audit_log() call in this router read current_user.get("name", "unknown") — current_user has no name key (the real field, used consistently everywhere else in the codebase, is full_name) — so every reconstruction-batch audit entry's actor name silently fell through to the literal string "unknown", regardless of who actually performed the action. Fixed across all 15 call sites in this router.
  • demo_bank_transactions.strata_year is not set by the current generator. The vendored package's import_historical_reconstruction() never persists a year field on the document it writes, despite ReconstructedTransactionRow.financial_year being set correctly upstream. scripts/finances/backfill_demo_bank_strata_year.py (dry-run by default) backfills it from the row's description text for already-materialised rows; this must be re-run after every future /generate call until the upstream package persists the field itself.

Operational Examples

curl -X POST "$API_BASE/api/financials/onboarding/building/13195/reconstruction-batches" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"financial_year_start":2022,"financial_year_end":2022,"reconstruction_method":"gst_uoe_largest_remainder_v5"}'

curl -X GET "$API_BASE/api/financials/onboarding/building/13195/reconstruction-batches?status=needs_review&limit=20" \
  -H "Authorization: Bearer $TOKEN"

curl -X POST "$API_BASE/api/financials/onboarding/building/13195/reconstruction-batches/BATCH_ID/review" \
  -H "Authorization: Bearer $TOKEN_REVIEWER" -H "Content-Type: application/json" -d '{"notes":"Totals verified against AGM pack."}'

curl -X POST "$API_BASE/api/financials/onboarding/building/13195/reconstruction-batches/BATCH_ID/approve" \
  -H "Authorization: Bearer $TOKEN_APPROVER" -H "Content-Type: application/json" -d '{}'

curl -X POST "$API_BASE/api/financials/onboarding/building/13195/reconstruction-batches/BATCH_ID/sync" \
  -H "Authorization: Bearer $TOKEN"
