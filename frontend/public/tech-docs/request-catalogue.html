Requests & Applications Catalogue — Tech Docs

The catalogue is the authenticated discovery layer for existing request workflows. It does not create a new request store; each mapped domain endpoint keeps ownership of validation and persistence.

Data Flow

  1. RequestsPage.jsx calls GET /api/request-catalogue.
  2. routers/request_catalogue.py resolves the authenticated user and active building.
  3. request_catalogue_service.py evaluates role, feature, lot and permission policy.
  4. The frontend joins public metadata to local icons and lazy form adapters.
  5. Existing forms submit to their existing domain APIs.

Error Responses

  • 401 — no authenticated user.
  • 403 — building context, role, feature, lot relationship or workflow permission denies access.
  • 404 — definition key is unknown.
  • 409 — definition version is stale.
  • 422 — request payload or parameters fail validation.

Shared Policy

The shared policy supports discovery, form access, submission, review and fulfilment. It evaluates the authenticated user, effective canonical role, building context, definition key/version, required feature, feature overrides, lot relationship and workflow permission. Frontend hiding is not authorisation.

Frontend Adapter Responsibilities

The frontend adapter owns icons, search synonyms and lazy imports only. It must not hardcode role authority. Unknown server keys are ignored to prevent arbitrary client imports. Forms remain lazily loaded so the initial catalogue bundle does not ship every form.

No Migration Required

No PostgreSQL migration is required for Phase 1B. Definitions are code-versioned and existing feature-toggle tables provide building and user availability. A migration should wait until editable per-building catalogue presentation, pricing/document requirements, or a shared request-case record is approved as durable product data.

Safe Workflow Addition Checklist

  1. Add the backend definition with a stable key, version, feature, roles, lot requirement and permissions.
  2. Reuse or add a domain endpoint that enforces building context and owns persistence.
  3. Call enforce_request_policy() before submission writes and before any review or fulfilment action that changes catalogue-owned state.
  4. Add a lazy frontend adapter and keep authority on the backend.
  5. Add backend, frontend, OpenAPI and Playwright coverage.
  6. Update architecture docs, this tech doc and role guides.
