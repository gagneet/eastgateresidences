Levy Due Date Priority Algorithm (Session 68)

The "Due in X days" badge on the Owner Dashboard and EC My Property View uses a two-field priority to determine which date to display. The owner-specific next_due_date from /owners-units/{unit} always takes precedence over the building-calendar period_status.current_due_date.

Data source priority (highest first):
1. next_due_date — owner-specific; computed per-unit from ledger (API: GET /owners-units/{unit})
2. period_status.current_due_date — building's current calendar quarter (same for all units)
3. Fallback hardcoded dates: March 1, June 1, September 1, December 1 (East Gate schedule)

next_due_date Computation Algorithm

Computed server-side in server.py (both GET /owners-units list and GET /owners-units/{unit} single endpoints). Uses integer-cent arithmetic to avoid floating-point rounding errors.

Algorithm (Session 53, refined Session 68):
net_credit = effective_total_paid − opening_arrears
nc_cents = round(net_credit × 100)
pl_cents = round(period_levy × 100)
periods_funded = nc_cents // pl_cents    # integer division
outstanding = (periods_funded + 1) × period_levy − net_credit

Before grace deadline (today ≤ due_dates[periods_funded] + 14 days):
next_due_date = due_dates[periods_funded]

After grace deadline:
next_due_date = due_dates[periods_funded + 1]

Fully paid: next_due_date = None; "All levies fully paid" shown

Registration & User Visibility Architecture

Session 2026-03-30 fixed a critical two-step visibility bug: a user could register successfully but never appear in the admin user list. This section documents the root cause, the fix, and the architectural rules that prevent recurrence.

The Two-Step Visibility Problem

The get_users() pipeline in server.py starts its aggregation from the memberships collection (not users). If a registered user has no corresponding membership document, they are invisible to all admin list views — even though their user document exists in MongoDB.

Root cause: register() in routers/auth.py created a users document and a user_units document but did not create a memberships document. Any registration made before the 2026-03-30 fix produces an invisible user.

GLOBAL vs. TENANT-SCOPED Collections

The database.py module classifies every MongoDB collection as either GLOBAL (shared across all buildings, no auto-injected building_id) or TENANT-SCOPED (the TenantCollection wrapper auto-injects the current building's building_id into every query).

Collection Type Notes
users GLOBAL No auto-inject — building_id must be set explicitly on insert
memberships GLOBAL No auto-inject — building_id from _building_id param
units TENANT-SCOPED Auto-injects building_id — caused 500 when no ctx set
user_units TENANT-SCOPED Auto-injects building_id
feature_toggles GLOBAL Two-tier: global (building_id=None) + per-building override

X-Building-ID Header Flow

The frontend sends X-Building-ID: 13195 (East Gate) in every API request. The FastAPI dependency get_optional_building() (utils/auth.py ~line 281) resolves the building context in this priority order:

  1. JWT token claim building_id
  2. X-Building-ID request header
  3. building_id query parameter
  4. Default: DEFAULT_BUILDING_ID = "13195"

The resolved value is stored in a Python context variable via set_ctx_building_id(). When a TENANT-SCOPED collection is accessed, the TenantCollection wrapper reads this context variable and injects building_id automatically. If no context is set, it raises RuntimeError — which was the original 500 error.

Membership Document Structure

Each membership document created during registration links a user to a building. The document is inserted into the GLOBAL memberships collection with an explicit building_id (not auto-injected by TenantCollection).

{
  "id": "uuid4()",
  "user_id": "<users._id>",
  "building_id": "13195",          // explicitly set from _building_id param
  "roles": ["owner"],              // primary role
  "units": ["TH017"],              // unit(s) associated at registration
  "is_active": true,
  "is_primary": true,
  "created_at": "2026-03-30T..."
}

Known Edge Cases

  • Pre-fix registrations: Users registered before 2026-03-30 may have no membership document. Manually backfill with db.memberships.insert_one(membership_doc) and set correct building_id.
  • building_id=None memberships: A membership with building_id=None will not be returned by get_users() for any building. Fix: update to the correct building_id string.
  • No X-Building-ID header: Falls back to DEFAULT_BUILDING_ID="13195". Safe for East Gate but incorrect for Sierra/Harbourview registrations.
  • Motor collection truthiness: Never use if not db_collection: with Motor — it raises NotImplementedError. Always use if db_collection is None:.

Rollback Mechanism

MongoDB does not support cross-document transactions in the default replica-set-free configuration. Registration uses a best-effort sequential insert approach with a persistence_tasks list:

  1. db.users.insert_one(user_doc)
  2. db.memberships.insert_one(membership_doc)
  3. db.user_units.insert_one(user_unit_doc)

If step 2 or 3 fails, the user document is left orphaned in users. The admin dashboard will not display the user (no membership). A re-registration attempt will return 409 Conflict (email already exists). Resolution: delete the orphaned user document from users and have the person re-register, or manually complete the missing inserts.
