System Architecture

High-level design of the East Gate Residences Strata Management Platform — a full-stack web application for managing an 87-unit residential community.

Current data architecture — verified live 2026-08-19. PostgreSQL is the system of record, but which store serves a read is decided per-domain AND per-building — never by a single global switch. core.domain_cutover_status is the runtime authority: a global feature toggle only says a PostgreSQL path is available; the cutover table is what makes it canonical for a building.

East Gate (13195) is promoted to PostgreSQL across all eight domains — finance_ledger, identity_core, governance, occupancy, settings, trust_ledger, trust_reconciliation and powerhouse_conversations all read and write PostgreSQL, with MongoDB as the DR mirror. Every other building is still served by MongoDB, because all protected toggles remain FALSE globally.

PostgreSQL is at Alembic 0104_manager_fn_scoping with 230 tables across 15 non-system schemas — but only 53 hold rows and 177 are empty, which is what a phased cutover looks like mid-flight. MongoDB holds 226 collections, 153 non-empty, and 128 of those have no PostgreSQL target at all. A domain being promoted does not mean its router reads PostgreSQL: only 10 of 133 routers consult the control plane and 103 call db.<collection> directly, so new code goes through the one dispatch seam, services/store_router.py::resolve_store. Verified live 2026-08-29. Do not restate this from memory: re-run backend/scripts/audits/cutover_readiness_snapshot.py (read-only). See the live PostgreSQL inventory.

System Overview

What it is

A multi-tenant SaaS platform managing an 87-unit strata property (apartments + townhouses). Handles financial management, maintenance requests, communications, compliance, and community features for residents, owners, executives, and administrators.

Hosting

  • Backend runs as a systemd service on a Linux host
  • Frontend is a static React build served via Nginx/Next.js
  • PostgreSQL 16 is the system of record; it serves all eight domains for East Gate today (reads and writes), and backs the financial core, identity, RLS and audit data
  • MongoDB serves every not-yet-promoted building, and is the DR mirror for promoted ones
  • Email via Migadu SMTP (port 465 SSL)
  • Payments via Stripe (test mode)

Design Principles

Backend Patterns

  • Modular routers — one file per domain (finance, maintenance, etc.)
  • Dependency injection — FastAPI Depends() for auth and DB
  • Async everywhere — all DB calls use Motor + await
  • Pydantic validation — models validate at runtime (no migrations)
  • Soft deletes — archive instead of delete for audit trail
  • Permission guards — every protected route calls check_permission()

Frontend Patterns

  • React Context — global auth state via AuthContext
  • ProtectedRoute — wraps all dashboard routes with auth check
  • Feature toggle gating — hasFeatureAccess() before rendering
  • Axios interceptors — auto-attach JWT, handle 401 logout
  • shadcn/ui — accessible Radix primitives for all UI components
  • Tailwind CSS v4 — utility-first responsive styling

Security

  • JWT tokens — 24-hour expiry, HS256 algorithm
  • bcrypt password hashing with salt
  • CORS configured per environment
  • Rate limiting via SlowAPI (optional)
  • Role-based access: 9 roles × 15 permission flags (added real_estate_agent role and can_manage_tenancy permission)
  • No sensitive data in JWT payload

Database Philosophy

  • MongoDB document model — JSON-native, schema-flexible
  • No ORM — direct Motor async queries
  • No migration files — Pydantic runtime validation
  • UUIDs as string IDs alongside MongoDB ObjectIds
  • ISO 8601 strings for all datetime fields
  • Collections initialised via seed scripts

Multi-tenant Architecture

Buildings Model

The platform supports multiple strata buildings. Each building uses its Unit Plan number as the canonical id stored in the buildings collection.

  • East Gate Residences — 13195 (Unit Plan 13195), 14 Hoolihan Street, Denman Prospect ACT 2611
  • Harbourview Residences — 18932, 12 Marina Drive, Pyrmont NSW 2009 (demo)
  • Sierra, Gungahlin — 16244 (Unit Plan 16244), 70 Efkarpidis Street, Gungahlin ACT 2912

Tenant Isolation

TenantCollection wraps every MongoDB collection and injects {"building_id": ctx_building_id} into all queries automatically. The context variable ctx_building_id is set by get_current_building() on every request.

  • All collections backfilled with building_id field
  • memberships collection links users to buildings
  • Super admin sees all buildings; other roles see their own

Multi-tenant Auth Flow

  1. Login → JWT is issued with building_id (auto-resolved from user's memberships)
  2. GET /buildings/me → returns user's accessible buildings
  3. POST /auth/switch-building → returns new scoped JWT with requested building_id
  4. All endpoints using get_current_building extract building_id from JWT

Fallback chain in get_current_building():

  1. JWT building_id claim
  2. User document's building_id field
  3. Single-membership auto-resolve
  4. → 403 if none found

Frontend Building Selection

AuthContext.tsx handles building selection transparently:

  • On login, fetches GET /buildings/me
  • If user has exactly one building, calls POST /auth/switch-building inline (no page reload)
  • Updates tokenRef.current and localStorage with scoped JWT
  • Multi-building users see a building selector UI

Building Switcher Component

BuildingSwitcher.tsx is embedded in the sidebar below the logo:

  • Fetches GET /api/buildings/me on mount to get accessible buildings.
  • If only one building: shows building name and address as a static badge (no dropdown).
  • If multiple buildings: renders a dropdown. On selection, calls AuthContext.switchBuilding(buildingId) which calls POST /api/auth/switch-building, stores the new JWT in localStorage, and triggers a page reload.
  • Switching sets the building_id JWT claim — all subsequent API requests are automatically scoped to the new building via get_current_building() dependency.

JWT Building ID Guarantee

After login, the JWT always contains a building_id claim:

  • If user.building_id is set → use that.
  • Else if user has exactly one active membership → use that building_id.
  • Else → fall back to DEFAULT_BUILDING_ID ("13195" — East Gate Residences Unit Plan).

This guarantees that finance-card endpoints (GET /stats/building-kpis) never receive a None building scope and always return data.
